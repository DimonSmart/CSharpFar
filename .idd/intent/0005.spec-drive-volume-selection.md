# 0005 - Drive and volume selection

## Context

Users need a Far-like way to switch a panel to another drive, volume, or file
system root without typing paths manually.

## Scope / Behavior

- Each panel can open a drive or volume selection dialog.
- The dialog is invoked for the active panel and changes only that panel after a
  successful selection.
- The list includes available local drives and mounted volumes discoverable on
  the current platform.
- The current panel location determines the initial selected list item when a
  matching root exists.
- The dialog shows enough information to distinguish roots, including display
  name, root path, drive type, and available size when that data can be obtained
  without blocking the UI.
- When the active source registry exposes a demo-only file system, the dialog
- lists only the reachable demo volume and does not expose host drives, mount
- points, or other real local roots.
- Slow or unavailable network volumes must not freeze the application while the
  list is being built.
- The drive dialog presents real filesystem volumes before module-backed disk-menu
  entries, preserving the existing order within each group. When both groups are
  present, one table section separator visually marks their boundary.
- Real volumes retain their volume shortcuts. Module-backed entries receive
  dialog-owned numeric shortcuts from `0` through `9` in display order; later
  entries remain selectable without a shortcut and retain the same prefix width.
  A real volume's display continues to consist of its display name and kind
  label; a numeric shortcut prefix is shown only for module-backed entries.
  Module disk-menu projections do not provide competing letter shortcuts in this
  dialog, while their ordinary application-menu shortcuts remain unchanged.
- Activating a displayed volume or numeric module shortcut with one matching
  entry immediately accepts that entry. When a volume shortcut has multiple
  matches, its first press selects the first match and repeated presses cycle
  among the matches without accepting; Enter accepts the current selection.
  Navigation and mouse actions reset that shortcut cycle. The dialog otherwise
  retains ordinary navigation, Enter, mouse, and Escape behavior.
- Keyboard navigation supports moving through the list, accepting the selected
  root, and canceling.
- The volume list uses one shared list state for selection, scroll position, and
  scrollbar drag. Scrollbar clicks and drags may move the viewport without
  changing a selected root that remains visible. Drag input remains captured
  until its matching release.
- When the viewport becomes too small, the dialog and every interactive region
  remain within it. A temporarily unavailable list area has no list or
  scrollbar mouse target; selection is retained for a later larger viewport.
- Cancel leaves the panel unchanged.
- If changing to the selected root fails, the panel remains at its previous
  location and the user sees an error.
- Windows implementation uses Windows drive and volume metadata.
- Linux implementation uses `/proc/self/mountinfo` as the primary source
  when available. It exposes the root file system, separate user-relevant mounts
  such as `/home`, WSL drive mounts such as `/mnt/c`, removable/media mounts,
  and network mounts, while hiding technical pseudo mounts such as `/proc`,
  `/sys`, `/dev`, and `/run`.
- Linux mount-point checks compare normalized paths with mount points from
  mountinfo and report the mount source as the volume name.
- macOS volume discovery and mount-point recognition use macOS-compatible
  platform facilities and show `/` plus accessible mounted local and external
  volumes. They do not use Linux `/proc` interfaces.
- Linux and macOS implementations must not construct Windows-only volume services
  or each other's native volume services.

## Non-goals

- This spec does not require editing mount points.
- This spec does not require showing every possible remote provider.
- This spec does not require complete Linux or macOS mount metadata parity beyond
  user-facing mount discovery and mount-point recognition.

## Acceptance criteria

- The active panel can open a drive/volume list.
- Accepting an accessible root changes the active panel to that root.
- Canceling or failing to open a root leaves the panel unchanged.
- The dialog remains responsive when slow or unavailable volumes exist.
- Initial selection follows the current panel root when possible.
- Scrollbar input updates the committed list viewport without spuriously
  changing a still-visible selection, and a drag can continue outside the
  scrollbar until release.
- Shrinking and restoring the viewport preserves the selected root and never
  publishes dialog or mouse-target bounds outside the viewport.
- A mixed volume/module list shows exactly one table section separator; lists
  containing only one group show none.
- The first ten module entries display and immediately accept shortcuts `0`
  through `9`; further module entries have an aligned blank prefix and remain
  available through normal list interaction.
- Real volumes retain their existing display-name-plus-kind formatting without
  a duplicated shortcut prefix. A unique volume shortcut accepts immediately;
  a duplicate volume shortcut cycles its matches and requires Enter to accept.
- On Linux, the volume list is based on mountinfo when available, includes
  `/` at minimum, includes WSL `/mnt/<drive>` mounts when present, hides
  technical pseudo mounts, and accepting an accessible mount opens that
  directory.
- On macOS, the volume list includes `/` and accessible mounted local or external
  volumes, and accepting an accessible mount opens that directory.
- In a demo-only session, drive or volume selection cannot switch a panel to a
  real host root on Windows, Linux, or macOS.
