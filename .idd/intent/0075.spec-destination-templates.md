# 0075 - Destination templates

Related:
- 0010
- 0060
- 0074

## Goal

Copy, move, and rename provide an explicit destination-template mode that
computes a destination path independently for every selected root source item.

## Behavior

- Copy, move, and rename dialogs expose a `Use template` checkbox adjacent to
  the destination. It is off each time a dialog opens, is never enabled by
  destination text, and is not stored as a default. Destination history may
  store template text as ordinary text.
- With template mode off, destination text remains ordinary text, including
  braces. A final component containing `*` or `?` continues to use only the
  FAR-compatible wildcard behavior from `0074`.
- With template mode on, FAR wildcard transformation is not applied. A template
  containing `*` or `?` is rejected rather than combining two destination
  languages.
- Version 1 recognizes only `{name}`, `{ext}`, and `{modified:<format>}`.
  `modified` formats the source last-write timestamp with invariant .NET custom
  DateTime formatting, without timezone conversion.
- For files, `name` is the filename without its final extension and `ext` is
  that extension including its dot. Dotfiles and names ending in a dot have no
  extension. For directories, `name` is the full directory name and `ext` is
  empty.
- `{{` and `}}` produce literal braces. Unmatched braces, malformed or unknown
  tokens, invalid format results, and token results containing a destination
  provider path separator reject the complete operation before mutation. The
  destination provider defines separator semantics: local Windows destinations
  treat both `\\` and `/` as separators, Unix local destinations treat `/` as a
  separator, and SFTP destinations treat `/` as a separator. A backslash is
  therefore allowed in a token result only when the destination provider allows
  it as part of a component.
- Tokens may appear in any destination path component. Template expansion
  supplies a fragment within one component; the written template itself defines
  directory structure. Required computed target directories are created through
  the normal operation workflow after successful preflight.
- The operation evaluates only explicitly selected root source items. A
  selected directory receives one computed root target and its descendants are
  copied or moved by the existing recursive workflow without template
  evaluation. Mixed file and directory selections are supported.
- Before the first mutation, the operation builds and validates the complete
  source-to-final-target plan. Validation includes template syntax, final path
  validity, provider constraints, self and directory-descendant targets, and
  duplicate computed targets. Any invalid source or duplicate target rejects
  the whole operation. Pre-existing targets continue through established
  operation conflict handling.
- Template evaluation is independent of dialogs, recursive traversal, and
  filesystem mutation, and operates on an extensible source context containing
  name, directory status, and last-write time. Unsupported future metadata
  tokens are validation errors. A future flattening feature may change the
  source set before evaluation; it does not change template semantics.
- The same planning and evaluation behavior applies to writable providers that
  already support copy, move, or rename.

## Non-goals

- Counters, indexes, sizes, hashes, creation/access timestamps, EXIF or other
  metadata extraction, conditions, replacement, regular expressions,
  variables, functions, a template editor or wizard, a batch rename UI, or
  recursive flattening of directory contents.
- Changing FAR-compatible wildcard semantics or automatically selecting
  template mode.

## Acceptance criteria

1. Copy, move, and rename expose an explicit disabled-by-default `Use template`
   mode, while braces remain literal when it is off.
2. `{name}`, `{ext}`, invariant `{modified:<format>}`, and brace escaping
   compute valid per-root targets in file names and directory components.
3. Template mode rejects invalid syntax, unsupported tokens, unsafe token
   fragments, and FAR wildcard characters before mutation.
4. Multi-source and mixed file/directory copy or move can compute different
   target directories; selected directories retain their descendant layout.
5. The full plan is validated before mutation, including duplicate targets and
   self/descendant protections; existing-target conflicts retain their existing
   behavior.
6. Local and writable-provider workflows use the same template planning model,
   while ordinary destinations and FAR wildcard destinations remain unchanged.

## Verification

- Unit coverage demonstrates name/extension edge cases, timestamp formatting,
  escaping, and invalid-template rejection.
- Copy, move, and rename scenarios demonstrate per-source routing, generated
  directories, root-directory preservation, all-or-nothing preflight,
  collision handling, existing-target conflict handling, provider support, and
  preservation of ordinary and FAR wildcard behavior.
