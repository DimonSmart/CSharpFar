# IDD-0019 - Reliable copy resume specification

Related:
- IDD-0010
- IDD-0012
- IDD-0054

## Goal

Offer a `Reliable` local copy mode that automatically retries transient
failures and resumes only operation-owned unfinished copies after verifying
their content. Existing destination data must remain intact until a complete
new version is ready to publish.

The analyzer remains a pure, UI-independent component. Copy mode and
existing-file conflict decisions remain separate choices.

## Context

The destination path selected by the user is **not** a resumable work file.
Even if it is shorter than the source and its tail matches, its ownership
cannot be inferred. Reusing or truncating it would violate the data-preservation
contract in IDD-0010.

Local copy, including files within a copied directory, uses an operation-owned
temporary file in the same destination directory. Failed attempts within this
operation may be resumed from this staging file after validation. A subsequent
independent operation may resume only a previously incomplete file whose
ownership can be safely established; a coincidentally matching user file
is never sufficient proof of ownership.

The user sees normal copy and conflict dialogs; no additional staging UI.

## Scope

- `Reliable` is selected before file or recursive directory copy starts.
  It is not a move/rename or provider copy mode.
- Resolve an existing-file conflict before starting a staging copy.
  `Overwrite` stages a replacement without deleting the existing file.
  `Skip`, `Rename`, and `Cancel` preserve their ordinary semantics.
  Automatic retries must not re-prompt for an already resolved conflict.
- An operation-owned staging file is created alongside the final destination;
  stream writes and retry-time truncation apply only to the staging file.
- After successful copying, close and flush the destination stream, validate
  its expected size when known, apply requested metadata, then publish through
  the safe replacement protocol in IDD-0010. Do not report a completed copy
  before publication succeeds.
- If publication fails, preserve the original destination. If rollback cannot
  restore its path, retain the original backup and report its exact path.
- If reading, writing or cancellation fails before publication, remove only
  the operation-owned staging file, or retain it under a distinct partial name
  when `KeepPartialFilesOnError` is enabled.

## Tail-validation algorithm

The `CopyResumeAnalyzer` evaluates resumability without changing either file.

1. Use seekable source and **owned staging** paths, plus a source length and
   UTC last-write-time snapshot when available.
2. Resume only when `0 <= staging.Length < source.Length`. Empty staging
   resumes from zero; equal or greater lengths are not automatically resumed.
3. Validate the last `min(1 MB, staging.Length)` bytes against the matching
   source range, with a 128 KB comparison buffer.
4. If the tail matches, the stage length is the safe resume offset.
5. Otherwise examine earlier candidates at 1 MB, 4 MB, 16 MB and 64 MB
   rollback windows (factor 4). Do not use nonzero candidates whose
   validation region is shorter than 64 KB.
6. Select the first verified matching candidate; otherwise return an unsafe
   resume decision and restart the **stage** at offset zero.
7. On verified resume, truncate only the stage to the safe offset, seek
   both streams, and finish copying. Never treat an in-memory byte offset
   as sufficient evidence for resumption.

Validation progress reports `Validating partial file...`,
`Tail validation passed` or `Tail mismatch detected`, the verified resume
offset, and rollback bytes when applicable. Total progress accounts for
validated existing stage bytes without double-counting retries.

## Automatic retry

Retry source-open, source-read, destination-open and destination-write failures
as specified in IDD-0054. Reopen streams and validate the physical stage after
a retryable failure. A transient source-read failure alone must not cause a
rollback; only a verified content mismatch can.

If the source snapshot changed or the analyzer cannot validate stage content,
do not resume it. Restart the stage or fail safely; never fall back to editing
an existing user destination.

## Non-goals

- Whole-file hashes or post-copy whole-file hashing.
- Rsync-like block matching or sparse rescue copies.
- Parallel copying of a single file.
- Provider-to-provider seekable resume.
- Retry/validation window configuration UI.
- A second copy engine, new panel architecture, or Append support.

## Acceptance criteria

- `Reliable` remains available for single-file and recursive local copy.
- Existing destination bytes remain untouched before publication, even if
  they match the beginning of the source.
- A midstream failure followed by a successful retry resumes only an owned
  stage from a verified offset and publishes the complete correct result.
- Repeated read failures do not roll back a verified matching stage.
- A failure, cancellation, insufficient space, or unsafe resume never
  truncates the original destination.
- Existing `Overwrite`, `Only newer`, `Skip`, `Rename`, masks, metadata
  and symlink policies remain supported.

## Verification

Test successful and failed overwrite, source/destination faults, cancellation,
size verification, preserved original bytes, stage cleanup/retention,
rollback and progress, retries without extra conflict prompts, and folder
copy. Verify platform-specific replacement and restoration separately.
