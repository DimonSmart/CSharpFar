# IDD-0067 - UI layer composition and modal resize specification

Related: IDD-0002, IDD-0004, IDD-0008, IDD-0016, IDD-0062

## Goal

Render the active full-screen surface and all visible overlays as one coherent
composition. A resize or layer close redraws from current state; it must not
restore outdated captured pixels or consume input belonging to another layer.

This document owns **normative observable behavior and durable architecture
invariants**. Exact private frames, routes, helpers, host constructors,
optimization decisions and the former detailed regression catalog are in the
[non-normative engineering reference](../../docs/architecture/ui-layer-composition-implementation-reference.md).
That reference does not override this intent or current code. Standard
reusable UI control behavior is specified by IDD-0062.

## Composition and ownership

- A full-screen **surface** may be the main panels/hidden-command-line
  workspace, editor, viewer or help. An **overlay** is a popup, top menu,
  completion list, quick-search UI, modal dialog or progress layer above it.
- One ordered layer stack controls both visual stacking and routed input.
  The active composition is the topmost full-screen surface and its visible
  overlays. Closing one returns to the underlying state without stale content.
- Layers have explicit balanced lifetimes; repeated registration of the same
  active interactive layer is not a supported runtime state.
- One shared composition owner is responsible for the viewport, stable render
  retries, overlay/modal lifecycle, interaction routing and final cursor.
  Application-owned surfaces do not run competing stable-frame loops or private
  underlay/screen-snapshot restoration.
- Domain work that may launch commands, modify the layer stack, open a dialog
  or render new UI happens only after routed input dispatch, not during it.
- The main application owns panels, command line, clock, shortcuts and function
  keys; completion, quick search and top menu are separately routed overlays.
  Editor, viewer and help are separate temporary surfaces; search and file
  operation progress are long-lived modal overlays.

## Transactional frames and resize

- An accepted stable frame commits together: visible drawing, viewport,
  geometry, interaction targets, focus/cursor metadata, scrollbar state and
  other frame-dependent state. No part of an unaccepted frame becomes active.
- Input uses the committed frame and target identities that produced the
  visible UI, not geometry recalculated from newer mutable application state.
- A rejected render or viewport race retains the previous committed
  interaction and cursor state. Retrying and resuming input must not apply
  a half-committed focus, scroll, mouse drag, command mapping or editor state.
- Resizing redraws all currently visible layers within the new viewport,
  preserving their stacking order and logical selections, document positions,
  text values, progress and valid focus where possible. Scroll and placement
  are clamped without inventing user actions.
- Resize events are handled by the shared composition and do not reach
  ordinary dialog input handlers as if they were user commands. An already-read
  semantic input event is not discarded during resize recovery.
- The topmost eligible layer owns cursor visibility and position through its
  committed metadata; physical cursor application participates in the same
  accepted viewport-protected frame.
- Small, safe incremental redraws for status, clock, cursor and function keys
  are allowed, but leave the exact same committed input geometry guarantees
  as full rendering. Uncertain layout changes use a full redraw.

### Committed-frame integrity

- Rendering prepares layout, input geometry, selection, focus, scroll,
  diagnostics and related frame-dependent state provisionally; they
  become observable to input only after a complete accepted render.
  A rejected or interrupted frame publishes none of them. Partial
  physical output is repaired by the following complete redraw.
- An accepted frame publishes its committed state and callbacks
  once in a predictable order. Rejected frames neither invoke
  commit callbacks nor consume pending requests for focus, input
  layout, selection or redraw.
- Interactive form and panel input uses geometry from the same
  committed frame that produced the visible UI. Every component
  receives the enclosing frame's viewport; competing nested render
  loops and size rereads cannot publish newer geometry mid-frame.
- A post-dispatch focus request is retained through rejected renders.
  Only an accepted frame can apply a valid enabled target; missing
  or disabled targets are ignored safely, without partial cursor
  changes or child-owned focus commits.
- Panel-scoped operations retain committed source-qualified
  active/passive item and directory identities. When an underlying
  provider or path changes before a command can execute, the
  stale operation is discarded rather than applied to a new item.
  Provider-specific source identity and case rules must be honored.
- Asynchronous or polling UI uses the same accepted data snapshot
  for the displayed rows, scroll position, hit testing and input
  selection. An input must never mix the frame geometry of one
  snapshot with rows from a later snapshot.
- Resize recovery preserves semantic key, modifier and mouse input
  without loss or duplication and never routes it through a
  rejected frame.

## Focus, routing, and modal isolation

- Each interactive layer has an independent focus scope and committed focus
  traversal. An invisible or disabled control must not become an actionable
  target merely because previous UI state once rendered it.
- Keyboard, modifiers and pointer events route through visible layers from
  top to bottom. A handled bubble layer stops dispatch; a modal layer blocks
  lower layers even if it does not otherwise handle the event.
- Mouse target selection uses the topmost matching committed hit region.
  Hit testing alone does not mutate focus; a focus request applies after the
  current routed event is handled.
- Commands and domain transitions run only after dispatch and use the
  committed target identity paired with the event. A stale panel item,
  scrollbar, function-key or directory shortcut mapping cannot silently
  dispatch a different action.
- Synchronous and routed modal handlers receive semantic input paired
  with their corresponding accepted composition frame, not a
  rejected resize recovery frame. Routed component state survives
  from dispatch into its domain handler; rendering/callbacks do
  not silently revert it between those steps.
- Synchronous, interactive and timed modal dialogs and temporary surfaces
  share the same routed composition lifecycle, including cancellation and
  completion wake-up. No synthetic keypress may be used to wake a dialog or
  consume the next event intended for its parent surface.
- Nested modal dialogs preserve and block their parent UI correctly. Closing
  the uppermost dialog redraws the prior layer from state and does not allow
  upper-layer input to fall through.
- Completion may be a bubble overlay, while an open top menu is modal. In
  HiddenCommandLine the panels-only top menu does not render or intercept
  input; switching workspace closes transient panel overlays.

## Mouse normalization and capture

- Windows and ANSI backends normalize mouse presses, releases, double clicks,
  pointer movement, wheels and modifiers into equivalent semantic events;
  mouse release retains the released button identity.
- Passive unpressed pointer movement cannot select, activate, focus or drag.
  It may contribute to an explicitly opted-in hover-reveal presentation.
- Mouse capture is owned by one active layer registration and one committed
  interactive target. A captured drag continues to receive movement and the
  matching release even outside the original hit region.
- Release, owner disposal, a modal layer above the owner, deactivation, loss of
  input policy, or disappearance of the target clears capture. A cleared
  capture is not resurrected when the lower layer becomes active again.
- A newly accepted geometry can rebase an active scrollbar or editor-selection
  drag when the target survives. A rejected frame leaves the old drag and
  capture unchanged. Capture does not alter render order or keyboard focus.

## Surfaces and movable forms

- Application keyboard and mouse actions use the committed main-surface
  state for panel navigation, command-line editing, scrollbars, function-key
  actions and directory shortcuts. Invisible or non-interactive controls
  publish no active pointer targets.
- Editor, viewer and help preserve location, cursor, selection, scroll and
  visible document state when temporarily covered by a modal or interrupted
  by a viewport resize. Nested dialogs own the cursor while open.
- Editor caret blink and lightweight cursor/status/function-bar updates are
  scheduled within the shared UI lifecycle and do not require a permanent
  background render loop or re-running unrelated syntax computation.
- Standard modal forms are centered and fixed by default; drag mobility is
  opt-in. An enabled title-row drag preserves pointer offset, does not
  reassign form focus or alter values, and commits user placement only after
  real movement.
- A user-positioned form retains its position during ordinary redraw and is
  constrained to the visible viewport on resize. A mere title click does not
  switch it from centered to user-positioned mode. A rejected frame cannot
  publish a new title hit region or placement.

## Non-goals

- No private per-dialog modal stack, independent viewport/retry framework,
  raw screen snapshot restoration, or domain command work during routing.
- No requirement to preserve old implementation-specific packet/adapter
  classes, private frame builder names, or test harness constructions.

## Acceptance criteria

1. Resize over panels, hidden command line, editor, viewer, help, progress
   and nested dialogs produces one coherent correct active frame without
   ghosting, stale cursor or incorrect mouse regions.
2. Rejected frames publish no new layout, focus, cursor, capture, selection,
   callback or target state; the next event uses the last committed frame.
3. Modal layers isolate all lower input, nested dialogs restore the correct
   parent state, and application commands run after routed dispatch.
4. Routed keyboard, pointer, scrollbar, function key and shortcut commands
   use committed item/action identity, including on partial redraw.
5. Mouse capture survives movement beyond old bounds, releases or invalidates
   predictably, and does not bypass modal layers or uncommitted frame state.
6. Timed operations complete and cancel without synthetic console input;
   subsequent input remains available to the correct active surface.
7. Editor/viewer/help and movable standard forms preserve state on
   transitions, drag, cancellation and resize.
8. Platform backends provide equivalent semantic mouse events.

## Verification

Use composition and viewport tests with nested overlays and rejected frames;
routing tests for focus, modal blocking, target identity and deferred domain
commands; mouse tests for backend normalization, drag/capture/release and
geometry changes; modal wake/cancellation tests; and editor, viewer, help
and movable dialog scenarios. Real-terminal smoke checks remain useful for
backend-specific cursor, modifier, viewport and restoration behavior.
The linked engineering reference retains the previous detailed test inventory.

The former IDD-0071 contained an overlapping specification and a detailed
transactional-frame test inventory. Its distinctive durable guarantees
are consolidated here. The original complete text and implementation-
specific regression cases are in the
[non-normative frame lifecycle testing reference](../../docs/testing/transactional-ui-frame-commit-reference.md).


The internal main-loop input readiness signal used by integration tests
is documented separately in
[application integration input lifecycle](../../docs/testing/application-integration-input-lifecycle.md).
It is a test-only synchronization mechanism, not a product-facing feature.
