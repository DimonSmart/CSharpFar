# IDD-0062 - Console UI component library specification

Related: IDD-0001, IDD-0002, IDD-0008, IDD-0020, IDD-0021, IDD-0038, IDD-0067

## Goal

Provide independently reusable console UI components for CSharpFar and other
applications. Standard controls must behave consistently for rendering,
keyboard, mouse, selection, scroll, resize, theme, and modal interaction.

This is the **normative intent for reusable components**, not a second owner
of the composition transaction, mouse capture, or scrollbar mechanics. It deliberately
does not prescribe private helper classes, adapter graphs, exact internal
method signatures, implementation sequences, or fixture implementations.
The complete pre-refactor component inventory, former API detail, and
regression checklist are preserved as a
[non-normative engineering reference](../../docs/architecture/ui-component-library-implementation-reference.md).
The reference supports maintenance and historical traceability; it does not
supersede this intent. IDD-0067 exclusively owns committed-frame lifecycle,
modal routing, shared capture and resize; IDD-0020 owns scrollbar geometry,
and IDD-0021 owns scrollbar mouse behavior.

## Reusable and packaging boundaries

- The platform-neutral console contracts, Windows and ANSI terminal backends,
  and reusable UI library form an independently consumable stack.
  A consumer uses the backend appropriate for its platform without loading
  incompatible platform implementations.
- UI components do not depend on CSharpFar file-manager models, application
  services, FTP/SFTP modules, product platform implementations, filesystem
  operations, or shell execution. Product state and actions are adapted by
  the application at the boundary.
- The stack is publishable as a coordinated beta terminal/UI package family
  and usable from source. Public UI contracts must enable an independent
  application without friend assembly access or copied private infrastructure.
  Product-only presentation choices remain outside the reusable packages.
- A runnable independent sample exercises real terminal backends and shared
  controls in complete workflows, including interactive application surfaces,
  menus, dialogs, forms, keyboard/mouse navigation, theme use, and operations.
  A binary-package-only sample build must detect accidental source coupling.
- Public ordinary controls accept semantic state, actions, availability,
  presentation and dialog options. They do not force callers to use private
  rendering frames, target IDs, focus indexes, layout calculators, or input
  packet types. Advanced consumer surfaces may use supported rendering,
  composition and routed-input APIs.
- This is a narrow component library, not a generic application framework,
  MVVM engine, widget tree or retained-mode UI framework.

## Standard component reuse

- Reuse or extend the library's standard primitives for list/table selection,
  scrolling, text/history input, dropdowns, checkboxes/choices, buttons,
  function-key bars, menus, popup frames, forms and modal dialogs. Application
  dialogs own their domain data, actions and results, not duplicate input,
  scrollbar, underlay, frame, and focus code.
- Interactive reusable components expose testable logical state and
  viewport-bounded presentation. Frame acceptance, committed interaction
  geometry and rejected-frame rollback are governed by `IDD-0067`, not
  redefined by individual components.
- Standard selectable lists/tables preserve identity, selection and a visible
  clamped viewport. Up/Down, PageUp/PageDown, Home/End, Enter, wheel and pointer
  selection behave predictably; resize must not select a different logical item.
- Standard components reuse scrollbars; `IDD-0020` exclusively defines their
  placement/visibility and `IDD-0021` their mouse hit targets, movement and
  drag semantics. Shared mouse capture and commit rules belong to `IDD-0067`.
- Dropdowns and history suggestions preview without committing. Escape and
  clicks outside close the popup without accepting that preview. Mouse wheel
  input inside a dropdown belongs to that dropdown, not the containing form.
- Single-line editing can use history and a host-provided clipboard abstraction.
  Text width, cursor, selection, clipping and mouse positions use terminal-cell
  semantics: CJK characters, wide emoji and combining marks must not corrupt
  adjacent cells, layout bounds or input mapping.
- Checkbox, tri-state and single/multiline choice controls expose clear
  focus, navigation and mouse behavior. A multiline choice remains one logical
  focused control; its cursor follows the selected choice marker.
- Disabled ordinary controls cannot receive focus or action, use a semantic
  disabled appearance, and show a supplied reason only while disabled.
  Re-enabling restores ordinary behavior.
- Function-key bars map clicking a rendered enabled slot to the matching
  semantic keyboard action. Invisible/disabled slots do not remain interactive.
- Standard buttons support focus, key activation, pressed feedback and
  activation on release over the same enabled button; release elsewhere cancels
  the press. Button IDs alone never imply a cancel or submit role.
- Optional truncated-text hover presentation stays within its own terminal-cell
  boundaries and does not start a private renderer. Pointer event routing and
  the distinction between movement and activation belong to `IDD-0067`.

## Themes, forms and dialogs

- A single shared theme is the source of semantic visual roles for reusable
  controls. Ordinary component APIs do not thread a product-specific palette
  through every call or hardcode independent component colors.
- The reusable palette uses generic roles and presets; CSharpFar-specific
  file/panel/module roles and product palettes remain in the application layer.
  Normal, focused, selected, disabled, popup, warning and error visuals use
  appropriate semantic theme roles.
- Standard forms offer consistent keyboard focus traversal, form validation,
  disabled behavior, pointer interaction, body scrolling, and viewport-safe
  layout. Labels, controls and disabled reasons remain intelligible at narrow
  widths.
- Standard dialog footer actions remain reachable independently of body
  scrolling. Dialog buttons, borders, background, popups, shadows, clipping
  and cursor ownership use shared behavior and current theme roles.
- Standard and composite dialogs use common preferred sizing and optional
  width/height expansion, constrained to the active viewport. Form value and
  valid scroll/focus state survive resize without a second modal loop.
- Composite dialogs can combine form controls, independently routed main
  content, status and actions using the shared modal lifecycle.
- Operation dialogs support asynchronous progress, cancellation, completion,
  failure and nested confirmation without fake input or a parallel event
  loop; cancellation and task cleanup are observed before completion.
- Popups and dialogs use the shared composition lifecycle owned by
  `IDD-0067`; their closure and underlying-surface redraw do not establish
  separate pixel restoration or input routing rules.

## Non-goals

- No file-manager domain models, plugin registration, persistence, process
  execution, or filesystem behavior in reusable components.
- No mandatory private API shape, class list, test fixture implementation,
  UI framework replacement, or hardcoded visual layout for every dialog.
- No parallel modal systems, independent component theme registries,
  duplicated scroll/capture implementations, or private snapshot restoration.

## Acceptance criteria

1. An external sample can use the reusable UI with production console backends
   and, separately, binary packages without depending on CSharpFar product code.
2. Product dialogs use standard semantic UI controls rather than private UI
   internals or duplicated modal, scrollbar, focus and input machinery.
3. Themes, disabled state, narrow layouts, dropdown preview, scrollbars, lists,
   buttons, function-key bars and text inputs behave consistently across
   application surfaces and modal dialogs.
4. Text input and component presentation handle wide Unicode without
   corrupting adjacent terminal cells or component layout bounds.
5. Shared forms and composed operation dialogs offer accessible footer actions,
   validated control state, and meaningful cancellation/completion results;
   the modal isolation and frame/cursor guarantees are verified under `IDD-0067`.
6. Component actions remain testable without constructing CSharpFar product
   services; scrollbar presentation/input obey `IDD-0020`/`IDD-0021` and
   accepted frames, routing and resize obey `IDD-0067`.

## Verification

Test a standalone source and binary-package consumer on supported platforms.
Exercise lists, tables, forms, buttons, dropdowns, text/history, menus, mouse
capture, theme and resize with keyboard and pointer input, including disabled,
error and cancellation paths. Verify terminal-cell width, scroll/selection
bounds, modal focus and nested progress. Use composition test hosts for routed
frames and consult the linked engineering reference for prior API-specific
test cases and the full regression inventory.
