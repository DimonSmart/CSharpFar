# IDD-0013 - Dynamic function key bar specification

Related:
- IDD-0012

## Goal

Make the bottom function key bar a real part of the command and key binding system.

The bar must show the actions that are available for the current function-key modifier state. When the user holds `Alt`, the row changes to `Alt+F...` actions. When the user holds `Control`, the row changes to `Ctrl+F...` actions. Releasing the modifier restores the plain function-key row.

The behavior should feel close to Far Manager: the row is not just static decoration; it follows the active key layer and must not advertise actions that the current application state cannot execute.

## Context

Function-key actions span several modifier layers and have availability that
depends on the active panel and provider capabilities. The bottom bar, shortcut
hints, and command invocation must remain consistent: independently maintained
labels and key maps can otherwise advertise an action that cannot run.

Some terminal input backends report separate modifier press/release events;
others report only completed key chords. The held modifier display must respect
the actual capabilities of the active backend.

## Scope

Maintain a shared command-binding contract for function-key commands, covering
stable command identities, key chords, concise labels, command execution, and
context-sensitive availability. Binding information used for display must be
consistent with the information used for keyboard and mouse command dispatch.

Required key layers:

1. plain function keys;
2. `Alt` + function keys;
3. `Control` + function keys;
4. `Shift` + function keys when the layer contains real commands such as
   `Shift+F6` rename.

Bindings cover `F1` through `F12`, including `Alt+F11` and `Alt+F12`.
The bar may clip or omit trailing keys on narrow terminals, but the available
bindings must not be limited to `F10`.

Application-level shortcut display is resolved by command identity, including
non-function-key shortcuts such as `Ctrl+O`. Menus and other command surfaces
must not maintain divergent shortcut text for the same action.

### Modifier state

The application must track the currently pressed key-bar modifier state independently from completed key chords.

Rules:

1. Pressing `Alt` alone changes the bottom row to the `Alt` layer.
2. Pressing `Control` alone changes the bottom row to the `Control` layer.
3. Releasing the modifier restores the plain layer.
4. Modifier-only events must not execute commands.
5. Modified function keys still execute their command normally, for example `Alt+F7` runs search.
6. Repeated modifier events should not cause unnecessary full-screen redraws when the visible layer did not change.
7. If both `Alt` and `Control` are pressed, show the plain layer unless a real `Ctrl+Alt` function-key layer is introduced by a later spec.
8. When the visible layer does change, the application and editor redraw only
   their function-key bar and republish its committed action targets unless
   another pending change requires a complete surface render.

The held modifier layer must come only from actual press/release state reported
by the active input backend, such as supported Kitty, evdev, or Win32 modifier
reporting. Modifiers accompanying a completed key chord apply to that chord
only and must never make the displayed layer sticky. In legacy terminal modes
without physical modifier reporting, the bar may remain plain while modified
shortcuts still execute. Focus loss and input suspend must reset the held layer
before new commands. Switching between the main workspace, editor, and modal
views must not revive a stale layer.

### Rendering

The bottom bar displays labels resolved from the active function-key layer.

Rendering rules:

1. Keep the existing Far-like number and label color split.
2. Fill the full bottom row background as today.
3. Show only commands that exist in the active layer.
4. For unavailable commands, either hide the label or render it with a disabled style; choose one behavior and keep it consistent.
5. Do not show a label for a command that the handler would reject in the same state.
6. Keep one-row rendering; no wrapping.
7. Clip cleanly on narrow terminals without ellipsis.
8. Do not resize panels or the command line when the key-bar layer changes.

Suggested plain layer:

```text
1Help 2UserMn 3View 4Edit 5Copy 6RenMov 7MkFold 8Delete 9ConfMn 10Quit
```

Suggested `Alt` layer:

```text
1Left 2Right 7Search 8History 11FHist 12DHist
```

Suggested `Control` layer:

```text
3SortNm 4SortExt 5SortTm 6SortSz
```

Suggested `Shift` layer:

```text
6Rename
```

Labels may be shortened if the final renderer needs tighter text, but they must remain recognizable and consistent with the actual command.

### Command handling

Function-key command execution and key-bar presentation must use the same authoritative binding information.

Rules:

1. Avoid independent copies of command chords, labels, and availability rules in dispatch and presentation.
2. Keep most non-function-key commands such as `Ctrl+Q`, `Ctrl+A`, arrows,
   `Enter`, and command-line text routing outside this spec unless a small
   helper is needed to keep input routing readable. `Ctrl+O` is part of the
   command binding data for primary shortcut display and dispatches through the
   same registered command id as the corresponding menu item.
3. Keep menu command ids reusable where they already exist, but do not force all panel commands through the top-menu command system if that makes the change larger than needed.
4. Preserve existing behavior for plain function keys and existing modified function-key commands.
5. Preserve the rule that `Alt+F7` is search and plain `F7` is create folder.
6. Preserve the rule that `F9` opens the top menu.
7. `Shift+F6` executes the rename command from
   `IDD-0060` and must use its own command id rather
   than falling through to plain `F6`.

### Availability

The bar should reflect the same state checks as command execution.

Required examples:

1. On local filesystem panels, plain `F4`, `F5`, `F6`, `F7`, and `F8` keep their current behavior.
2. On search results panels, availability follows the referenced-item capabilities defined in `IDD-0012`: structural read-only status alone does not disable `F4` or `F8`.
3. `F4 Edit` is advertised when the active search result is an editable file and the same capability check permits command execution. Directories are not editable.
4. `F8 Delete` is advertised when the active search-results panel supports deletion, using the same capability check as command execution. It deletes referenced items, not virtual rows alone.
5. `F6 RenMov`, `Shift+F6 Rename`, and `F7 MkFold` remain unavailable for search results; `F5 Copy` may remain available when the source supports `CopyFrom` and the destination supports `CopyTo`.
6. For any other read-only source, unavailable file operation commands must not be advertised as executable.
7. `Ctrl+F3` through `Ctrl+F6` remain available only when the active panel can be sorted.

## Non-goals

Do not implement in this spec:

1. a full shortcut help system for every key combination;
2. dynamic hints for non-function-key commands generally, except contextual
   bottom-action hints explicitly required by another current specification;
3. a plugin API for third-party commands;
4. a configurable keyboard layout or user-editable key bindings;
5. extra `Shift` function-key commands beyond commands owned by current specs;
6. a `Ctrl+Alt` layer;
7. mouse hover help for the bottom bar.

## Acceptance criteria

- Plain bottom row still shows the current `F1` through `F10` actions.
- Holding `Alt` changes the bottom row to the `Alt` function-key layer.
- Releasing `Alt` restores the plain layer.
- Holding `Control` changes the bottom row to the `Control` function-key layer.
- Releasing `Control` restores the plain layer.
- Holding `Shift` changes the bottom row to the `Shift` function-key layer when
  `Shift+F6` rename is available.
- `Alt+F7` still starts search and plain `F7` still creates a folder.
- `Shift+F6` starts rename and plain `F6` keeps move behavior.
- `Alt+F1`, `Alt+F2`, `Alt+F8`, `Alt+F11`, and `Alt+F12` keep their current behavior.
- `Ctrl+F3`, `Ctrl+F4`, `Ctrl+F5`, and `Ctrl+F6` keep their current sorting behavior.
- The key bar is rendered from the same binding data that command dispatch uses.
- Keyboard and mouse activation of a function-key binding use the same
  committed panel command invocation, including the committed active side,
  visible rows, and active and passive panel keyboard snapshots.
- The active and passive panel snapshots, including current-item operands, are
  source-qualified. A function-key command is discarded when the live
  `PanelLocation` differs from the committed location, even when the display
  path and item index are unchanged.
- Primary shortcut display can be resolved by command id for both function-key
  bindings and registered keyboard shortcuts.
- The key bar does not show file operation commands as available when provider capabilities would block them.
- On a search results panel, `F4 Edit` is available for an editable referenced file, and `F8 Delete` is available for referenced items when deletion is supported. Both use the same capability checks as execution.
- On search results, `F6` move, `Shift+F6` rename, `F7` create, and copying or moving into the virtual panel remain unavailable.
- Modifier-only key events do not insert command-line text and do not execute commands.
- Modifier-only layer changes do not rebuild unrelated panel, command-line, or
  editor content.
- Narrow terminal rendering stays one row and clips cleanly.
- Existing menu, command line, panel navigation, and dialog key handling keep their current behavior.
- A contextual non-function-key action hint required by another current
  specification is displayed only when its command is available and does not
  alter function-key binding labels or command dispatch.

## Verification

Automated verification covers the binding catalog as the shared source for
labels, keyboard dispatch, mouse dispatch, availability filtering, and shortcut
display. Component-level checks own slot layout, clipping, and function-key
mouse hit testing. Application-level checks own user scenarios: modifier-only
layer changes without command-line text insertion, executable keyboard and
mouse function-key commands, provider-capability filtering (including enabled
`F4` and `F8` on search results and blocked move/create/rename), and committed-frame
command invocation.

Manual verification is justified for terminal modifier press/release behavior
and narrow real-console rendering where backend event timing or host rendering
can differ from deterministic fake-console input.
