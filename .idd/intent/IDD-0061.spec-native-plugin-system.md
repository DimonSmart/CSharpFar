# IDD-0061 - Native plugin system specification

Related: IDD-0029, IDD-0035, IDD-0073

## Goal

CSharpFar uses a single registration mechanism for native, in-process .NET
plugins. First-party FTP/FTPS, SFTP, and Processes and Ports use the same
`ICSharpFarPlugin` and `IPluginHost` contracts as plugins explicitly supplied
by the application's composition root. The host does not discover, load,
install, sandbox, or version arbitrary plugin DLLs.

The neutral API is in `CSharpFar.Plugin.Abstractions`. No public plugin
contract depends on application implementation classes or FarNet.

## Registration and ownership

The composition root constructs a `PluginDescriptor` and plugin instance for
each enabled plugin. The native runtime supplies a **plugin-bound host** and
invokes `InitializeAsync`. Registration is a one-time initialization phase.

Each plugin may register:
- commands with plugin-local identifiers;
- `Plugins` and disk-selection menu items pointing to its own commands;
- globally unique, case-insensitive command-line prefixes;
- panel providers returning `PluginPanelOpenRequest`.

Registrations are collected as a batch and validated *after* initialization,
allowing menu items to be declared before commands. Duplicate local IDs,
duplicate global prefixes, unknown command targets, invalid IDs, and failed or
cancelled initialization reject the entire batch. Failure does not publish
partial commands or menu entries. Other plugins may continue initialization.
Once composition completes, the runtime is sealed against more registrations.
Menu ordering follows successful plugin and item registration order, never
hash-table enumeration order.

Plugin-local command, menu and provider IDs may be reused by different plugins.
Existing built-in menu action GUIDs are carried explicitly by descriptors and
remain stable; arbitrary plugin-local menu IDs receive stable application-side
action identifiers based on both plugin ID and local item ID. The
application's menu projection is not a second command registry.

## Bootstrap completion and failure isolation

An explicitly supplied external plugin enters the same ordered composition as built-in
plugins. The synchronous application factory supports plugins whose initialization
finishes synchronously. If initialization remains pending, it fails promptly with
guidance to use the asynchronous factory; it does not block the terminal thread.
A failed composition closes publication before it returns an error. A late
in-process initializer cannot publish after this point, even if it ignores cancellation.

The asynchronous factory waits for each initialization in composition order.
A plugin's own cancellation is a local registration failure when startup was not
cancelled. Cancellation of the overall startup stops the remaining registrations
and never returns a partially composed application. Independent local failures
leave previous successful registrations intact and do not prevent subsequent
plugins from registering. All effective menu action identifiers, both supplied
and application-generated, must be unique.

An unsuccessful registration releases resources owned by its staging batch.
Runtime-owned providers live for the application session and are released at
shutdown; file-panel sources follow their separate source-registry ownership.
Demo plugin settings are removed at session shutdown. Arbitrary in-process
plugin code cannot be forcibly terminated or prevented from retaining its own
resources.

The user receives a single summary of failed plugin initializations once the
terminal UI is ready, even without diagnostics enabled. Detailed plugin events
enter only the opt-in diagnostics report and are sanitized. During asynchronous
bootstrap, modal UI calls are permitted only on the terminal-owning thread.
Plugins can register metadata after asynchronous waits, but should defer
interactive UI to runtime commands; modal UI calls from another thread fail
locally without touching the terminal.

## Invocation and results

A command receives a snapshot of the requested panel side, invocation origin
(`Plugins` menu, disk menu, or command line), cancellation token, application
context, host-bound settings, UI and credential facades, and (for command-line
invocations only) the raw input and unmodified argument substring.

The side is the active side when a Plugins menu/command-line entry is invoked,
or the explicitly requested side for `Alt+F1`/`Alt+F2`. Later changes to
active UI state do not change an in-progress invocation.

The runtime converts command exceptions and cancellation to distinct outcomes:
completed, open panel, cancelled, or failed. Known prefixes are considered
handled even if their command fails or is cancelled; they never fall through to
the external shell. `ShellInvocationParser` retains its precedence before
plugin prefix matching. Prefix scanning stops at the first colon or whitespace
and does not perform shell-like tokenization.

The application command interface remains synchronous, but unfinished plugin
`ValueTask` results are awaited asynchronously and their completion is queued
back to the application input/UI loop. Terminal modal operations must run on
the UI thread. The application does not synchronously block the UI on
unfinished plugin operations.

## Built-in plugins and legacy behavior

The composition order is SFTP, FTP/FTPS, Processes and Ports.

- SFTP registers `SFTP...` in Plugins, `SFTP` in both disk menus, the `sftp`
  prefix, and a connection-panel provider.
- FTP/FTPS registers `FTP/FTPS...` in Plugins, `FTP/FTPS` in both disk menus,
  `ftp` and `ftps` prefixes, and a connection-panel provider.
- Processes and Ports registers `Processes and Ports...` and `ports` with
  optional text after the first colon or whitespace. It is a dialog, not a
  file-panel provider.

FTP/FTPS and SFTP prefix commands continue to open the saved connection
manager; they do not parse an optional path/URL as a connection target.
The disk-menu entries also open the connection manager, rather than
enumerating saved connections. Existing protocol engines, terminal dialogs,
storage files and credentials remain unchanged by the plugin refactor.

The first-party network modules continue using their narrowly scoped legacy
dialog/startup collaborators to preserve credential keys and stored
connection formats. Those collaborators do not register menus or commands.
Newly composed plugins receive standard plugin host services.

The existing module GUIDs remain stable:

- FTP: `e56632fd-6aa0-4e5b-a43c-0d48ba2ea7bd`
- SFTP: `2c5a3c9b-5b79-4986-8569-f06a1fb57c31`

Their saved connection files remain at
`<config>/plugins/<module-guid>/ftp-connections.json` (FTP) and
`<config>/plugins/<module-guid>/connections.json` (SFTP). The existing
`CredentialId` is used literally, including unprefixed SFTP credential IDs;
there is no migration and passwords are not embedded in JSON.

## Panel integration and lifecycle

Opening a plugin panel supplies an `IFilePanelSource`, its existing
`PanelSourceId`, start directory, title, and any format/shortcut/free-space/
key-bar metadata. The application retains `PanelController`,
`PanelLocation` and `FilePanelSourceRegistry` as the execution path.

Remote source identity remains
`plugin:{module-guid:D}:{connectionId}`, not `ftp:{connectionId}` or a
random opening-session ID.

The source is registered and the initial location is loaded before changing
the displayed title, quick view or active side. Load failure preserves the
previous panel, rolls back a newly registered source and disposes unused
owned sources. Rejected newly created sources are disposed exactly once; if
cleanup is asynchronous, it proceeds without blocking the terminal input loop.
Cleanup failures are observed and reported to diagnostics without replacing
the original open failure, and pending cleanup is completed during application
shutdown. Existing compatible registered sources are never disposed as part of
rejected-source cleanup. A duplicate source ID never silently replaces a live source.
An existing source may be reused only when it explicitly reports compatible
connection settings. Saved plugin sources remain registered during the application session and
are disposed at shutdown. Temporary connection sources remain registered
while referenced by either panel or by an active operation; after the last
reference and operation are gone they are unregistered and disposed.
Common local/demo sources are not treated as plugin-owned.

## Settings, credentials and demo mode

Settings access is bound to a plugin ID; a plugin cannot use the ordinary
settings facade to request another plugin's folder. New plugin credential
identifiers are namespaced by plugin owner. This is a programming/API boundary,
not a security sandbox for arbitrary in-process .NET code.

`IPluginApplicationContext.RunMode` exposes Normal or Demo in initialization,
commands and panel providers. In demo mode the host provides a separate
temporary plugin settings area and denies access to real credentials. FTP and
SFTP are not composed in the built-in demo session. Processes and Ports uses
the deterministic demo platform service and must not terminate real processes.
Plugin authors must not perform real destructive local/network operations in
demo mode. In-process arbitrary code could bypass these APIs; the host does
not claim isolation from untrusted plugins.

Simple messages, input and menus are available via `IPluginUiService`.
First-party complex dialogs continue using the existing modal UI lifecycle.

## Non-goals

No dynamic DLL discovery, NuGet plugin installation, marketplace, hot reload,
permission model, sandbox, out-of-process plugins, event bus, editor/viewer
extensions, scripting system, FarNet compatibility, or protocol rewrite.

## Verification

Automated integration tests should demonstrate an independent plugin registering
commands, both menu placements, a prefix and a virtual panel using only neutral
contracts. Other tests protect atomic registration, collisions, cancellation,
incomplete asynchronous commands, immutable target side, demo service isolation,
source identity, compatibility and ownership, and existing first-party
connection and process behavior.
