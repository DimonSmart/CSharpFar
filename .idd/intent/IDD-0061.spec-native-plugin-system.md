# IDD-0061.spec-native-plugin-system

Related: IDD-0029, IDD-0035, IDD-0073, IDD-0086

## Goal

CSharpFar uses a single registration mechanism for native, in-process .NET
plugins. First-party FTP/FTPS, SFTP, Processes and Ports, Network Traffic,
and Archives use the same
`ICSharpFarPlugin` and `IPluginHost` contracts as plugins explicitly supplied
by the application's composition root. At normal startup, the host discovers trusted external plugins from the user configuration directory and from the official application distribution. All plugins share the same
registration, validation, dispatch and ownership runtime; discovery does not
introduce a second registry.

The neutral API is in `CSharpFar.Plugin.Abstractions`. No public plugin
contract depends on application implementation classes or FarNet.

## Registration and ownership

The composition root constructs a `PluginDescriptor` and plugin instance for
each enabled plugin. The native runtime supplies a **plugin-bound host** and
invokes `InitializeAsync`. Registration is a one-time initialization phase.

Each plugin may register:
- commands with plugin-local identifiers;
- `Plugins` and disk-selection menu items pointing to its own commands;
- globally unique, case-insensitive command-line prefixes;
- panel providers returning `PluginPanelOpenRequest`.
- optional `IFileOpenHandler` registrations which claim files on Enter.

Registrations are collected as a batch and validated *after* initialization,
allowing menu items to be declared before commands. Duplicate local IDs,
duplicate global prefixes, unknown command targets, invalid IDs, and failed or
cancelled initialization reject the entire batch. Failure does not publish
partial commands or menu entries. Other plugins may continue initialization.
Once composition completes, the runtime is sealed against more registrations.
Menu ordering follows successful plugin and item registration order, never
hash-table enumeration order.

Plugin-local command, menu and provider IDs may be reused by different plugins.
Existing built-in menu action GUIDs are carried explicitly by descriptors and
remain stable; arbitrary plugin-local menu IDs receive stable application-side
action identifiers based on both plugin ID and local item ID. The
application's menu projection is not a second command registry.

## Bootstrap completion and failure isolation

Externally discovered and explicitly supplied plugins enter the same ordered
composition after built-in plugins. The synchronous application factory supports plugins whose initialization
finishes synchronously. If initialization remains pending, it fails promptly with
guidance to use the asynchronous factory; it does not block the terminal thread.
A failed composition closes publication before it returns an error. A late
in-process initializer cannot publish after this point, even if it ignores cancellation.

The asynchronous factory waits for each initialization in composition order.
A plugin's own cancellation is a local registration failure when startup was not
cancelled. Cancellation of the overall startup stops the remaining registrations
and never returns a partially composed application. Independent local failures
leave previous successful registrations intact and do not prevent subsequent
plugins from registering. All effective menu action identifiers, both supplied
and application-generated, must be unique.

An unsuccessful registration releases resources owned by its staging batch and,
when disposable, the plugin instance itself. Successfully registered disposable
plugin instances are released after their providers on session shutdown.
Runtime-owned providers live for the application session and are released at
shutdown; file-panel sources follow their separate source-registry ownership.
Demo plugin settings are removed at session shutdown. Arbitrary in-process
plugin code cannot be forcibly terminated or prevented from retaining its own
resources.

The user receives a single summary of failed plugin initializations once the
terminal UI is ready, even without diagnostics enabled. Detailed plugin events
enter only the opt-in diagnostics report and are sanitized. During asynchronous
bootstrap, modal UI calls are permitted only on the terminal-owning thread.
Plugins can register metadata after asynchronous waits, but should defer
interactive UI to runtime commands; modal UI calls from another thread fail
locally without touching the terminal.

## External extension installation and binary contracts

External extensions are installed as independent directories under
`<config-directory>/extensions/<extension-folder>/` or shipped under
`bundled-extensions/<extension-folder>/` beside the real application executable.
Each contains a
`plugin.json` manifest with `id`, `name`, `version`, `apiVersion` (currently
`2`), `assembly` (one DLL filename), and `entryType` (fully qualified class
name). The file name must be a single safe path component. The entry class must
be public, implement `ICSharpFarPlugin`, and provide a public parameterless
constructor. Extensions are enumerated in deterministic directory-name order,
with built-in plugins composed first. A missing extensions directory is normal.
No arbitrary assembly scanning or download takes place.

Malformed manifests, missing assemblies or types, unsupported API versions,
construction failures and incompatible types are reported per extension without
preventing other extensions from loading. Plugin IDs are unique regardless of
letter case, and this rule also applies to collisions with built-ins. The
startup failure summary includes discovery failures as well as initialization
failures. Extensions are disabled in demo mode by default.

Each extension loads in a separate `AssemblyLoadContext` using
`AssemblyDependencyResolver` for private managed and native dependencies.
`CSharpFar.Plugin.Abstractions` and `CSharpFar.Core`, whose types form the
public contract, resolve to the host's default context. Private dependency
versions must not clash across extensions. No unload or hot reload is provided.
The host offers reproducible versioned NuGet binary packages for the public
contract assemblies; authors can build without the application source tree.
A writable file-panel provider needs only IFilePanelSource and the relevant
operation capabilities. Transactional batches and safe-publication interfaces
are optional and indicate stronger guarantees, not prerequisites for copying.
The host selects the strongest applicable write strategy without protocol-specific
dispatch. A base provider must honor overwrite:false as far as its protocol
allows, report stream finalization failures, and not claim guarantees it lacks
(see IDD-0010).

The two assembly identities remain stable within the binary-compatible v2 SDK
line; NuGet package versions advance independently from application releases.
A pinned initial v2.0.0 binary baseline is checked in CI for both assemblies
using an API-compatibility tool, including method parameter names. Any
intentionally incompatible change requires an explicit reviewed major API
migration, not silently replacing the baseline. SDK and template packages are
distributed as release assets; publication to NuGet.org requires deliberate
maintainer action. A versioned `dotnet new` template generates an independently
buildable extension and deployable manifest. The release workflow validates
independent extensions against the exact packaged single-file executable.

Manually installed extensions remain installed when the application package is updated.
Bundled extensions are application-owned and replaced with the application package;
settings and enablement state remain user-owned in both cases. Official distributions
include selected, independently built SDK-compatible extension packages (initially
Azure Blob Storage). Release packaging stages complete checksum-verified packages
without host project references or shared contract DLL copies, and verifies loading
from the final distribution on each supported architecture. The macOS app, CLI
archives, Homebrew Formula and Debian package keep the real executable and
bundled-extensions together; the updater need not install plugins separately.
No startup download or write into the user extension directory is required.

Extension code runs in process with full user privileges; neither the plugin host
services nor load contexts isolate untrusted code. Only trusted extensions are
installed or bundled.

Debug solution builds may stage repository-owned external packages beside the
host in a dedicated development-extensions directory. Across roots, manually
installed packages take precedence over Debug packages, which take precedence over
bundled packages; a matching folder name or manifest ID (case-insensitive) shadows
a lower-priority package. Duplicates within one root retain normal registration
validation. A bundled folder uses its manifest ID, and the existing folder-based
disable state is preserved across application updates. User overrides are never
overwritten by application updates; removing the override exposes the bundled copy.

## Managing installed external extensions

The Options > Plugins dialog lists discovered external extensions, including bundled packages (not
first-party built-in modules), including each directory containing `plugin.json`
even when the manifest is unreadable. The list shows folder name, manifest ID
when known, display name, version, effective startup state (`Loaded`,
`Disabled` or `Error`) and a concise failure reason. Details show the
installation path, error stage (`manifest`, `load`, `construction` or
`initialization`) and any pending change. Displaying metadata must never
execute extension code. Initialization errors remain isolated per extension and
enter the existing sanitized diagnostics pipeline.

Users enable or disable an extension by its **installation folder name**,
not the manifest ID. Case-insensitive disabled folder names persist in
`<config>/extensions-state.json` as `{"disabled":["folder-name"]}`.
Newly installed extensions are enabled unless their folder is on this list.
A persisted global enabled boolean (default true for legacy files) gates all
external DLL loading without modifying individual disabled choices. The dialog
provides a global switch, shows current session versus next startup, and requires
a restart. Built-in modules are not affected.
Entries for temporarily missing folders are preserved. State changes are
atomically saved, with an explicit error on failed writes; the UI must not
claim success unless persistence succeeds. Disabling retains all binaries,
settings and user data. Enabled/disabled changes take effect at the **next**
application launch; a loaded plugin remains registered for the current session,
and the dialog clearly distinguishes this pending configuration from the
actual current-session state. The manager is only a view of installed packages,
not an additional runtime command registry.

`--no-extensions` starts a normal session without loading or constructing
any external extension, regardless of its source or saved state. It neither modifies
the disabled list nor affects built-in modules. The Plugins dialog remains
available so the user can persistently disable a problematic package before a
normal restart. Demo mode already omits external extensions.

## File-open handlers

A plugin registers one or more `IFileOpenHandler` objects through the same
`IPluginHost` initialization batch. Each handler has a unique ID within its
plugin, a synchronous lightweight `CanOpen(FilePanelItem)` check, and an
asynchronous `OpenAsync(FileOpenContext, CancellationToken)` function.
The context contains the originating panel location, source object, selected
item, target side, and the plugin's application/settings/UI/credentials.

Claims are evaluated in registration order. Zero claims use the existing
system launcher or built-in viewer. Multiple claims open a terminal-thread
selection menu identifying each handler by plugin name, plugin ID and handler ID.
The user may select one matching handler, explicitly choose the normal
system launcher/viewer, or press Escape to cancel without opening anything.
No plugin silently wins by registration order and no matching handler is
invoked until selection is complete. Errors during selection fail closed without
falling through to the system launcher.
A selected handler returns one of `NotHandled`, `OpenPanel`,
`Cancelled`, or `Failed`. Failure and cancellation never trigger an
unintended fallback launcher. Completion of asynchronous opening is dispatched
through the existing plugin UI queue, with no blocking wait in the Enter route.
Only a successfully loaded source changes the active panel. Its navigation
return point owns a source usage lease until exit or explicit panel replacement.

A file-open handler is an in-process registration, not dynamic DLL discovery,
and no handler for a particular archive format is built into the core.

## Invocation and results

A command receives a snapshot of the requested panel side, invocation origin
(`Plugins` menu, disk menu, or command line), cancellation token, application
context, host-bound settings, UI and credential facades, and (for command-line
invocations only) the raw input and unmodified argument substring.

The side is the active side when a Plugins menu/command-line entry is invoked,
or the explicitly requested side for `Alt+F1`/`Alt+F2`. Later changes to
active UI state do not change an in-progress invocation.

The runtime converts command exceptions and cancellation to distinct outcomes:
completed, open panel, cancelled, or failed. Known prefixes are considered
handled even if their command fails or is cancelled; they never fall through to
the external shell. `ShellInvocationParser` retains its precedence before
plugin prefix matching. Prefix scanning stops at the first colon or whitespace
and does not perform shell-like tokenization.

The application command interface remains synchronous, but unfinished plugin
`ValueTask` results are awaited asynchronously and their completion is queued
back to the application input/UI loop. Terminal modal operations must run on
the UI thread. The application does not synchronously block the UI on
unfinished plugin operations. The running application owns outstanding
asynchronous commands and file-open operations, supplies a session cancellation
token, and requests cancellation at shutdown. It waits for a bounded grace
period rather than hanging forever on a non-cooperative in-process plugin.
Completions after shutdown must not change panels or open UI; newly returned
unused panel sources are disposed. Queued completions are drained in discard
mode after the input loop ends, and an exception in one queued action must not
prevent the remaining actions from being processed.

## Built-in plugins and legacy behavior

The composition order is SFTP, FTP/FTPS, Processes and Ports, Network Traffic,
then Archives, followed by externally supplied plugins.

- SFTP registers `SFTP...` in Plugins, `SFTP` in both disk menus, the `sftp`
  prefix, and a connection-panel provider.
- FTP/FTPS registers `FTP/FTPS...` in Plugins, `FTP/FTPS` in both disk menus,
  `ftp` and `ftps` prefixes, and a connection-panel provider.
- Processes and Ports registers `Processes and Ports...` and `ports` with
  optional text after the first colon or whitespace. It is a dialog, not a
  file-panel provider.

- Network Traffic registers `Network Traffic...` and `traffic`, opening the
  live modal consumer ranking owned by IDD-0086. Demo uses sample traffic.

FTP/FTPS and SFTP prefix commands continue to open the saved connection
manager; they do not parse an optional path/URL as a connection target.
The disk-menu entries also open the connection manager, rather than
enumerating saved connections. Existing protocol engines, terminal dialogs,
storage files and credentials remain unchanged by the plugin refactor.

The first-party network modules continue using their narrowly scoped legacy
dialog/startup collaborators to preserve credential keys and stored
connection formats. Those collaborators do not register menus or commands.
Newly composed plugins receive standard plugin host services.

The existing module GUIDs remain stable:

- FTP: `e56632fd-6aa0-4e5b-a43c-0d48ba2ea7bd`
- SFTP: `2c5a3c9b-5b79-4986-8569-f06a1fb57c31`

Their saved connection files remain at
`<config>/plugins/<module-guid>/ftp-connections.json` (FTP) and
`<config>/plugins/<module-guid>/connections.json` (SFTP). The existing
`CredentialId` is used literally, including unprefixed SFTP credential IDs;
there is no migration and passwords are not embedded in JSON.

## Panel integration and lifecycle

Opening a plugin panel supplies an `IFilePanelSource`, its existing
`PanelSourceId`, start directory, title, and any format/shortcut/free-space/
key-bar metadata. The application retains `PanelController`,
`PanelLocation` and `FilePanelSourceRegistry` as the execution path.

Remote source identity remains
`plugin:{module-guid:D}:{connectionId}`, not `ftp:{connectionId}` or a
random opening-session ID.

The source is registered and the initial location is loaded before changing
the displayed title, quick view or active side. Load failure preserves the
previous panel, rolls back a newly registered source and disposes unused
owned sources. Unexpected exceptions from non-local source methods used during
directory view building (path normalization, enumeration, parent lookup and
capabilities) are surfaced as provider load errors, not unhandled UI failures.
Unrelated errors in core panel logic must not be swallowed. Rejected newly created sources are disposed exactly once; if
cleanup is asynchronous, it proceeds without blocking the terminal input loop.
Cleanup failures are observed and reported to diagnostics without replacing
the original open failure, and pending cleanup is completed during application
shutdown. Existing compatible registered sources are never disposed as part of
rejected-source cleanup. A duplicate source ID never silently replaces a live source.
An existing source may be reused only when it explicitly reports compatible
connection settings. Saved plugin sources remain registered during the application session and
are disposed at shutdown. Temporary connection sources remain registered
while referenced by either panel or by an active operation; after the last
reference and operation are gone they are unregistered and disposed.
Common local/demo sources are not treated as plugin-owned.

## Settings, credentials and demo mode

Settings access is bound to a plugin ID; a plugin cannot use the ordinary
settings facade to request another plugin's folder. New plugin credential
identifiers are namespaced by plugin owner. This is a programming/API boundary,
not a security sandbox for arbitrary in-process .NET code.

`IPluginApplicationContext.RunMode` exposes Normal or Demo in initialization,
commands and panel providers. In demo mode the host provides a separate
temporary plugin settings area and denies access to real credentials. FTP and
SFTP are not composed in the built-in demo session. Processes and Ports uses
the deterministic demo platform service and must not terminate real processes.
Plugin authors must not perform real destructive local/network operations in
demo mode. In-process arbitrary code could bypass these APIs; the host does
not claim isolation from untrusted plugins.

Simple messages, input and menus are available via `IPluginUiService`.
Plugins may additionally request a confirmation, a message with explicit choice
buttons, and a read-only multi-line help dialog. These operations use the
existing terminal-owned modal lifecycle and cannot be invoked from background
threads. Default interface implementations preserve compatibility with existing
hosts that implement only messages, input and menus. First-party complex
dialogs continue using the existing modal UI lifecycle.

## Non-goals

No automatic downloads, NuGet-based plugin installation, marketplace, hot reload,
permission model, sandbox, out-of-process plugins, event bus, editor/viewer
extensions, scripting system, FarNet compatibility, or protocol rewrite.

## Verification

Automated integration tests should load independently built plugin DLLs, including
in published self-contained/single-file hosts on Windows, Linux and macOS.
They verify independent private dependencies, error isolation and lifecycle.
Other integration tests should demonstrate an independent plugin registering
commands, both menu placements, a prefix and a virtual panel using only neutral
contracts. Other tests protect atomic registration, collisions, cancellation,
incomplete asynchronous commands, immutable target side, demo service isolation,
source identity, compatibility and ownership, and existing first-party
connection and process behavior.

SDK 2 deliberately breaks the v1 mutable string selection and duplicate operation-request contracts. Existing extensions must be rebuilt against SDK 2 and declare manifest API version 2. The host rejects old manifests explicitly.

### Semantic external plugin forms

SDK 2.1 supports multi-field modal forms through the public plugin UI service without exposing internal renderer types. The host owns layout, palette, keyboard and mouse handling, scrolling, focus, and modal lifetime. Plugins declare labeled text (including masked input), checkbox and dropdown controls, labels, separators, footer and inline auxiliary buttons. Stable row and action identities support synchronous callbacks, conditional visibility and enablement, validation with focus, and inline status. Escape or Cancel returns no accepted action; plugins must not persist draft values on cancellation. Masked inputs have no host history; all plugin form text inputs are history-free by default. Modal calls and callbacks remain terminal-thread-only; external cancellation propagates. Existing SDK 2.0 extensions remain compatible; manifest API and assembly identity remain 2.
