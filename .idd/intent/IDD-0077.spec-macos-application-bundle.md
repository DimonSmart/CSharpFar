# IDD-0077 - macOS application bundle specification

## Intent

CSharpFar provides a standalone macOS application launched from Applications,
Finder, Dock, Spotlight, or Launchpad. Its window, Dock entry, application menu,
and application-switcher entry belong to CSharpFar and use its product identity.
The existing terminal UI runs inside the application's own terminal host.

The portable self-contained CLI remains independently supported. The macOS
application does not duplicate the shared file-manager UI or business logic.

## Behavior

### Application identity and launch

The bundle identifier is `com.dimonsmart.csharpfar`; the application name is
`CSharpFar`. The icon derives from the shared original CSharpFar artwork.
Finder, Dock, and Cmd+Tab consistently identify the running application as
CSharpFar. Activating its Dock or Cmd+Tab entry focuses its own window.
Pinning the application in Dock and reopening it after exit preserve that
identity and launch the same application.

A desktop launch creates a CSharpFar-owned terminal window and starts the
shared file manager in the user's home directory. It requires neither Kitty,
Terminal.app, another external terminal application, nor a separate .NET
runtime. It does not modify other terminals, their icons, settings, or
registration. An already-running Kitty session remains independent.

The native desktop host marks its bundled CLI PTY process using the internal
`CSHARPFAR_FINDER_LAUNCH=1` environment hint. Under `shell.macOsPathMode=auto`
this enables one-time login-shell PATH discovery (IDD-0017). Direct CLI/TTY
launches do not receive the hint. This marker is not a security boundary.

A normal reopen activates an existing CSharpFar window when available instead
of creating a duplicate session. An explicit new-instance launch remains
available for the update/relaunch workflow in IDD-0082.

The bundled terminal executable remains directly runnable from an existing
terminal. Attached-TTY execution and CLI diagnostics, including `--version`,
`--check-system-git`, `--check-terminal`, and the input laboratory, preserve
existing contracts and do not unexpectedly open a GUI window. Invoking the
bundle executable with `--version` or `--check-system-git` also works without
creating a window. Interactive desktop launches with supported application
arguments pass them intact to the shared application.

### Terminal behavior and shared UI

The embedded terminal provides a real interactive terminal session to the
shared executable and its current-console children. It supports ANSI/VT output,
main and alternate screens, terminal queries, cursor visibility and shape,
colors, Unicode text, resizing, and scrollback needed by the existing UI and
command workspace. Input and output retain ordering and are not dropped during
normal sustained command output.

Panels, editor, viewer, dialogs, themes, application shortcuts, settings, and
file operations retain shared product behavior. Resizing, maximizing,
fullscreen transitions, and moving between displays with different pixel
densities preserve a legible cell grid and usable UI.

The host preserves keyboard identity, text input, key repeat, modifier state,
and focus transitions. Enhanced keyboard reporting is negotiated according to
IDD-0064. The desktop host supports its full keyboard lifecycle profile,
including standalone Shift/Alt/Control changes, without requiring the Kitty
application. Unsupported protocol modes are not falsely acknowledged. Focus
loss clears held modifiers, preventing stuck function-key bars or commands.

Mouse buttons, double-click, wheel, pointer motion, and dragging preserve
application behavior. Main-screen text selection and system clipboard copy
work when application mouse reporting is disabled. Cmd+C copies a terminal
selection; without a selection it does not synthesize Ctrl+C. Cmd+V pastes text
once through the terminal's supported paste handling. Ctrl+C remains the
terminal interrupt/application shortcut. Unicode input, including composed
text and IME commit, is delivered without duplication or corruption.

Current-console commands and executable panel items run in the same embedded
terminal, with proper controlling-terminal and foreground-process behavior.
Interactive commands can read input; Ctrl+C interrupts the foreground command
without terminating CSharpFar. On child exit, the file manager restores its
input mode and appropriate workspace as defined by IDD-0017 and IDD-0028.
Associated documents still open through macOS associations.

### Session lifetime and failures

Normal file-manager exit closes its desktop session and releases terminal and
process resources. Window close and Cmd+Q use the normal application shutdown
flow, respecting existing unsaved-work and active-operation decisions. A
running foreground command requires an explicit terminate-or-cancel choice
before desktop shutdown. Cancellation leaves the session usable. Confirmed
shutdown terminates session-owned processes and leaves no orphaned terminal
host or foreground command; intentionally detached associated applications
remain independent.

Startup failures are visible in the CSharpFar desktop host with a useful error
and a way to close it. Unexpected core-process exit is distinguishable from
normal exit and reports the failure before closure. Host failure releases its
terminal session. Failure never silently falls back to an external terminal
or opens duplicate file-manager sessions. Diagnostics follow IDD-0081 and do
not record terminal keystrokes or full terminal contents by default.

### Compatibility and settings

Desktop startup no longer selects an external terminal provider. Existing
`application.preferredMacOsTerminal` values (`auto`, `kitty`, `terminal`) are
accepted for configuration compatibility but do not affect desktop startup.
The obsolete terminal-provider option is removed from the settings UI.
Migration preserves unrelated settings and user data. Portable CLI behavior
continues to depend on its actual attached terminal, as defined by IDD-0064.

## Distribution and release integration

Architecture-specific releases remain available for Apple Silicon and Intel:

- `CSharpFar-v<version>-osx-arm64-app.zip`;
- `CSharpFar-v<version>-osx-x64-app.zip`.

Each archive contains a conventional `CSharpFar.app` bundle with valid
`Contents/Info.plist`, desktop host under `Contents/MacOS`, application icon,
and self-contained `Contents/Resources/csharpfar` terminal executable. That
executable remains byte-for-byte identical to its corresponding portable CLI
release. Embedded-host dependencies are bundled and architecture-compatible;
first launch requires no additional component download.

`CFBundleShortVersionString` and `CFBundleVersion` match the release version.
App assets remain covered by `SHA256SUMS.txt` and GitHub artifact attestations.
The existing Homebrew Cask, Formula coexistence, installer, and guarded
self-update contracts remain supported under IDD-0076 and IDD-0082.
Post-update relaunch opens the standalone host, not an external terminal.

Application bundles are assembled on macOS. Signing and notarization remain
separate distribution-hardening work. Development builds do not require
signing credentials. While bundles remain unsigned and not notarized, existing
Gatekeeper guidance and the scoped quarantine workaround in IDD-0082 apply.

## Non-goals

- Replacing panels, editor, viewer, or other shared TUI with native widgets.
- Building a general-purpose terminal with tabs, profiles, or SSH UI.
- Changing Windows/Linux behavior or removing portable macOS CLI releases.
- Changing the shared icon artwork as part of the host migration.
- Renaming or patching an installed third-party terminal to impersonate CSharpFar.
- Requiring signing/notarization or a particular terminal-engine library here.

## Acceptance criteria

1. On both supported architectures, desktop launch works without Kitty or
   another external terminal and presents CSharpFar in Finder, Dock, Cmd+Tab,
   and the application menu. Activation and pinned-icon reopening work.
2. A running Kitty instance, its settings, and its icon remain unaffected.
3. Panels, dialogs, editor, viewer, mouse interaction, resizing, Unicode/IME,
   clipboard, and full modifier lifecycle work inside the owned window.
4. Interactive current-console commands use that same terminal, respond to
   Ctrl+C, and return to a usable CSharpFar workspace after completion.
5. Window close, Cmd+Q, normal exit, cancellation, startup failure, and core
   failure follow the lifetime rules without silent fallback or orphan processes.
6. Desktop launches ignore old provider settings without losing user data;
   settings no longer offer an ineffective provider selection.
7. CLI/TTY launches and diagnostics remain available without creating windows.
8. Both app archives retain version, architecture, checksum, attestation,
   installation, and update compatibility, including standalone-host relaunch.

## Verification

Automated checks cover bundle identity/version/architecture and dependencies,
CLI binary parity, no-window diagnostics, argument integrity, meaningful
session lifecycle and failure boundaries, resize delivery, and interactive
foreground-process interruption/restoration. Use the smallest stable set of
tests that proves these contracts rather than tests for private host structure.

Manual acceptance on Apple Silicon and Intel covers:

- Launch from Finder, Spotlight, Dock, and Launchpad where available; pin,
  quit, reopen, activate through Cmd+Tab, reopen an existing session, and
  explicitly launch a second instance.
- Repeat startup with Kitty absent and with an independent Kitty session
  running; exercise all legacy provider-setting values.
- Navigate panels/dialogs, edit/save Unicode text, use IME and clipboard,
  hold/release modifiers, switch focus while holding a modifier, use mouse
  drag/wheel, resize, fullscreen, and move between display scales.
- Run substantial command output and an interactive full-screen child,
  interrupt a long-running child using Ctrl+C, then verify panels and Ctrl+O
  history/selection and normal input restoration.
- Exercise unsaved editor state, an active operation, a foreground child,
  shutdown cancellation, confirmed shutdown, startup failure, and unexpected
  core exit; verify session-owned processes are released.
- Run portable CLI and bundled CLI diagnostics in an external terminal.
- Install/update through Homebrew Cask, verify the version, and confirm About
  self-update relaunches the new standalone host successfully.

The current [manual macOS acceptance matrix](../../docs/macos-standalone-validation.md)
records scenarios requiring verification on physical macOS desktop sessions.
