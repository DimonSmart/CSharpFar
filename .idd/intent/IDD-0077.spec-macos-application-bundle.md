# IDD-0077 - macOS application bundle specification

## Intent

CSharpFar provides a normal macOS `CSharpFar.app` application bundle for users
who expect to install and launch the program from Applications, Finder,
Spotlight, or Launchpad, without converting the terminal UI into a native GUI.

The application bundle is an additional distribution shape over the existing
self-contained macOS executable. The portable CLI archives remain supported.

## Behavior

A release publishes architecture-specific application archives for both
supported macOS architectures:

- `CSharpFar-v<version>-osx-arm64-app.zip` for Apple Silicon;
- `CSharpFar-v<version>-osx-x64-app.zip` for Intel.

Each archive contains `CSharpFar.app` with a conventional macOS bundle layout:

- `Contents/Info.plist` contains the bundle identity and release version;
- `Contents/MacOS/CSharpFar` is the bundle launcher;
- `Contents/Resources/csharpfar` is the same self-contained terminal executable
  produced for the corresponding CLI release;
- `Contents/Resources/CSharpFar.icns` is the application icon;
- `Contents/Resources/launch.command` is the Terminal.app entry point used as
  the explicitly selected provider or the fallback.

The bundle identifier is `com.dimonsmart.csharpfar`.

CSharpFar remains a terminal application. When the bundle launcher has both
stdin and stdout attached to a terminal **or receives any explicit arguments**,
it executes the bundled `csharpfar` binary directly. When launched without
arguments or a terminal (Finder, Dock, Spotlight, Launchpad, or the Homebrew
relaunch path), the shell wrapper calls the bundled host with the exact
internal argument `--launch-from-finder`. This early host mode runs before
terminal-driver creation and opens the user's preferred terminal.

The selection is stored in the existing `application.preferredMacOsTerminal`
value of `settings.json`. It is edited under **Options → Settings →
Application**, and takes effect on the **next** no-TTY app-bundle launch:

- `auto` (default): choose Kitty when a verified application bundle is
  installed; otherwise use Terminal.app.
- `kitty`: prefer Kitty, with Terminal.app fallback if unavailable.
- `terminal`: always use Terminal.app.

Kitty discovery checks `/Applications/kitty.app` followed by
`~/Applications/kitty.app`, requires the bundle identifier
`net.kovidgoyal.kitty`, and checks executable permissions. The host starts
`Contents/MacOS/kitty` directly with separate `--directory`,
`--session none`, and CSharpFar executable arguments. Custom Launch Services
registration outside the two standard paths is not discovered. Terminal.app
uses `/usr/bin/open -a Terminal Contents/Resources/launch.command` with
separate process arguments. No shell interpretation of user paths occurs.

If Kitty is absent, invalid, or synchronously rejected, one Terminal.app
fallback is permitted. Once a Kitty launch request is accepted, the launcher
does not start another terminal merely because the first window has not
appeared: it cannot confirm a GUI session without IPC. A failed Terminal.app
request returns an error. The preference is never overwritten by fallback.

The internal argument is invalid in an attached interactive terminal and
outside the expected app bundle. It is not forwarded to the CSharpFar process
started inside the selected terminal. A direct CLI or TTY launch stays in its
original terminal regardless of preference.

A Finder launch starts CSharpFar in the user's home directory. The application
does not introduce a separate GUI shell merely to obtain a Finder icon.

The macOS icon is derived from the existing original CSharpFar icon asset so
Windows and macOS retain the same product identity. Packaging may convert the
repository icon into the `.icns` sizes required by macOS.

The application bundle is assembled on macOS because the packaging step uses
macOS bundle/icon tooling. This does not require the managed application itself
to be compiled on macOS: future release-pipeline optimization may cross-publish
the `osx-*` executable on another OS and reserve macOS runners for bundle
assembly, terminal verification, signing, or notarization.

## Release integration

The Release workflow creates the app archive from the already published
architecture-specific macOS executable and publishes it alongside the existing
CLI archive.

Each app archive has a SHA-256 entry in `SHA256SUMS.txt` and receives the same
GitHub artifact attestation treatment as the portable release archive.

Release notes distinguish the Finder/Applications app archives from the
portable CLI archives.

## Signing and notarization

Application bundles are currently unsigned and not notarized. Direct/manual
installation may therefore require the normal macOS Gatekeeper **Open Anyway**
workflow.

The recommended Homebrew installer described by IDD-0082 temporarily removes
`com.apple.quarantine` only from `/Applications/CSharpFar.app` after Homebrew
has installed or upgraded the verified Cask. This workaround is not part of the
bundle format and must be removed once Developer ID signing and notarization are
available.

Code signing and Apple notarization are distribution-hardening work and may be
added later without changing the bundle/launcher contract in this specification.

## Non-goals

- Do not replace the terminal UI with AppKit, SwiftUI, Catalyst, or another GUI.
- Do not remove or weaken the portable `osx-arm64` and `osx-x64` CLI releases.
- Do not require a separately installed .NET runtime.
- Do not duplicate the CSharpFar application implementation inside a macOS-only
  UI project.
- Do not make signing credentials a prerequisite for producing development or
  experimental app bundles.

## Acceptance criteria

- Releases contain `CSharpFar.app` ZIP archives for Apple Silicon and Intel.
- The bundle contains a valid `Info.plist`, application icon, executable
  launcher, terminal launcher, and self-contained `csharpfar` binary.
- `CFBundleShortVersionString` and `CFBundleVersion` match the release version.
- The bundle launcher can execute `--version` directly for automated checks.
- Finder launches honor the `auto` / `kitty` / `terminal` preference, with
  Terminal.app fallback, without running terminal UI without a TTY.
- A Kitty-start acceptance is not treated as proof of the CSharpFar UI being ready.
- Existing CLI arguments and interactive TTY sessions never launch a new terminal.
- App archives are included in release checksums and attestations.
- Existing portable macOS CLI assets continue to be published.

## Verification

Automated release verification:

1. Validate `Info.plist` with `plutil`.
2. Verify the bundle launcher executes the bundled binary and reports the
   expected release version.
3. Verify both app ZIP assets are generated and checksummed.

Manual macOS verification:

1. Unpack the architecture-matching ZIP.
2. Move `CSharpFar.app` to Applications.
3. Open it from Finder and verify the **selected** terminal opens with a
   working CSharpFar TUI. Test both Kitty and Terminal.app preferences.
4. Confirm the application icon is visible in Finder/Applications.
5. Confirm the portable `csharpfar` CLI archive still runs independently.
6. From Terminal.app (or another real terminal emulator), run:
   `/Applications/CSharpFar.app/Contents/Resources/csharpfar --check-terminal`.
7. Run:
   `/Applications/CSharpFar.app/Contents/Resources/csharpfar --check-terminal --input-lab`
   and confirm the shared terminal input laboratory starts on macOS and reads
   the real TTY rather than a Finder/GUI event source.

For the complete manual macOS desktop acceptance matrix, see
[macOS preferred terminal validation](../../docs/macos-terminal-preference-validation.md).
