# IDD-0001 - CSharpFar file manager specification

Related (authoritative product-area contracts):
- IDD-0003 / IDD-0007 (display, settings and panel options)
- IDD-0013 (function-key bar and command bindings)
- IDD-0017 / IDD-0018 / IDD-0022 / IDD-0028 (external shell, command history, scrollback and workspace modes)
- IDD-0032 / IDD-0046 (viewer and editor)
- IDD-0038 (text input and histories)
- IDD-0061 / IDD-0062 / IDD-0067 (plugins, reusable console UI and composition)
- IDD-0065 (Debian/Ubuntu distribution and APT)
- IDD-0076 / IDD-0077 / IDD-0082 (Homebrew, macOS app bundle, installer and update)
- IDD-0083 (F2 user menu)

## Context

CSharpFar is a console two-panel file manager written in C# for .NET 10. Its
primary user model follows Far Manager: two file panels, a command line,
function-key actions, command and directory history, file operations, a viewer,
and an editor.

The product supports separate Windows, Linux, and macOS executable hosts over a
shared application layer. The implementation must keep direct control over
console input, rendering, shell command execution, and the screen buffer so that
Far-like dual-panel and command-output scenarios remain possible.

## Scope / Behavior

- The application provides left and right file panels with independent current
  directories, cursor positions, selections, sorting, and scrolling.
- A readable local directory remains navigable when individual child entries
  cannot be inspected. Such entries are omitted without changing filtering,
  sorting, parent-directory, summary, or rendering behavior.
- Keyboard operation is primary. Mouse input may enhance behavior but must not
  be required for core workflows.
- The command line executes shell commands in the active panel's directory;
  `IDD-0017` owns execution, `IDD-0018` owns command-history completion,
  and `IDD-0038` owns shared text-field history behavior.
  Output remains available through the terminal's shell-output workspace under
  `IDD-0022`, rather than being treated as part of the panel-rendering buffer.
- The two-panel and hidden-command-line workspace contract, including `Ctrl+O`,
  is owned by `IDD-0028`; shell scrollback is owned by `IDD-0022`.
- The function-key bar and command availability are owned by `IDD-0013`;
  application-independent console components by `IDD-0062` and UI layering
  and resize by `IDD-0067`.
- File viewing and editing are owned by `IDD-0032` and `IDD-0046`.
  Settings, panel options and field history are owned by `IDD-0003`,
  `IDD-0007` and `IDD-0038`; the F2 user menu is owned by `IDD-0083`.
- The application also supports `csharpfar --demo <root-path>` on Windows,
  Linux, and macOS hosts. Demo mode imports the specified readable directory once,
  builds a complete in-memory snapshot, and exposes it as one logical
  platform-independent file system rooted at `/`.
- After demo import succeeds, runtime panel navigation, viewer, editor, file
  operations, and other file access in that session use only the in-memory demo
  source. The physical fixture path is not shown in the UI and is not used
  again for runtime file operations.
- Demo mode is composed from isolated services rather than scattered mode
  checks. In demo mode the reachable source registry exposes only the demo
  source, shell command execution is disabled, launching files through external
  OS applications is disabled, built-in network modules are disabled, and
  session settings/history changes do not modify the user's normal
  configuration state.
- In demo mode the reachable source registry is the runtime allow-list for file
  system sources. A panel location or file-operation request targeting the local
  file system must be rejected before any local directory enumeration, file
  existence check, or physical file-system mutation when the local source is not
  registered.
- A rejected transition to an unregistered panel source is transactional: the
  panel keeps its previous source-qualified location, items, capabilities,
  cursor, selection, and transient navigation state instead of entering the
  panel-load error surface for that rejected target.
- Local-only commands and services treat `SourceId.Local` as necessary but not
  sufficient authority for physical file-system I/O. Physical local I/O is
  allowed only when the panel state is local and the runtime source registry
  still registers the local source.
- Demo startup determines run mode before creating or validating persistent user
  settings. A demo session uses an isolated ephemeral configuration directory,
  does not create or modify the normal user `settings.json`, and does not read
  or write the user's normal credential store.
- Demo mode is also the safe source of truth for reproducible documentation
  recordings. Repository-owned fixture files can drive an automated
  product-owned demo recorder without giving the recording session access to
  the physical fixture as live mutable state.
- Automated README demo generation uses the application's own rendering and
  input model instead of an external terminal-video DSL. The supported
  recording path is a deterministic scripted runner over a fake or recording
  console driver that can feed application input, capture committed screen
  frames, and export visual artifacts such as screenshots, GIFs, or videos.
- Supported product-owned demo scenarios are not limited to static panel
  navigation. The demo-recording flow must be able to drive representative
  modal and document workflows over committed frames, including file viewing,
  file editing, create-folder and create-file dialogs, copy and move dialogs,
  rename flows, delete flows, and the visible delete confirmation surface.
- The documentation recording path is intentionally product-owned rather than
  browser-hosted. External recorder stacks such as VHS, browser automation,
  or web terminal bridges are not part of the supported demo-generation design
  because they add non-product dependencies, hide failures behind external
  rendering behavior, and reduce deterministic reproduction across machines and
  CI environments.
- The fake or recording console driver is also an approved source for visual
  regression artifacts. The product may capture real rendered screenshots from
  committed screen frames for documentation or future test evidence without
  changing the observable application behavior.
- Demo-recording scenarios should prefer visible workflow surfaces over hidden
  internal shortcuts when the documentation goal is to show the product's
  actual dialogs, confirmations, and editor or viewer interactions.
- The solution is layered so that UI orchestration, console access, file-system
  models, shell execution, file operations, viewer behavior, editor behavior,
  settings, and histories are not concentrated in a single entry-point file.
- Platform selection happens in explicit host/platform composition roots. The
  application layer owns shared application bootstrap, commands, settings,
  histories, menus, and application services, but does not directly choose
  Windows, Linux, or macOS implementations for console access, shell execution, file
  launching, credentials, volumes, mount points, or terminal screen mode.
- Windows, Linux, and macOS hosts are separate executable projects that reference
  the shared application layer and their corresponding platform service implementations.
- ANSI/VT rendering and parsing remain shared across Linux and macOS, while
  terminal-native ABI, external file opening, shell defaults, volume discovery,
  mount-point recognition, and file metadata ownership are owned by their
  respective platform compositions.
- Linux portable/Debian packaging and the signed APT repository are owned by
  `IDD-0065`. macOS release packaging and Homebrew distribution are owned
  by `IDD-0076` and `IDD-0077`; guided installation and updates by
  `IDD-0082`. This overview does not define their package metadata, signing
  policy, installation steps or update workflows.
- CSharpFar uses its own shared rendering and component stack, with reusable
  boundaries owned by `IDD-0062` and committed composition behavior by
  `IDD-0067`.
- Native plugin lifecycle, command/menu registration and panel API requirements
  are owned by `IDD-0061`.

## Non-goals

- Full Far Manager macro compatibility is outside the current scope.
- Archive panels are outside the current scope.
- A full hex editor is outside the current scope.
- A full IDE-like code editor is outside the current scope.
- Exact compatibility with every Far Manager hotkey is outside the current
  scope unless another spec names the hotkey explicitly.
- Full Linux or macOS terminal parity is outside the current scope.
- Linux package architectures other than `amd64` and distribution formats
  other than the portable archive and Debian package are outside the current
  scope.

## Acceptance criteria

- The product launches through its Windows host and independently composed
  Linux/macOS hosts without constructing services belonging to another OS.
- A user can perform the core two-panel, shell, viewer, editor and settings
  workflows. Their detailed acceptance criteria live in the related owning
  specifications and are not repeated here.
- Opening a readable local directory succeeds and shows its accessible children
  even when another direct child is inaccessible.
- Windows releases include a portable Windows archive with its checksum and
  artifact attestation; this remains an integration-level release guarantee
  because the specialized distribution documents address Linux and macOS.
- Linux and macOS release artifacts and installation paths satisfy `IDD-0065`
  (Linux/APT), `IDD-0076` (Homebrew), `IDD-0077` (macOS bundle), and
  `IDD-0082` (installation/update). Their package-specific details are not
  duplicated in this overview.
- Running `csharpfar --demo` without a path, or with an unreadable or
  non-existent directory, fails before UI startup with a clear non-zero-exit CLI
  error.
- Running `csharpfar --demo <root-path>` opens both panels on the logical demo
  file system, never exposes the physical fixture path in panel UI, and keeps
  normal startup behavior unchanged when `--demo` is not supplied.
- A repository checkout can regenerate the README demo from source-controlled
  demo fixtures and a product-owned scripted recording runner, and all visible
  edits during that demo disappear when the demo session exits.
- The supported repository demo flow can render and record the core visible
  workflow surfaces for file management, including viewer, editor, copy, move,
  rename, create-folder or create-file, and delete confirmation dialogs,
  without requiring manual typing outside the scripted runner.
- A demo session cannot navigate to real local volumes, run external shell
  commands, launch files in external programs, or reach built-in network
  providers.
- In a demo-only session, no command or malformed panel location or file
  operation request can switch a panel or operation path back to the local file
  system.
- In a demo-only session, a rejected attempt to open a local panel location
  leaves the panel on the prior demo location without exposing the rejected
  local path as the current or retry location.
- After any demo session ends, a later normal startup sees no settings,
  histories, credentials, or file-system mutations caused by that demo session.

## Verification

- Verify the Windows release archive and its checksum/attestation at the
  product integration level. Verify Linux/APT distribution under `IDD-0065`,
  macOS bundles under `IDD-0077`, and Formula/Cask and guided installation
  under `IDD-0076` and `IDD-0082`; do not maintain a second packaging test
  inventory for those areas here.
- Start `csharpfar --demo` from a small fixture, verify both panels open on the
  logical demo root or configured demo startup locations, and confirm the
  source path is not visible in the normal UI surface.
- During one demo session, view, edit, create, rename, copy, move, and delete
  demo items; verify those changes are visible inside the demo source and the
  original physical fixture remains unchanged byte-for-byte.
- Run the repository demo-recording flow against Demo Mode and verify the
  recording runner uses only the imported in-memory fixture, captures committed
  application frames without depending on an external browser-hosted recorder,
  and leaves the physical fixture and normal user configuration unchanged after
  the session.
- Run a representative scripted demo-recording scenario that visibly opens the
  viewer, edits and saves a file in the editor, opens create, copy, move,
  rename, and delete dialog surfaces, and shows the delete confirmation UI;
  verify the committed recorded frames contain those visible surfaces and the
  underlying fixture remains unchanged after the session.
- Capture at least one rendered screenshot from the fake or recording console
  driver during a demo-recording run and verify it reflects the same committed
  UI frame that the user would see in the live application.
- In demo mode, attempt drive or volume switching, shell command execution,
  external file launching, and built-in network access, and verify each action
  is unavailable or fails with a clear demo-mode result without escaping to real
  user resources.
- Start one demo session after saving the normal user `settings.json` bytes and
  any normal credential-store bytes; change settings during the session; then
  verify the normal user files remain byte-for-byte unchanged after exit.
