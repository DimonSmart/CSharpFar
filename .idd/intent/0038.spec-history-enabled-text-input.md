# 0038 - History-enabled text input

Related:
- 0018
- 0020
- 0034

## Goal

Add optional command-history-style suggestions to reusable single-line text input controls, and document the current control ecosystem so new controls are not duplicated.

## Context

CSharpFar has many one-line input fields in dialogs and plugin dialogs. Fields with an explicit stable history key remember recent submitted values without duplicates: when the same value is submitted again, it becomes the most recent item.

The application already has command-line history completion and panel quick search overlays. This change should reuse the same rendering conventions: a compact framed list, single border, no padding, and the shared right-border scrollbar style.

## Scope

Implement reusable history support for single-line text input:

1. Keep `SingleLineTextInput` usable without history by default.
2. Application-scoped field history owns only persistent suggestion values,
   normalization, duplicate removal, the maximum item count, accepted-value
   addition, and persistence notification. It does not own popup visibility,
   filtered matches, selection, scrolling, scrollbar interaction, or geometry.
3. Store suggestion items without duplicates, ordered from most recent to oldest.
4. Adding an existing item moves it to the top.
5. Do not store empty or whitespace-only values.
6. Render a dropdown arrow as the rightmost input-field character when history is enabled and the field is wide enough.
7. Clicking or otherwise requesting the arrow opens the history dropdown.
8. Typing the first characters in a history-enabled field opens the dropdown when matching items exist.
9. Suggestions match by prefix against the current input text.
10. Use up to 10 content rows, reduced by available screen height. A visible dropdown begins with a transient empty neutral row, so this limit includes that row and at most nine real suggestions are shown at the maximum.
11. If there is not enough room for a single-border frame plus at least one item, do not open the dropdown.
12. Draw the dropdown as a single-border popup without padding and with the shared right-border scrollbar.
13. Keep keyboard handling predictable: every opened or rebuilt dropdown selects its transient empty neutral row first. Up does not move above it; Down moves to the first real suggestion. Enter on the neutral row closes the dropdown and confirms the current input unchanged, while Enter on a real suggestion accepts that suggestion and closes the dropdown. Escape closes the dropdown without changing text.
14. Keep field history in a dedicated `field-history.json` in the already selected application configuration directory, separate from command, directory, and file history.
15. Restore history automatically on a later application launch and save a changed field history after a successful addition.
16. Use one application-scoped history provider for application dialogs and
    built-in modules; fields with the same stable typed key share one isolated
    persistent value list. Production dialogs receive that provider from
    composition and do not create a fallback in-memory registry.
17. Persist only normalized items: non-empty values, ordinal duplicate removal, most-recent-first order, and at most 100 items per key.
18. Do not persist masked input or transient dropdown state.
19. Enable history only when the caller supplies an explicit stable `TextHistoryId`; keys are persistent identifiers and are not derived from visible text or runtime state. Existing persisted key values remain stable across this API change.
20. Keep the arrow visible for every history-enabled field. When the history is empty it is disabled, does not open a popup or publish an active popup target, and retains the current input background.
21. Application and module dialogs use the same application-scoped history provider. They do not create an in-memory provider or registry when no history is requested.
22. A supplied history identifier is valid only when it has a non-empty value. Application-specific identifier catalogs belong to their owning application or module assembly; the reusable UI assembly exposes only the typed identifier and reusable history abstractions.
23. A field without an explicit history identifier has no history object, does not query the provider, shows no history arrow, and does not retain submitted values. Masked fields follow the same behavior regardless of an identifier supplied by a caller.
24. Standard form dialogs create every ordinary single-line text field through the application-scoped `FormFieldFactory`, including fields without history. `TextHistoryId` is an explicit stable history-bucket identifier and is never inferred from visible text or runtime state. A `TextField` owns its buffer, optional history binding, masking, width, submit policy, and transient input state; consumers use its row projections and do not provide separate buffer or history-row state. Consumers accept history only after successful validation.
25. Connection forms bind each named text field to its own explicit stable identifier when the form is created. Password fields never have history, and accepted connection validation is required before any connection-field history is retained.
26. Field-history persistence failures remain non-fatal but are reported to the application's diagnostic sink; unreadable persisted history similarly falls back to an empty history while reporting the failure.
27. Each `TextField` instance owns its transient history-popup state. Two fields
    with the same stable history identifier see the same persistent values but
    independently filter, open, select, scroll, and close their dropdowns.
28. Completing or closing a dialog leaves no field-history overlay in
    application-scoped state. A newly created dialog starts with every history
    dropdown closed even when it reuses the same provider and identifier after
    submit, cancel, or programmatic completion.
29. Separating persistent and transient state does not change history-arrow
    availability, prefix filtering, the neutral first row, Enter and Escape
    semantics, dropdown scrolling, outside-click closing, mouse capture,
    maximum history size, most-recent-first order, persisted key values, or the
    `field-history.json` format.

Create a controls registry:

1. Add a repository document that lists current user-interface controls.
2. For each control, record purpose, owning type/file, important functions, supported interaction features, and known reuse points.
3. Include existing text input, command completion, quick search, list dialogs, button bar, popup/frame renderers, scrollbars, panels, menus, and progress/message dialogs.
4. Registered reusable controls support their basic mouse interaction by default unless a specific control documents why it cannot receive mouse input.
5. Form-dialog option rows, including copy mode and copy conflict options, can be selected with the mouse through the shared form-dialog control model.

## Non-goals

Do not implement now:

1. fuzzy, substring, or case-sensitive mode switches;
2. an external or general-purpose UI framework;
3. mouse dragging for the new dropdown scrollbar;
4. compatibility shims for older input APIs.

## Acceptance criteria

- Existing calls to `SingleLineTextInput.HandleKey` and `Render` keep working.
- History-enabled input can keep a duplicate-free recency list.
- Re-adding an existing history item moves it to the top.
- Empty and whitespace-only items are ignored.
- History-enabled rendering shows a down arrow at the right edge and reserves that character from text display.
- Typing a prefix opens the dropdown when matching history entries exist.
- The dropdown does not open when the screen cannot fit a frame and at least one item.
- The dropdown shows at most 10 content rows and shrinks to available height.
- Up and Down move dropdown selection without editing text.
- A dropdown begins with a transient empty neutral row that is selected by default and is never persisted as history.
- Enter on the neutral row keeps the input buffer unchanged and closes the dropdown; a dialog may submit that unchanged value when its row is configured to submit on Enter.
- Enter accepts a real suggestion only after it has been explicitly selected, and that acceptance does not submit a containing dialog with the same key press.
- Escape closes the dropdown without changing text.
- The dropdown uses a single border, no shadow, no padding, and the shared right-border scrollbar when scrollable.
- The numbered console UI component library spec describes current reusable
  controls and supported functions.
- The controls registry says reusable controls support mouse interaction by default unless a specific control documents an exception.
- Copy dialog conflict options can be selected with the mouse through the shared form-dialog control model.
- Field histories survive restart in `field-history.json` without changing `history.json`.
- Histories for distinct stable keys remain isolated; masked fields are never written.
- Application-scoped field history contains persistent values and persistence
  behavior only; popup state and geometry belong to an individual field.
- Fields with the same stable history identifier share persistent values but
  cannot open, close, select, filter, or scroll one another's dropdown.
- Closing a dialog removes its transient history overlays, and reopening a
  dialog with the same provider and identifier starts with the dropdown closed.
- Ordinary form consumers can create a text field through the high-level field factory without constructing command-line state or row state. History is explicitly accepted only after successful form validation.
- `FormFieldFactory` is the sole production API for ordinary single-line form fields. Low-level text-row constructors are UI-infrastructure-only, and module-facing UI services expose the factory rather than the history provider.
- An empty history arrow uses the disabled-control foreground with the ordinary or focused input background, cannot open a dropdown, and does not create an active popup target.
- A field without a history identifier, including a masked field, never queries or changes field history; it has no history arrow.
- Invalid default identifiers are rejected, while existing persisted identifier values remain stable.
- Standard dialogs and connection forms retain history only after accepted validation; each connection field retains only its own history and never retains passwords.
- Persistence read and write failures are observable through diagnostics without interrupting the dialog or application.

## Verification

Manual checks:

1. Render a history-enabled input in a small console and verify the arrow and dropdown clipping behavior.
2. Open the dropdown with a prefix and verify duplicate-free recency order.
3. Navigate suggestions with Up/Down, verify Enter on the initial neutral row preserves and confirms the typed value, then explicitly select and accept a real suggestion; close with Escape.
4. Select a copy dialog copy-mode option such as `Reliable` with the mouse.
5. Submit a history-enabled dialog field, restart with the same configuration directory, and verify that its dropdown contains the submitted value.
6. Verify that a masked field and an invalid or cancelled submission do not change the field-history document.
7. Submit a standard dialog and a connection dialog successfully, then reopen them to confirm each named non-secret field has its own persisted suggestions.
8. Simulate a persistence read or write failure and confirm that the application remains usable and diagnostics receive the failure.

Focused automated checks cover two simultaneous fields with one identifier:
they observe the same persistent items while their filtered matches, open state,
selection, scroll position, and scrollbar interaction remain independent.
Dialog-lifecycle checks open a dropdown, complete through submit, cancel, and
programmatic completion, then recreate the dialog with the same provider and
identifier and verify that no overlay survives while accepted persistent values
remain available.
