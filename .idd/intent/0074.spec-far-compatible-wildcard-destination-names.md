# IDD-0074 - FAR-compatible wildcard destination names

Related:
- `0010.spec-file-operations.md`
- `0060.spec-file-rename-operation.md`
- `0075.spec-destination-templates.md`

## Goal

Copy, move, and rename support FAR-compatible wildcard transformation in the
final component of the entered destination.

## Behavior

- A destination whose final name component contains `*` or `?` is a name
  transformation pattern. Wildcards in a parent path component are rejected.
- The transformation follows FAR Manager `ConvertWildcards` behavior. `*`,
  `?`, dots, and literal characters have FAR semantics; bracket expressions and
  other file-mask constructs remain literal text.
- Destination transformation is independent from `FileMask`: the latter selects
  source files, while the former computes a target name for each selected root
  item.
- F5 copy and F6 move transform each selected root file or directory before
  execution. A directory transformation affects its root destination name only,
  not descendants.
- Shift+F6 and single-source F6 rename accept a wildcard name pattern without a
  directory and retain the item in its current parent directory.
- The complete source-to-final-target plan is formed and validated before any
  operation mutation. Validation includes invalid final names, self-targets,
  directory descendants, provider path rules, and collisions between operation
  sources.
- Multiple sources resolving to the same final target reject the operation
  before mutation. Conflicts with an already existing final target use the
  established operation conflict behavior.
- The same behavior applies through writable provider file-operation workflows.
- Destinations without `*` or `?` retain the existing file-operation behavior.

## Non-goals

- A batch-renaming UI, destination previews, regular expressions, capture
  groups, counters, template syntax, or a new source mask language. Explicit
  destination templates, including destination-directory computation, are a
  separate capability governed by `0075` and are not FAR wildcard syntax.

## Acceptance criteria

1. Copy, move, and rename accept final-component wildcard destination patterns.
2. Transformed names are FAR-compatible and source file-mask matching is not
   repurposed for the transformation.
3. Files and selected root directories receive transformed names without
   recursively renaming their contents.
4. Invalid, self-referential, descendant, and intra-operation-collision targets
   fail before mutation.
5. Existing final-target conflicts retain established conflict handling.
6. Local and writable-provider operations support the behavior, and ordinary
   destinations remain unchanged.

## Verification

- Representative FAR `ConvertWildcards` cases cover dots, literals, stars,
  question marks, and unusual literal bracket content.
- Copy, multi-item move, single-item rename, root-directory copy, collision,
  conflict, and writable-provider scenarios demonstrate the operation contract.
