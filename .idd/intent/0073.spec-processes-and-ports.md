# IDD-0073 - Processes and Ports specification

## Goal

CSharpFar provides a first-party **Processes and Ports** module for diagnosing
local TCP and UDP endpoints and safely identifying or terminating the process
that blocks a required local port on Windows and macOS. Linux endpoint
collection remains unsupported.

## Behavior

The Plugins menu exposes `Processes and Ports...`; the `ports` command opens
the same modal workflow, and `ports <filter>` pre-populates its filter. The
workflow initially includes TCP listeners and UDP endpoints, while other TCP
connections are opt-in.

Each visible row represents exactly one endpoint in a selectable, scrollable
table. The table has stable Process, PID, Proto, Port, Local address, State,
and Remote columns. Header and rows use the same column boundaries, and every
value is clipped within its own cell using terminal-cell width, with an ellipsis
when applicable. PID and Port are right-aligned; the remaining visible columns
are left-aligned. It shows process, PID, protocol, numeric local address, local
port, and TCP state when applicable; active TCP connections also expose their
remote endpoint. Rows remain usable at narrow console widths by reducing or
hiding Remote, Local address, and then other less essential columns before the
process name and the PID, protocol, and port diagnostic fields where physical
width permits. The list always reserves its final console column as a scrollbar
gutter, so filtering, refresh, and endpoint-count changes never shift table
columns. Search text is used solely for filtering, not for row display.
Rows sort by local port, protocol, local address, process name, PID, and state.
The case-insensitive invariant filter operates only on the captured snapshot
and matches process name, PID, executable path, protocol, addresses, ports,
and state. It never causes DNS lookups or a fresh OS query.

The Processes and Ports dialog uses the shared two-axis adaptive modal sizing
policy. Its ordinary useful size remains compact enough for its default
presentation, while a larger terminal viewport gives the dialog nearly all
available width and height within the shared outer margins. A smaller viewport
uses the ordinary viewport-constrained layout. On every committed resize
render, the filter controls, table, status line, and footer receive their new
bounds through the shared composite-modal lifecycle; flexible table columns use
new horizontal space and optional columns retain their ordinary collapse rules.

Details and termination always apply to the selected row, never an implicit
first row. Enter on the endpoint list opens details; Delete requests
termination only while that list has focus and the selected process is eligible.
Other focused controls retain their ordinary Delete and Enter behavior. Missing
process metadata does not hide endpoints, and metadata distinguishes access
denial, exited processes, and other unavailable data. Refresh captures a new
snapshot and preserves the selected endpoint and list position when possible;
capture failures are reported without replacing a prior successful snapshot
with an empty list.

Terminating a process requires confirmation that identifies the process, PID,
executable, start time, and affected ports and warns about unsaved work.
CSharpFar never terminates itself, requires a reliable process start time in
the process identity to reject observed PID reuse immediately before
termination, and refreshes after completion or exit-race results. Termination
can be independently unavailable even when endpoint capture is supported. Demo
sessions display deterministic data but disable termination and never inspect
or terminate real processes. Unsupported hosts explain that the feature is
unavailable and do not run shell fallbacks.

Windows and macOS endpoint capture preserve IPv6 scope/interface information
when the operating system provides it. Native table or ABI failures and
malformed native data are reported as capture failures rather than appearing as
a valid empty endpoint snapshot. A failure to obtain metadata for one process
does not discard its endpoint or other independently obtainable metadata.

On macOS, endpoint ownership and process metadata are obtained directly from
`libproc`; the runtime does not invoke `lsof`, `netstat`, `ps`, `kill`, `sudo`,
`osascript`, or shell-script fallbacks. Capture and pre-termination identity
checks use the same native process start-time source and normalization path.
Linux remains unsupported.

The module is a native first-party module, not a file-panel source. Platform
collection and termination are isolated behind the platform-services boundary;
UI and module code contain neither platform probes nor P/Invoke.

## Non-goals

This is not a task manager: it does not expose all processes, resource usage,
trees, services, windows, process priorities, or process-tree termination. It
does not poll automatically, resolve DNS, launch `netstat`, PowerShell, `ss`,
or `lsof`, or implement Linux endpoint collection. It does not add a separate
macOS UI, privilege-elevation workflow, or process-tree/graceful-termination
policy.

## Acceptance criteria

1. A user can find the owner of a local TCP or UDP port through the menu or
   `ports` command, including IPv4 and IPv6 endpoints on Windows and macOS.
2. Filtering and refresh remain responsive without repeated platform reads
   during rendering.
3. A user can select any visible endpoint by keyboard or mouse; filtering,
   endpoint-type changes, refresh, and returning from details retain that
   selection when the endpoint remains available.
4. Details, access errors, stale identities, process exit races, capture
   failures, and empty results are understandable and do not crash the
   application.
5. Termination is explicit, applies only to the selected eligible endpoint,
   rejects self-termination and observed stale process identities immediately
   before the kill operation, and is unavailable without real side effects in
   demo mode.
6. The dialog follows the shared composite-modal lifecycle: its filter controls,
   endpoint table, status, and actions retain shared scrolling, focus,
   input-routing, and resize behavior.
7. Long process names and IPv6 addresses cannot shift neighboring columns, and
   resizing or scrollbar visibility preserves the table's column boundaries for
   its current content width.
8. At a larger terminal viewport, the dialog expands in both dimensions and
   gives the endpoint table the additional content area without changing the
   compact sizing of unrelated dialogs.
9. macOS uses `libproc` for endpoint ownership and process metadata, preserves
   the existing TCP/UDP query semantics, and does not start external helper
   processes.
10. Linux continues to report Processes and Ports as unsupported.

## Verification

Automated verification covers Windows loopback TCP/UDP behavior and native-row
parsing, plus macOS ABI layout and parsing, IPv4/IPv6 loopback listeners, UDP,
an established TCP connection with `IncludeOtherTcpConnections`, process
metadata normalization, and platform composition. The macOS native integration
verification runs only on macOS and inspects endpoints owned by the test process
so it does not require root or access to unrelated system processes. Automated
verification also covers deterministic filtering/sorting and selection
preservation, stable table layout and terminal-cell clipping for long and
Unicode values, selected-row termination safety and refresh behavior with a
fake service, and unsupported Linux composition. Manual verification checks the
command, keyboard and mouse list selection, TCP/UDP IPv4 and IPv6, details,
denied termination, demo data, capture failures, scrollbar appearance while
filtering, and adaptive narrow-to-wide resize behavior.
