# IDD-0081.spec-runtime-diagnostics

## Intent

CSharpFar provides an opt-in runtime diagnostics mode that lets a user reproduce
a problem in an ordinary Debug or Release build, inspect recent application
events in the UI, and copy one safe diagnostic report for an issue, chat, or
developer without attaching a debugger or finding log files.

## Behavior

The independent command-line flag `--diagnostics` enables runtime tracing. It
works in normal mode and together with `--demo <root-path>` in either argument
order. Diagnostics is not a build configuration and does not replace Debug or
Release.

`Help -> Diagnostics...` is always available. With diagnostics enabled it
shows safe system information and the most recent runtime events. With
diagnostics disabled it still shows safe current system information, states that
runtime tracing is off, and explains that CSharpFar must be restarted with
`csharpfar --diagnostics`.

The diagnostics dialog is read-only and scrollable and provides Copy, Clear, and
Close actions. Copy puts the same complete report representation shown by the
dialog on the configured text clipboard. Clipboard failure is reported without
crashing the application. Clear removes only buffered events; diagnostics stays
enabled and records that the log was cleared. Escape closes the dialog through
normal modal behavior.

Runtime events are kept only in memory in a thread-safe 1000-entry ring buffer.
Overflow discards the oldest entries while preserving event order. Diagnostic
entries contain timestamp, source category, and message. Exception entries
capture string data needed for diagnosis, including type, message, stack trace,
and inner exception chain; they never retain the original Exception object.

The report contains display, informational, assembly, and comparable release
versions; OS and process architecture; .NET runtime; process ID and start time;
a home-redacted current directory; diagnostics state; safe terminal/input state;
and recent events. Event timestamps include milliseconds and the report header
contains an explicit timezone offset.

The existing `Options -> Terminal diagnostics`, TerminalTrace, and crash report
remain separate features.

## Safety And Performance

Diagnostic call sites log allow-listed metadata rather than arbitrary
application data. Reports do not intentionally include passwords, access tokens,
API keys, authorization headers, connection strings, file contents, clipboard
contents, response bodies, or environment dumps. URL userinfo, query, and
fragment are removed. Known credential patterns in exception text are
best-effort sanitized, and a user-home prefix in paths is represented by `~`.

When diagnostics is disabled there is no ring buffer, stack-trace capture,
diagnostic string formatting, disk I/O, extra HTTP request, or UI invalidation
for event tracing. Diagnostic failures are contained inside the diagnostics
infrastructure and must not break the application operation being observed.

## Update Check Integration

The application composition owns one UpdateCheckService using the session-wide
diagnostic log; opening About does not construct an independent service or log.

When tracing is enabled, update checking records request start, HTTP status and
elapsed time, safe GitHub rate-limit headers when present, parsed release tag,
final result, and a concrete reason for every unavailable result. Internal
service timeout is distinct from caller cancellation. HttpRequestException,
invalid JSON, invalid/missing tag data, invalid release URL, unsupported response
format, and unavailable current comparable version are diagnosable. Response
bodies and authorization/cookie headers are never logged.

## Application Update Integration

The macOS Homebrew updater defined by 0082 uses the same session-wide opt-in
diagnostic log and a separate `ApplicationUpdate` category. It records safe
high-level stages, updater availability, detected Homebrew and installation
classification, expected/available/installed versions, process exit codes,
sanitized short stderr, quarantine result, and relaunch result.

Updater diagnostics never create a persistent updater log. When diagnostics are
disabled the updater performs no diagnostic buffering or disk logging.

## Acceptance Criteria

1. `csharpfar --diagnostics` starts an ordinary session with diagnostics
   enabled; demo mode can be combined with the flag in either order.
2. Normal startup propagates ApplicationRunOptions into application composition.
3. Help contains Diagnostics while Options retains Terminal diagnostics.
4. Diagnostics ON retains only the newest 1000 events and Copy produces one
   sanitized report with application, environment, terminal, and event data.
5. Diagnostics OFF allocates no event buffer but the dialog still explains how
   to restart with diagnostics enabled and can copy its safe system report.
6. About uses the application-owned UpdateCheckService, and any unavailable
   update-check result has a specific diagnostic reason when tracing is enabled.
7. Diagnostics, report formatting, optional terminal metadata, and clipboard
   failures do not crash the main application.
