# IDD-0010 - File operations specification

Related:
- IDD-0007
- IDD-0008
- IDD-0060
- IDD-0074
- IDD-0075

## Context

CSharpFar file operations must be predictable for everyday Far-like workflows:
copy, move, delete, and create directory. Operations need explicit dialogs,
progress, cancellation, conflict handling, metadata options, mask filtering, and
structured results. Single-item rename through `Shift+F6` is owned by `IDD-0060`.

Copy operations separate two concerns:

- conflict decision: what to do when the destination item already exists;
- copy mode: how to behave after read or write failures during content copy.

Append is not a supported operation or conflict decision.

## Scope / Behavior

Operation model:

- File operations use a request/result model rather than string overloads.
- Supported operation kinds are copy, move, delete, and create directory.
- Requests include sources, optional destination, and operation options.
- Options include copy mode, a default conflict policy (not an unconditional
  overwrite instruction), timestamp preservation, attribute preservation,
  security mode, symlink mode, recycle-bin delete, and optional file mask.
- Execution is asynchronous, observes cancellation, and reports structured
  progress.
- For writable non-local providers, copy and move compute and validate the
  final target path for every source item before the first provider mutation.
- Provider preflight rejects a target that resolves to the same provider item
  as the source, and rejects directory targets that resolve inside the source
  directory tree.
- Cancellation may leave already completed items in place but must not report
  success.
- Results report copied, moved, deleted, skipped, failed, canceled counts, byte
  totals, and item errors.
- Old string-based operation APIs are not kept as compatibility shims.

Pre-operation dialogs:

- `F5` opens a copy dialog.
- `F6` opens a move dialog unless the single-source edited destination is a
  rename case owned by `IDD-0060`.
- Copy and move destinations are prefilled from the opposite panel directory.
- Copy dialog fields include destination path, copy mode, access-rights mode,
  existing-file behavior, preserve timestamps, preserve attributes,
  symlink-content option, use-filter option, and filter mask.
- Copy and move dialogs include an explicit `Use template` destination mode,
  disabled whenever a dialog opens and not persisted as an operation default.
  The destination text itself may remain in history.
- Move dialog fields include destination path, mask for multi-source moves, and
  conflict/metadata options needed when move falls back to copy-delete. Move and
  rename do not expose copy mode.
- Delete dialog shows item count, total size when reasonably available, and
  permanent-delete versus recycle-bin behavior.
- Dialogs use the shared popup/dialog renderer, active palette, and existing
  input patterns.
- Last selected operation options are stored in settings and reused as defaults.
- The built-in default access-rights mode for new settings is `Default`.

Copy dialog UI:

- The copy dialog title is `Copy`. Its footer contains `{ Copy } [ Preview ] [ Help ] [ Cancel ]`. `Preview` is governed by `IDD-0075`. `Help` and `F1` open a dedicated contextual Copy Help page without submitting, validating, accepting field history, or closing the dialog. This page is a separate Copy document, not a scrolled position within Main Help, and begins at its own top. Closing Help resumes the same dialog session with its entered text, selected values, focus, and scroll position preserved.
- It contains the line `Copy <source> to:`, destination input, copy-mode radio
  row, access-rights radio row, existing-file behavior row, timestamp checkbox,
  attributes checkbox, symlink checkbox, filter checkbox, filter mask input, and
  `{ Copy } [ Preview ] [ Help ] [ Cancel ]` buttons.
- Local copy modes are `Normal`, `Reliable`, and `Fast salvage`.
- Provider copy exposes only `Normal` until provider copy supports seekable
  resume validation and per-file salvage continuation.
- Access rights use exactly radio-style notation such as
  `(x) Default ( ) Copy`.
- The existing-file choices are one logical focusable control even when they
  occupy multiple visual lines below `Already existing files:`. Left and Right
  move through all values, Tab leaves the whole group, and the console cursor
  follows the selected radio-style marker across lines.
- The `Already existing files` choice configures a default conflict policy,
  not the final action on every existing destination. Available defaults and
  type-sensitive execution are defined in the authoritative Conflict handling
  section below.
- The default filter mask text is `*`.
- When `Use filter` is off, the mask is not applied.
- A disabled filter input does not retain its value in field history when the dialog is accepted.
- When `Use filter` is on, only matching files are copied; recursive directory
  copy still traverses directories whose names do not match.
- Multiple simple masks may be separated with `;`; whitespace is trimmed.
- The dialog is compact, centered, visually modal, and uses shared dialog colors
  and shadow behavior.
- Contextual Copy Help is headed `CSharpFar — Copy` and documents Copy destination behavior, FAR-compatible destination `*` and `?` transformations, explicit `Use template` syntax (including `{name}`, `{ext}`, modified-date formatting, and escaping), Copy modes, existing-file choices, access-rights and metadata options, and source filtering. It makes clear that `Filter mask` selects source files, destination wildcards transform destination names, and templates compute destination paths and names. It contains no unrelated Main Help sections.
- Main Help remains the application-wide help document and retains its ordinary top position when opened normally. It may summarize Copy but does not duplicate the detailed Copy Help page.

Progress:

- Copy progress has a preliminary scan phase and an operation phase.
- The visible console cursor is hidden while the modal copy operation runs; the
  next active surface controls cursor visibility after the operation closes.
- During scan, the dialog shows current scanned folder, discovered file count,
  folder count, and accumulated byte count. It does not show a progress bar.
- During operation, the dialog shows current file path, destination path when
  applicable, current file progress, total byte progress, processed item counts,
  elapsed time, estimated remaining time, and speed.
- Total progress is byte-based after scan denominators are known.
- Long paths may be shortened in the middle.
- Progress bars use block-style characters, not `#`.
- `Esc` during scan cancels immediately.
- `Esc` during copying opens a warning confirmation dialog with `{ Yes }` and
  `[ No ]`; copying is paused while confirmation is open.
- Modal file-operation dialogs use shared dialog/window helpers.

Conflict handling — authoritative contract for copy, move, and rename:

Pre-operation dialog policy (distinct from a per-item conflict action):

- The `Already existing files` control in the Copy dialog offers exactly
  `Ask`, `Overwrite`, `Skip`, `Rename`, and `Only newer`.
- Move and Rename dialogs offer exactly `Ask`, `Overwrite`, `Skip`, and
  `Rename`. They do not offer copy-only `Only newer` or `Append`.
- These selections are stored as operation defaults. `Ask` defers the decision
  until the destination item and both item types are known.
- A configured `Overwrite` is a file-conflict default only. For an existing
  directory-to-directory Move/Rename target, it must become `Ask`; it must not
  select `Replace`, delete the destination tree, or authorize an implicit merge.
  `Skip` and `Rename` defaults retain their meanings for compatible item types.
- Per-conflict `Remember choice` is operation-scoped, not a persisted dialog
  default. It can produce `OverwriteAll`, `SkipAll`, or `RenameAll` where
  applicable; these are not additional choices in the pre-operation dialog.

Per-item decisions (chosen or normalized only after target type is known):

- Copy, file -> file: `Overwrite`, `Skip`, `Rename`, `OnlyNewer`
  (copy-only policy), or `Cancel`; `Ask` obtains a per-item choice.
  `OverwriteAll`, `SkipAll`, and `RenameAll` are the operation-wide
  forms of the corresponding decisions. `OnlyNewer` replaces a file only
  if the source last-write timestamp is newer than the destination's; it
  is not supported for provider copy.
- Copy, directory -> directory: traverse/copy into the existing destination
  directory; resolve encountered file conflicts according to the copy policy.
  This is not a whole-directory `Replace` and must not silently delete the
  destination tree. Copy does not introduce a destructive whole-directory
  overwrite choice.
- Move/Rename, file -> file: `Overwrite`, `Skip`, `Rename`, or `Cancel`;
  `Ask` opens the file-conflict dialog. `OverwriteAll`, `SkipAll`, and
  `RenameAll` are operation-wide variants where applicable.
- Move/Rename, directory -> directory: `Merge`, `Replace`, `Rename`,
  `Skip`, or `Cancel`; `Ask` opens the directory-conflict dialog.
  `Overwrite` / `OverwriteAll` never alias `Replace`. `Merge` and
  `Replace` require an explicit directory-conflict decision, not a remembered
  file overwrite setting.
- A file -> directory or directory -> file type mismatch is non-destructive.
  It cannot be resolved as overwrite, merge, or replace and must not delete
  either existing item; validation fails or the item remains unchanged under
  an applicable skip policy.
- The per-item conflict dialog uses `{ Overwrite } [ Skip ] [ Rename ] [ Cancel ]`
  for file -> file and `{ Merge } [ Replace ] [ Rename ] [ Skip ] [ Cancel ]`
  for directory -> directory. It shows source/destination metadata when available.
  Move/Rename dialogs never offer append or `OnlyNewer`.
- `Rename` selected interactively asks for a new destination name. An
  automatic `Rename` default or `RenameAll` without an explicit new name
  generates a free name in the same destination directory by appending ` (2)`,
  ` (3)`, and so on before the extension.
- `OverwriteAll` applies only to file conflicts and never extends to
  directory replacement. Operation-wide `SkipAll` and `RenameAll` never
  authorize deletion of a mismatched destination. `Merge` and `Replace`
  are not silently remembered as a blanket decision for other directories.
- `Append`, `AppendAll`, and tail-validated resume are not conflict
  decisions; copy retry/resume behavior is governed by the selected copy mode.

Move/Rename execution safety (including same-parent Rename):

- Move and Rename are data-preserving operations. A failed direct move is an
  error unless the direct-move layer explicitly determines that the operation
  is unsupported for the source/destination topology. Arbitrary
  `IOException`, permission errors, sharing violations, provider errors, and
  locked files must not trigger copy/delete fallback.
- Whole-item same-parent Rename always uses the provider/filesystem rename
  operation, even when a wildcard or destination template produced the final
  name. A failed direct Rename does not fall back to per-file Copy + Delete.
- Local Move across filesystems uses the existing Copy/Delete fallback only for
  a known cross-filesystem topology or a native cross-device error. On Windows,
  clearly different roots are recognized before the direct attempt. The source
  may be deleted only after successful completion of the Copy.
- For known cross-filesystem `Replace`, use destination-side staging; the
  original destination remains intact until staging Copy succeeds. Arbitrary
  `IOException` must never be interpreted as permission to use the fallback.
- `Merge` keeps the destination root and moves children individually. After
  skip, error, or cancellation, already moved children remain in the
  destination and untransferred children remain in the source. Remove the
  source root only when it is actually empty.
- `Replace` must preserve the old destination until committing the new one.
  A same-filesystem replacement uses a unique sibling backup. Copy/delete
  replacement uses a unique sibling staging path, copies fully before touching
  the existing destination, commits staging, then removes the source and cleans
  the backup. Rollback/cleanup may mutate only temporary paths owned by the
  active operation.
- Provider Move/Rename never calls `DeleteAsync(destination)` before a
  potentially failing `RenameAsync(source, destination)`. Where provider
  capabilities cannot support the necessary backup/rollback semantics,
  destructive `Replace` is unavailable.
- Provider self-target validation runs before conflict resolution, destination
  deletion, directory creation, or stream opening, so overwrite cannot delete
  a source item through the same provider path.

Copy modes:

- `Normal` performs ordinary copying with no automatic retry. Destination
  conflicts use the configured conflict decision.
- `Reliable` aims to produce a complete correct destination file. It uses the
  tail-validation resume behavior from `IDD-0019`, retries source read and
  destination write failures, closes streams after failures, rereads the real
  destination length from disk, validates the source snapshot, and resumes only
  from the analyzer's safe offset.
- `Fast salvage` quickly copies readable files from a failing source. Source
  read failure marks that file failed, records an item error, cleans up the
  partial destination by default, and continues with later files. If
  `KeepPartialFilesOnError` is enabled, the partial destination is renamed with
  a safe partial-file suffix instead of being deleted. Destination write
  failures get at most one short retry and must not silently skip large batches
  of files.

Mask filtering:

- File operations use the existing Far-like mask support from
  `CSharpFar.Core.FileMasks`.
- Empty mask means all selected sources.
- Recursive masked copy applies masks to files and still traverses directories
  that may contain matching files.
- Empty directories are copied only when the mask is empty.
- File operations do not introduce a second mask syntax.

Metadata:

- When enabled, copied files preserve creation time, last-write time, and
  last-access time after content copy.
- Directory timestamps are restored after child processing.
- When enabled, ordinary file attributes are preserved after content copy.
- `ReadOnly` is preserved by default.
- Default security mode is `Default`.
- `CopyAccessControl` attempts to copy Windows ACLs and reports ACL failures as
  item errors.
- Persisted `Inherit` and unrecognized security-mode values are treated as
  `Default`; `Inherit` is not a selectable or supported access-rights mode.
- No cross-platform compatibility layer is added for ACL behavior.

Symlinks and reparse points:

- Supported policies are `CopyLink` and `CopyTargetContents`.
- Links and junction-like reparse points are detected before recursive
  traversal.
- Default behavior is `CopyLink`.
- If link recreation is not permitted, the operation reports a clear item error
  instead of silently copying target contents.
- `CopyTargetContents` follows the target and copies contents.

Delete:

- Delete supports permanent delete and recycle-bin delete.
- `AppSettings.FileOperations.UseRecycleBinForDelete` requests recycle-bin
  deletion only when the active source is local and the current platform
  reports recycle-bin support.
- Recycle-bin behavior is Windows-specific and belongs in platform-specific
  filesystem code.
- When the platform does not support recycle-bin deletion, the normal delete
  command confirms permanent deletion and deletes permanently regardless of
  the recycle-bin setting.
- Shared file-operation workflow delegates platform-specific filesystem details
  to platform-owned operations. Windows owns recycle-bin delete, reparse-point
  link recreation, attributes, and ACL copying. Unix/Linux owns symlink
  recreation and Unix file mode preservation and must not silently treat an
  explicit recycle-bin delete request as permanent delete.
- Writable non-local providers may implement the same copy, move, delete,
  rename, create-directory, and stream contracts without using local
  `System.IO` operation branches. A demo in-memory provider is one supported
  example.
- The reachable panel-source registry is the runtime allow-list for filesystem
  operation execution. When the local source is not registered, a legacy or
  malformed local request must fail before any `System.IO` enumeration, file
  existence check, read, write, move, or delete against the host filesystem.
- Delete progress shows item count and current path.
- Permanent recursive delete reports per-item failures.

Create directory:

- `F7` can create nested directories such as `a\b\c`.
- Invalid names fail before partial creation where possible.
- After success, the panel refreshes and places the cursor on the created
  top-level directory when possible.

## Non-goals

- Alternative NTFS data streams.
- Ordinary destinations resolving to multiple destination directories. Explicit
  destination templates are governed by `IDD-0075`.
- Copying to `NUL`.
- `.diz` description preservation.
- Append.
- Rescue copy, sparse reconstruction of unreadable ranges, zero-filled damaged
  ranges, rsync-like block matching, whole-file hash verification, and parallel
  copy of a single file.
- Creating hard links or symbolic links instead of copying ordinary files.
- Hard-link identity preservation.
- Plugin or virtual-filesystem copy/move APIs.
- Archive, FTP, SFTP, or cloud file operations.
- Background minimized progress that allows panel browsing during an operation.
- Compatibility wrappers for old file-operation APIs.
- CD/DVD-specific read-only attribute clearing.

## Acceptance criteria

- `F5` opens a copy dialog with destination and operation options.
- A copy dialog opened with built-in default settings selects access-rights
  mode `Default` and offers only `Default` and `Copy`.
- Copy dialog keyboard navigation can move focus to the `{ Copy }`,
  `[ Preview ]`, `[ Help ]`, and `[ Cancel ]` buttons; Enter or Space activates
  the focused button.
- Moving focus from the destination input to access-rights, existing-file, or
  checkbox options moves the visible console cursor into the active option
  marker; it never remains visible in the previous input.
- `F6` opens a `Move` dialog prefilled with the opposite panel directory.
- Confirming an unchanged `F6` dialog moves current or selected items into the
  opposite panel directory.
- When a writable non-local provider is active on both panels, confirming an
  unchanged `F6` dialog moves current or selected items into the opposite panel
  directory inside that provider instead of treating the destination directory
  as a conflicting rename target.
- Provider copy to the same provider item leaves the source unchanged and does
  not let overwrite delete or rewrite that same item through itself.
- Provider copy or move of a directory into itself or one of its descendants is
  rejected before any provider tree mutation.
- If any source item in a multi-item provider copy or move has an invalid final
  target, the whole request is rejected before the first item is modified.
- `F8` can delete permanently or send to recycle bin.
- On a supported platform, local `F8` delete uses the recycle bin when
  `UseRecycleBinForDelete` is enabled and confirms permanent deletion when it
  is disabled.
- On Unix/Linux, local `F8` delete always confirms permanent deletion and
  deletes permanently, including when `UseRecycleBinForDelete` is enabled.
- `F7` can create nested directory paths.
- Copy and move progress show current file progress and total progress.
- The console cursor does not blink over the copy progress dialog while copying
  is running.
- Progress shows speed, ETA, and processed item count.
- User cancellation stops the operation and reports cancellation.
- UI does not synchronously block on async file operations.
- Copy and Move/Rename use their distinct pre-operation policy lists and
  resolve individual conflicts according to source/destination item types.
- A preselected `Overwrite` never replaces a destination directory: a
  directory-to-directory Move/Rename conflict requires a deliberate `Merge`
  or `Replace` action; Copy preserves the existing destination directory
  while processing its children.
- `OverwriteAll` applies only to file conflicts; directory type mismatches
  cannot delete or overwrite an existing destination.
- Copy mode is selected independently from conflict handling and supports
  `Normal`, `Reliable`, and `Fast salvage` for local copy.
- Normal application Help opens the Main Help document. `F1` and `[ Help ]` in
  the Copy dialog open a separate `CSharpFar — Copy` document at its top, whose
  scrolling cannot expose unrelated Main Help sections.
- Closing contextual Copy Help with its help close commands returns to the same
  Copy dialog session. Confirming or cancelling after return uses the preserved
  destination and selected Copy options.
- `Append`, `AppendAll`, and resume-with-tail-validation are not conflict
  decisions.
- Old persisted `Append` and `AppendAll` conflict settings fall back to `Ask`.
- Old persisted `ResumeWithTailValidation` conflict settings become
  `CopyMode = Reliable` with a non-overwriting conflict decision.
- Rename-generated names use `name (2).ext`, `name (3).ext`, and so on.
- File masks use the existing Far mask parser.
- Masked recursive copy does not copy non-matching files.
- Timestamps, attributes, ACL mode, and symlink mode follow selected options.
- A persisted `Inherit` access-rights value loads as `Default` without making
  settings invalid.
- Link creation failure is reported clearly and does not silently copy target
  contents.
- On Unix/Linux, explicit recycle-bin delete fails clearly until Freedesktop
  Trash support exists.
- Directory/file type conflicts do not destructively replace the destination
  on local or writable-provider operations.
- Move/Rename failures cannot trigger destructive fallback on arbitrary I/O
  errors; safe `Merge`/`Replace` preserve existing data as described in the
  authoritative Conflict handling section.
- Operation defaults persist under `AppSettings.FileOperations`.
- Panel refresh and selection clearing remain predictable after operations.
- When the active source or destination is a writable non-local provider such as
  the demo file system, the shared file-operation workflow uses provider-aware
  operations instead of treating the provider path as a local filesystem path.
- In a composition whose source registry omits the local source, an accidental
  legacy local delete, copy, move, or create-directory request cannot mutate
  the host filesystem.
