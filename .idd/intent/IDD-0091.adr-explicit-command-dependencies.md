# IDD-0091 — Explicit application command dependencies

## Status

Accepted

## Context

Application commands are internal, synchronous use-case entry points shared by keyboard shortcuts, function keys, menus and the application runtime. Their dependencies must be apparent at construction, without access to the entire application. The committed-frame input contract remains owned by IDD-0067; provider-qualified identity remains owned by IDD-0090.

## Decision

- Implement `IApplicationCommand` with a stable command ID and `CanExecute(object? args)` / `Execute(object? args)`. Inject only the services and state slices needed by the command in its constructor. Invocation arguments carry data for that execution, not services.
- Compose the standard commands explicitly in `DefaultApplicationCommands` through the application composition root. `ApplicationCommandRegistry` stores commands by ID, checks availability and dispatches; it does not resolve dependencies. Preserve the existing unknown-ID behavior and all public command IDs.
- Use `PanelCommandTargetResolver` for active and passive panel resolution. With a committed invocation, retain its side, visible row count and both frame snapshots. Without one, resolve live state on each invocation. Use the same resolver's committed-location and item-identity checks before consuming a committed item; never silently substitute the current cursor's item for a stale committed identity.
- Reuse existing domain-specific panel, navigation, sort, viewer, search and plugin services. `PanelFileOperationWorkflow` owns file-operation options, preview, execution and refresh; `PanelSettingsChangeService` owns applying panel settings changes by refreshing both panels and saving. Neither is an application-wide facade.
- Use narrow callbacks when a real lifecycle boundary requires late composition. Auto-refresh's refresh callback closes the navigation/refresh cycle; function-key availability and module panel opening are wired when the registry and plugin opener exist. Runtime callbacks connect terminal lifecycle and input/menu dispatch to the application. `ExternalPluginSession` exposes only the optional ready extension manager, not arbitrary services.

## Alternatives Considered

- A universal command context or multiple renamed service bags: rejected because dependencies remain implicit.
- A service locator, global application singleton or DI container accessible to commands: rejected because it conceals dependencies and prevents focused tests.
- A new interface per dependency: rejected; existing concrete services can be composed directly.

## Consequences

New commands must declare their dependencies explicitly, use data-only arguments and be registered with their stable IDs in the composition root. Test the command in isolation where possible, including changing panel state after construction and committed-frame identity when applicable. Keep integration tests for keyboard/menu dispatch and plugin behavior. Architecture tests guard against universal contexts, service locators and direct composition-root dependencies. The change does not alter the public SDK or the user-facing command semantics.
