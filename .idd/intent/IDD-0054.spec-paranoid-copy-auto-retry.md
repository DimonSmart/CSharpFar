# IDD-0054 - Reliable copy auto retry specification

Related:
- IDD-0019
- IDD-0030
- IDD-0038

## Goal

`Reliable` copy automatically retries transient read-side and write-side
failures without modal prompts, while leaving the existing user destination
unchanged until a complete staged copy is published.

## Context

Retry/resume applies only to a temporary file belonging to the current
copy operation (or a safely identified unfinished operation), as defined
in IDD-0019. A matching length or tail does not establish ownership
of an existing user destination.

## Scope

1. Retry source-open, source-read, staging-open and staging-write failures
   within the existing bounded retry policy, with an internal delay and
   deterministic test hooks.
2. Before resumed writes, close/reopen source and stage, read their actual
   state from disk, and run tail validation on the **owned staging file**.
3. Resume only from an analyzer-verified offset; never use unverified stream
   positions or modify the final user destination during retry.
4. Transient source failures do not themselves justify rollback. Rollback
   follows only an actual validation mismatch.
5. If the stage is unsafe or the source snapshot changed, restart the stage
   from byte zero or fail the operation safely.
6. Do not repeat an `Overwrite` prompt on retries when the original
   destination has not changed.
7. Exhausted retries use existing error reporting. Do not mark a failed file
   as copied or delete the original destination.

## Non-goals

- Retry configuration UI.
- Automatic retries in ordinary `Normal` mode.
- Provider-to-provider resumable copies.
- Different tail validation window sizes.
- New reusable dialog interactions.

## Acceptance criteria

- Transient source-open/read and staging-open/write failures are retried
  without modal prompts.
- Already completed and validated stage bytes are reused between attempts.
- Existing destination content remains identical until publishing succeeds.
- A failed retry or cancellation leaves old data available; only
  operation-owned stages may be cleaned or retained.
- Repeated source read faults do not induce spurious rollbacks.

## Verification

Tests cover transient source-read and staging-write faults, source
validation failure, matching and mismatching stage tails, retries without
repeated conflict prompts, and real bytes of the original destination.
