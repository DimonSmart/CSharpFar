# IDD-0012 - Search feature specification

Related:
- IDD-0007
- IDD-0009
- IDD-0010

## Goal

Provide file, directory, and text search in CSharpFar.

Search starts from the active file panel, collects a normalized request, runs as a cancellable operation, and opens results as a virtual snapshot-based panel instead of only showing a temporary popup list. The results collection is structurally read-only, but supported actions may edit or delete its referenced filesystem items.

The search engine must return data. It must not render panels directly.

## Context

The current search architecture separates command orchestration, filesystem search,
and presentation:

1. `SearchFilesCommand` handles `Alt+F7`. It checks that the active panel can
   access the registered local filesystem source and that the committed panel
   location still matches UI state. `SearchDialog` builds the request.
2. `FileSystemSearchService` implements `ISearchService`, streams
   `SearchResultItem` values from a local filesystem search, reports
   `SearchProgress`, and uses the existing `FarMaskMatcher` for names.
   `SearchProgressDialog` owns progress, a live result list, Go to, and Stop.
3. `PanelSearchResultsService` projects retained results into a flat
   `PanelContent` snapshot at `PanelLocation.SearchResult(request.RootPath)`,
   with `PanelProviderCapabilities.SearchResults`. `PanelController`
   installs the snapshot in the active panel.

Panel locations are source-qualified: `FilePanelState.CurrentLocation` has a
`PanelSourceId` and source path. `CurrentDirectory` exposes that source path;
it does not by itself imply a local filesystem panel. The search-results
source is virtual, while its rows retain the real `FullPath` of each referenced
local file or directory. Actions on those items must respect panel capabilities
and preserve the real local item location.

The current `Alt+F7` command operates on registered local filesystem panels,
not arbitrary remote or plugin providers. Local file operations can still use
real filesystem paths, after source and capability checks. The virtual results
panel is not a writable directory and does not use generic refresh or watchers.

Search must continue to use `CSharpFar.Core.FileMasks.FarMaskMatcher`, not an
independent mask syntax.

## Scope

The feature comprises the search dialog and `SearchRequest`, the streaming
engine and progress UI, and the virtual results panel. The following sections
group current requirements by responsibility; they do not prescribe unfinished
implementation stages or temporary migration APIs.

### Search dialog and request

`Alt+F7` opens the search dialog using the shared console UI components.
Plain `F7` must keep creating folders.

Illustrative dialog content (the options use two columns; parallelism depends
on the CPU count):

```text
Find file

A file mask or several file masks:
*.*

Containing text:

Using code page: Automatic detection

[ ] Case sensitive            [ ] Include folders in results
[ ] Whole words               [ ] Search in symbolic links
[ ] Not containing

Select search area:
Current folder and subfolders

Parallelism:
4

[ Find ] [ Cancel ]
```

Dialog rules:

1. `Find` validates the fields and returns a `SearchRequest` for execution
   via `SearchProgressDialog` and `ISearchService`.
2. `Cancel` and `Esc` close without starting a search.
3. At the standard dialog size, all parameters and action buttons are visible
   without body scrolling. The error row and buttons form a fixed two-row footer.
4. A form scrollbar reserves its own column and never obscures controls,
   including text-history arrows.
5. Use existing console dialog helpers, shared components and palette conventions.
   Do not introduce a separate UI framework.

Search area:

```csharp
public enum SearchScope
{
    CurrentDirectoryOnly,
    CurrentDirectoryRecursive,
}
```

Rules:

1. `CurrentDirectoryOnly` searches only the active panel directory.
2. `CurrentDirectoryRecursive` searches the active panel directory and descendants.
3. The search-area control is a dropdown whose labels explicitly distinguish
   recursive and non-recursive search:
   - `Current folder and subfolders` selects `CurrentDirectoryRecursive`.
   - `Current folder only` selects `CurrentDirectoryOnly`.

Mask field:

1. The dialog initially displays `*.*`, interpreted with the existing Far-mask semantics.
2. Empty or whitespace-only input normalizes to `*`.
3. The value is a Far mask expression, not a new custom mask list.
4. The expression must be passed through the existing `FarMaskMatcher` semantics: `*`, `?`, ranges, comma/semicolon lists, `|` excludes, regex tokens, groups, `%PATHEXT%`, and `*.*` normalization.
5. Whitespace around the whole field is trimmed.
6. Do not split the request into `IReadOnlyList<string>` in a way that loses existing Far mask expression semantics.

Preferred request model:

```csharp
public sealed record SearchRequest
{
    public required string RootPath { get; init; }
    public required string FileMaskExpression { get; init; }
    public string? ContainingText { get; init; }
    public bool CaseSensitive { get; init; }
    public bool WholeWords { get; init; }
    public bool NotContaining { get; init; }
    public bool IncludeDirectoriesInResults { get; init; }
    public bool SearchInSymbolicLinks { get; init; }
    public SearchScope Scope { get; init; }
    public int MaxDegreeOfParallelism { get; init; }
    public SearchEncodingMode EncodingMode { get; init; } = SearchEncodingMode.Automatic;
    public long MaxContentSearchFileSizeBytes { get; init; } = 100L * 1024 * 1024;
}

public enum SearchEncodingMode
{
    Automatic,
}
```

Naming rules:

1. Use `FileMaskExpression`, not `FileMasks`, because the existing matcher accepts one expression.
2. Use `IncludeDirectoriesInResults`, not `SearchFolders` or `Recursive`.
3. Use `SearchInSymbolicLinks` only for link traversal.
4. Use `SearchScope` for recursive vs non-recursive search.
5. Use `MaxDegreeOfParallelism` for the parallelism setting.

Containing text:

1. Empty text means search by file and optional directory names only.
2. Non-empty text means files must match the name mask and then pass content search.
3. Directories are never searched by content.
4. Directories may appear only when `IncludeDirectoriesInResults` is true and their name matches the mask.

Case sensitivity:

1. When disabled, wildcard mask matching, directory/file name matching, and content search are case-insensitive on Windows.
2. When enabled, wildcard mask matching, directory/file name matching, and content search are case-sensitive.
3. Implement this by extending or optioning the existing mask matcher. Do not create a second mask implementation.
4. Regex mask tokens should have explicit tests before implementation because they already have flags.

Whole words:

1. Applies only when `ContainingText` is non-empty.
2. Word characters are Unicode letters, Unicode digits, and `_`.
3. `Customer` must not match inside `CustomerId` when enabled.

Not containing:

1. Applies only when `ContainingText` is non-empty.
2. If text is empty, the checkbox is visually disabled, excluded from keyboard
   focus and mouse toggling, and ignored during request construction.
3. A file matches `NotContaining` only when its name matches the mask and searchable text content was checked and did not contain the text.

Encoding:

1. First version supports only automatic detection.
2. Detection order:
   - UTF-8 BOM;
   - UTF-16 LE BOM;
   - UTF-16 BE BOM;
   - UTF-8 without BOM when the byte stream is valid UTF-8;
   - Windows ANSI code page.
3. The ANSI fallback must use the Windows ANSI code page explicitly. Do not assume `Encoding.Default` is ANSI on modern .NET.
4. If code page support requires `System.Text.Encoding.CodePages`, add it deliberately in the project that owns content reading.

Parallelism:

1. Valid range is `1..16`.
2. `1` means sequential file content processing.
3. Default is `Math.Min(Environment.ProcessorCount, 4)`.
4. Invalid input shows validation error and does not start search.

### Search engine and progress

`ISearchService` accepts `SearchRequest`, reports progress, supports
cancellation, and streams results. The contracts live in `CSharpFar.Core`.
The filesystem-specific `FileSystemSearchService` owns local traversal and
content reading; the engine returns data and never renders UI.

Service contract:

```csharp
public interface ISearchService
{
    IAsyncEnumerable<SearchResultItem> SearchAsync(
        SearchRequest request,
        IProgress<SearchProgress>? progress,
        CancellationToken cancellationToken = default);
}
```

Result model:

```csharp
public sealed record SearchResultItem
{
    public required string FullPath { get; init; }
    public required string Name { get; init; }
    public required SearchResultItemKind Kind { get; init; }
    public long? Size { get; init; }
    public DateTime LastWriteTime { get; init; }
    public FileAttributes Attributes { get; init; }
    public string? MatchedTextPreview { get; init; }
    public int? LineNumber { get; init; }
}

public enum SearchResultItemKind
{
    File,
    Directory,
}
```

Do not emit filesystem errors as fake search result rows. Report diagnostics through progress, logging, or a separate diagnostic model.

Progress model:

```csharp
public sealed record SearchProgress
{
    public long ScannedDirectories { get; init; }
    public long ScannedFiles { get; init; }
    public long MatchedItems { get; init; }
    public long ErrorCount { get; init; }
    public string? CurrentPath { get; init; }
    public string? LastErrorPath { get; init; }
    public string? LastErrorMessage { get; init; }
}
```

Traversal:

1. Validate `RootPath` before starting.
2. Enumerate files and directories under `RootPath`.
3. Apply `FileMaskExpression` to item names, not full paths.
4. Include directories as results only when `IncludeDirectoriesInResults` is true.
5. Always traverse directories needed by `SearchScope`, even if directory names do not match the mask.
6. If `SearchScope` is `CurrentDirectoryOnly`, do not enqueue child directories.
7. Access denied, path too long, disappeared files, and invalid reparse points must not fail the whole search.

Symbolic links and reparse points:

1. `SearchInSymbolicLinks` defaults to false.
2. When false, do not follow symlink or junction directories during recursive traversal.
3. When true, follow them with cycle protection.
4. Cycle protection may start with normalized full paths of resolved directories.
5. Windows file identity is allowed later if needed, but it is not required for the MVP if normalized paths already prevent ordinary cycles.

Content search:

1. If `ContainingText` is empty, a matching file name is enough.
2. If `ContainingText` is set, a file must match the mask before content is read.
3. `NotContaining == false` means the content must contain the text.
4. `NotContaining == true` means searchable text content must be checked and must not contain the text.
5. Binary files, too-large files, and decode failures do not match either containing or not-containing searches. They may add diagnostics.
6. `MatchedTextPreview` and `LineNumber` are populated only for positive content matches when practical.

Large and binary files:

1. Default `MaxContentSearchFileSizeBytes` is 100 MB.
2. Files larger than the limit are not read for content search.
3. A simple binary heuristic is enough for the first version: sample the beginning of the file and treat it as binary when it contains NUL bytes or a high NUL density.
4. Hex search is out of scope.

Parallelism:

1. Bound all file content work by `MaxDegreeOfParallelism`.
2. Do not create an unbounded task per file.
3. A practical design is one directory producer plus bounded file workers.
4. Use a bounded `Channel` or equivalent backpressure so very large trees do not accumulate unbounded memory.
5. Directory traversal may stay sequential for the first implementation.

Cancellation:

1. Pass `CancellationToken` through every async boundary.
2. Check cancellation during traversal, before content reads, and between read chunks for large files.
3. `Go to` during an active search may cancel the running search and use the selected result to navigate.
4. Explicit stop/cancel of the active search discards already collected results and returns to the previous panel.

Progress UI:

`SearchProgressDialog` shows the current path, counters, a live selectable
results list, and Go to / Stop actions. Example values:

```text
Find file: *.cs
C:\\Project\\src
Files: 1,520  Folders: 84  Found: 17  Errors: 0

Results
      C:\\Project\\src\\Program.cs
      C:\\Project\\src\\Search.cs

[ Go to ] [ Stop ]
```

Rules:

1. Do not show a percentage because total work is unknown.
2. `Esc` or `[ Stop ]` asks for confirmation using the standard red cancellation dialog.
3. Confirmed stop cancels the search and returns to the previous panel without opening partial results.
4. Keep progress rendering on the UI side. The search service only reports data.
5. Confirmed stop is a terminal outcome for the active progress dialog: already streamed results are discarded, no selected result is returned, and later keyboard or mouse input cannot replace the stop with navigation to a result.
6. `Go to` during an active search is a terminal outcome for the active progress dialog: it fixes the selected result from the committed visible results frame, requests cancellation of the running search, and later keyboard or mouse input cannot replace that selected result or switch to stop.
7. After either terminal outcome is selected, the progress dialog may continue showing a stopping state while the background search observes cancellation, but interactive stop, go-to, and list confirmation actions are no longer available.
8. The progress dialog completes only after the background search has actually finished and its final results, cancellation state, or exception outcome is available. Natural search completion must not consume the next console input event that was intended for the parent UI.

### Search results panel

A search run with retained, nonempty results and no Go to / discard decision
opens a virtual snapshot-based panel. An empty result list produces a "No files
found" message, not an empty results panel. Confirmed Stop discards partial
results and preserves the previous panel; Go to navigates to the committed
selected result according to the progress-dialog rules.

An internally cancelled search run can retain results when neither confirmed
Stop nor Go to was chosen. The cancellation flag is then preserved in panel
metadata. Unlike that case, a user-confirmed Stop never opens partial results.

Search results preserve source-qualified item locations. Operations that affect a referenced file must use that item's underlying filesystem location, not treat the virtual results panel as a writable filesystem directory. Panel capability checks apply before dispatching actions; generic refresh, watching, create, rename, move, and copy-to must never accidentally operate on the virtual collection.

Capability model:

```csharp
[Flags]
public enum PanelProviderCapabilities
{
    None = 0,
    Enumerate = 1 << 0,
    OpenRead = 1 << 1,
    OpenWrite = 1 << 2,
    CreateFile = 1 << 3,
    CreateDirectory = 1 << 4,
    Delete = 1 << 5,
    Rename = 1 << 6,
    CopyFrom = 1 << 7,
    CopyTo = 1 << 8,
    MoveFrom = 1 << 9,
    MoveTo = 1 << 10,
    Edit = 1 << 11,
    Refresh = 1 << 12,
    Watch = 1 << 13,
}
```

Use `PanelProviderCapabilities`, not `FileSystemCapabilities`, because the flags describe what the panel may do with a source. A source may be the local filesystem, search results, and later something else.

The search-results panel is an in-memory snapshot; no asynchronous provider loading contract is required solely for presenting that snapshot.

Provider requirements:

1. Local filesystem provider keeps current behavior and has normal write/copy/move/delete/create/refresh/watch capabilities.
2. Search results provider exposes these capabilities for its referenced items:
   - `Enumerate`;
   - `OpenRead`;
   - `CopyFrom`;
   - `Edit`;
   - `Delete`.
3. Search results provider must not expose operations that would make the virtual collection writable or change its topology:
   - `OpenWrite`;
   - `CreateFile`;
   - `CreateDirectory`;
   - `Rename`;
   - `CopyTo`;
   - `MoveFrom`;
   - `MoveTo`;
   - `Refresh`;
   - `Watch`.
4. `Edit` and `Delete` authorize actions on the referenced underlying items, not direct writes or structural mutations through the search-results provider.

Provider and operation boundary:

1. The active search command targets the registered local filesystem source;
   its results are displayed through a separate virtual panel source.
2. Copying from search results uses the referenced items' real `FullPath`
   values and source-qualified locations with the existing file-operation
   service, after checking both sources' capabilities.
3. General provider-to-provider stream copy/move is not required by this
   search feature. FTP/SFTP and native plugin providers exist under separate
   specifications; `Alt+F7` does not search those sources.
4. A search-results panel is not a destination filesystem simply because its
   source path is the real root that was searched.

Panel representation:

1. Reuse existing `FilePanelItem` rendering where practical.
2. Search result items must keep the real filesystem path needed to open and copy the original item.
3. If new provider metadata is added, do not change the meaning of `FilePanelItem.FullPath` to a non-filesystem URI without first updating every operation path that consumes it.
4. The search results panel is a flat list. Do not add virtual folder grouping.
5. Do not show a `..` item in the flat search results panel.
6. Show duplicate file names safely; selection identity must be based on full real path.
7. The UI must expose the full real path of the current result, at least in a status row or a search-specific path row. A full path column is optional for the MVP.

Title examples for ordinarily completed searches:

```text
Search results: *.cs;*.json
Search results: IDisposable
```

The implementation can also display `Search results: *.cs, cancelled` for a
cancelled run that retained results without an explicit Stop or Go to decision.
Confirmed Stop discards results and leaves the previous panel open; it does not
produce that title in a new results panel.

Operations in search results:

1. `Enter` on a file opens its real parent directory in the current panel and selects that file.
2. `F3` views a referenced file when it exists.
3. `F4` opens the built-in editor for a referenced file. Saving modifies the underlying file, not the virtual results collection. Use the selected item's source-qualified location. Directories are not editable. Returning from the editor must not refresh or rebuild the results snapshot and must not re-run search.
4. `Enter` on a directory opens the real directory in the current panel through the local filesystem panel.
5. `F5` copies referenced items only when the active source supports `CopyFrom` and the destination panel supports `CopyTo`.
6. `F6` move and `Shift+F6` rename are disabled for search results.
7. `F7` create folder and all other create operations are disabled for search results.
8. `F8` deletes the referenced underlying items using normal deletion semantics, including the Recycle Bin when enabled and supported for local items. Multi-selection is supported. Selected directories subsume selected descendant items in the physical delete request, avoiding duplicate delete attempts.
9. After an `F8` operation, remove successfully deleted referenced items from the existing result list. Also remove rows for descendants of a deleted directory when those referenced paths no longer exist. On cancellation or partial failure, remove only rows whose underlying items are actually gone; preserve all others. Normalize cursor and scroll state after reconciliation. Never re-run the search as part of deletion.
10. The virtual panel does not support deleting rows independently of the referenced items.
11. Copying or moving items into search results is disabled with a clear message:

```text
Cannot copy to search results panel.
Search results are read-only.
```

Snapshot and refresh:

1. Opening search results stores the retained list as a snapshot of that search run; confirmed Stop and Go to do not open one.
2. Generic panel refresh must skip search-results panels. It must not re-run the stored `SearchRequest` or open `SearchProgressDialog`.
3. Filesystem changes do not automatically reconcile an existing search-results snapshot. Missing files remain in the list, and newly matching files are not added; the exception is targeted reconciliation after `F8` deletion from the results panel.
4. Acting on a snapshot row whose underlying item no longer exists may show the normal open/view/copy error, but absence alone does not remove the row except during `F8` post-delete reconciliation.
5. Returning from `F4` editing does not automatically refresh the result list, even if a file's contents or metadata have changed.
6. `SearchRequest` may remain attached to panel state for search metadata or other existing behavior; its presence is not a refresh trigger.
7. A fresh result snapshot is produced only by an explicit new Search, which replaces the previous search-results content. Post-delete reconciliation removes rows from the current snapshot without creating a new one.

Watchers and history:

1. Do not start `IFileSystemChangeWatcher` for search results panels.
2. Directory history should record real directories opened from search results, not the virtual search results title.
3. File history should record real file paths viewed or opened from search results.

## Non-goals

Do not implement in this spec:

1. a new mask syntax separate from `FarMaskMatcher`;
2. manual code page selection beyond automatic detection;
3. hex/binary content search;
4. approximate/fuzzy text search;
5. search inside archives;
6. search in alternate NTFS streams;
7. live updating search results while the filesystem changes;
8. removing items from results without deleting originals;
9. moving from or into search results;
10. copying into search results;
11. provider-to-provider stream copy for arbitrary virtual providers;
12. extending search into archive, FTP/SFTP, Git status, favorites, or plugin
    sources; these are covered by other features where implemented;
13. reading a demo fixture from its original physical directory after the demo
    snapshot import has completed.

## Acceptance criteria

Dialog and request:

1. `Alt+F7` opens the search dialog.
2. `F7` still creates folders.
3. Empty mask normalizes to `*`.
4. Mask input is treated as a Far mask expression.
5. Invalid parallelism blocks `{ Find }` with validation feedback.
6. `Not containing` is disabled or ignored when containing text is empty.
7. `{ Find }` creates a `SearchRequest` with the active panel directory as `RootPath`.
8. `[ Cancel ]` does not create or execute a request.
9. The standard dialog layout shows the parallelism field and both action buttons without body scrolling; the footer remains fixed and any form scrollbar does not overwrite row content.
10. Search options are presented compactly in two visual columns without
    changing their request semantics.
11. The search area is selected through the standard dropdown control and
    defaults to `CurrentDirectoryRecursive`.
12. Search text inputs use their explicit stable field-history identifiers and share the application history provider. Successful request construction retains normalized submitted values; cancel or validation failure does not.

Engine and progress:

1. Search supports recursive and non-recursive scopes.
2. Search applies masks to item names, not full paths.
3. Search can find files by name only.
4. Search can find files by text content.
5. `Case sensitive`, `Whole words`, and `Not containing` work for content search.
6. Directories appear only when `IncludeDirectoriesInResults` is true and their names match the mask.
7. Symbolic-link traversal follows `SearchInSymbolicLinks` and avoids cycles.
8. Large and binary files are skipped for content search with diagnostics.
9. Access errors do not fail the whole search.
10. Results stream before the whole search is complete.
11. Progress reports scanned files, scanned directories, matched items, current path, and errors.
12. `Go to` during search cancels the running search and navigates to the selected result.
13. Parallel file content work is bounded by `MaxDegreeOfParallelism`.
14. After confirmed stop, partial results are discarded and no later input can choose a result.
15. After the first successful `Go to`, the originally selected visible result remains the navigation target even if later input arrives while cancellation is still finishing.
16. The progress dialog remains open until the background search has actually finished and its final outcome has been observed.

Results panel:

1. Search results open in the active panel when a search run has retained, nonempty results without a Go to / discard outcome.
2. Confirmed Stop during the initial search returns to the previous panel without opening partial results.
3. The results panel is a virtual, structurally read-only snapshot. Editing and deleting referenced filesystem items are explicitly permitted, but the panel is not a writable filesystem source.
4. The results panel is flat and has no `..` item.
5. The current result's real path is visible somewhere in the panel UI.
6. `Enter` on a result file loads its parent directory as a local filesystem panel and selects the file.
7. `F3` views the referenced file.
8. `F4` on a file result opens the built-in editor, and saving modifies the referenced file rather than the virtual results collection; directories are not editable.
9. Returning from `F4` neither refreshes the virtual snapshot nor re-runs search.
10. `Enter` on a result directory opens that real directory as a local filesystem panel.
11. Copying from search results to a capable destination panel works; copying into search results is blocked with a clear message.
12. Move-from, move-to, rename, and create operations remain unavailable for search results.
13. `F8` on a result file or directory deletes its referenced underlying item through normal delete semantics and reconciles the existing result list without re-running search.
14. `F8` honors the Recycle Bin setting when supported for local items and supports multi-selection.
15. Selecting both a directory and an item below it does not cause redundant physical delete attempts.
16. Successful deletion removes corresponding result rows, including now-missing descendants of deleted directories.
17. Cancellation or partial failure preserves rows for referenced items that still exist.
18. Generic refresh does not re-run search, add new matches, or reconcile missing results; only `F8` deletion explicitly reconciles affected rows.
19. Cursor and scroll positions remain valid after result rows are removed.
20. The search results panel does not start an auto-refresh watcher.
21. Existing local filesystem panels retain their navigation, selection, sorting, file operations, refresh, and watching behavior.
22. If a searchable demo provider supports the search contract, search runs against the provider's current in-memory state instead of its original physical fixture.
23. Starting a local-filesystem search requires the local panel source to remain registered in the runtime source registry; `SourceId.Local` alone does not authorize physical search.
24. A new explicit Search creates a fresh snapshot and replaces the previous search results.
25. Confirmed Stop never creates a results panel; an internally cancelled
    run retaining results without Stop or Go to may show a `, cancelled` suffix.
26. A search with no retained results reports no files found instead of
    opening an empty results panel.

## Verification

Manual checks:

1. Open `Alt+F7`, validate each field, cancel, and confirm no search starts.
2. At the standard console size, verify all search parameters, the error row, and Find and Cancel are visible together without a body scrollbar or obscured field edge.
3. Search `*.cs` recursively from a test folder and verify result count.
4. Search current directory only and verify child folders are not searched.
5. Search text with case-sensitive on/off.
6. Search text with whole words against `Customer` and `CustomerId`.
7. Search with `Not containing`.
8. Search with access-denied or disappearing files and verify the search continues.
9. Stop a long recursive search, confirm cancellation, and verify the previous panel remains open without partial results. Separately verify retained-result cancellation metadata and title formatting without interpreting confirmed Stop as opening partial results.
10. While a stopped search is still showing its stopping state, try to activate `Go to` or confirm a visible result and verify that no partial result opens.
11. While a `Go to` cancellation is still showing its stopping state, try to move selection and activate another result and verify that the originally selected result is used.
12. Copy a file from search results to a normal folder; verify copy-to, move, rename, and create remain blocked.
13. Press `F4` on a file result, edit and save it, return to the results, and verify that the underlying file changed but the virtual list was not rebuilt or refreshed. Verify directories cannot be edited.
14. Press `F8` on a result file and directory and verify the referenced item is deleted, the correct result rows disappear, and search is not re-run.
15. Delete multiple selected results, including a selected directory and its descendant; verify that the physical delete roots are not duplicated.
16. With Recycle Bin enabled and supported, delete a referenced local item and verify normal Recycle Bin semantics.
17. Cancel deletion or force a partial failure and verify that result rows referring to existing files remain while rows for deleted items are removed. Verify cursor and scroll remain valid.
18. In a composition where the local source is not registered, verify `Alt+F7` is unavailable before any local filesystem search or existence check starts.
19. Open search results, hide panels, run an external command, restore panels, and verify the same result rows remain without a new search progress dialog.
20. Delete a found file and create another matching file *outside* CSharpFar, run generic refresh, and verify the existing snapshot stays unchanged.
21. Run Search again and verify the panel is replaced with a fresh snapshot.
