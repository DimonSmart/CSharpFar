# IDD-0017 - Current-console program launch specification

Related:
- IDD-0009
- IDD-0016
- IDD-0022

## Goal

Change external program launch behavior so executable files and typed commands run
like Far Manager: the child console process writes directly to the same console,
CSharpFar waits for it to exit, and then CSharpFar redraws its UI.

## Context

`IDD-0009` opened every file through Windows Shell. Platform association opening is
still right for documents, folders, images, PDFs, URLs, and other
association-based objects, but it is not the desired behavior for console
programs. For executable files and commands, CSharpFar
should not redirect stdout/stderr and should not ask the shell to create a separate
window. The child process should inherit the current console and write directly to
the visible console buffer.

The current rendering model in `IDD-0016` already has a clear distinction between UI
rendering mode and shell output underlay. The terminal screen mode from `IDD-0022` makes
that boundary physical in VT-supported terminals: full-screen CSharpFar UI lives in the
alternate screen buffer, while external program output lives in the main screen buffer
and remains part of terminal history. This VT-first model is also the intended
direction for Linux and macOS terminal portability.

## Scope

- On Windows, the built-in simple `set NAME=value` command expands `%NAME%`
  references against CSharpFar's current process environment before assigning
  the variable. Expansion observes the target's pre-assignment value; quoted
  assignments store the unquoted expanded value; and an empty assignment still
  removes the variable. Unresolved `%NAME%` references remain literal, matching
  interactive `cmd.exe`. Special `set` forms remain delegated to `cmd.exe`, and
  this built-in expansion does not change Unix behavior.
- Keep command-line execution in current-console mode: `UseShellExecute = false`,
  no stdin/stdout/stderr redirection, no new console window, and wait for process
  exit.
- Typed command execution is built with platform command-line builders that keep
  each platform shell's quote semantics intact. Windows `cmd.exe` receives the
  complete typed command as a single `/d /s /c "..."` command string through
  `ProcessStartInfo.Arguments`. The outer command-string quotes must preserve
  commands without quotes, quoted arguments, and a quoted executable path followed
  by quoted arguments. `ArgumentList` is not used because it escapes quotes in a
  way that `cmd.exe` and `.bat` files do not interpret as ordinary command quotes.
  Linux and macOS pass `-c` and the complete command to `/bin/sh` or the configured
  shell through `ProcessStartInfo.ArgumentList`.
- A typed command may explicitly select a registered shell with a
  case-insensitive `<alias>:` prefix. An unregistered prefix remains ordinary
  command text and follows the configured default shell. Explicit selection
  takes precedence over built-in command and module handling.
- Windows registers PowerShell aliases `ps`, `pwsh`, and `powershell`. Its script
  is supplied as one `ProcessStartInfo.ArgumentList` value following `-NoLogo`
  and `-Command`, preserving quotes, indentation, and line breaks. PowerShell 7
  (`pwsh.exe`) is preferred, with Windows PowerShell (`powershell.exe`) as
  fallback. If neither is available, the command reports a clear error and
  CSharpFar continues running.
- Before every current-console child process starts, ensure the terminal is in main
  screen mode. In VT-supported terminals this means leaving alternate screen mode before
  process execution and scrolling the main screen buffer viewport to the bottom before
  synchronizing the renderer with that visible main screen viewport, then writing the
  prompt and child output.
- On Unix-like terminals, also reset attributes, show the cursor, restore cooked
  terminal mode, and flush before starting the child process. After the child
  exits, restore application input mode, re-enter alternate screen when panels
  should be visible, resize the logical UI surface if the terminal size changed,
  and repaint from the UI buffer.
- After the child process exits, return to alternate screen mode only when the
  workspace mode is `Panels`; remain in main screen mode in `HiddenCommandLine`.
- While a current-console child process is running, `Ctrl-C` is delivered to the
  child process as a normal console control event so a long-running child can be
  stopped without closing CSharpFar.
- Executable-file detection is a platform service, separate from the shell
  command profile.
- On Windows, executable panel items are detected from `PATHEXT`, falling back
  to `.exe`, `.com`, `.bat`, and `.cmd` when `PATHEXT` is empty. Extension
  matching is case-insensitive and directories are not executable files.
- On Linux and macOS, executable panel items are detected from file execute bits on
  regular files or symlink targets. File extensions do not make a file
  executable.
- Windows `.bat` and `.cmd` files run through `cmd.exe /c` in the current
  console and wait for exit. Other executable files run directly.
- Linux and macOS executable files run directly in the current console and wait for
  exit.
- Local file opening has two modes: `AssociatedDetached` for non-executable
  files and `CurrentConsole` for executable files. The mode names describe the
  process behavior relative to CSharpFar.
- `AssociatedDetached` opens a non-executable file through its platform file
  association and returns immediately. It never moves CSharpFar to the main
  screen, hides panels, waits for the associated application, or routes through
  current-console execution.
- On Windows, `AssociatedDetached` delegates the system `open` association to
  the Explorer shell as a detached broker. The associated application is not a
  child of CSharpFar's console: it cannot write diagnostics or normal output
  into the CSharpFar terminal, and CSharpFar does not create an extra visible
  console window.
- On Linux, `AssociatedDetached` tries `xdg-open`, `gio open`, `wslview`,
  and (in WSL) `explorer.exe` in that order. Launcher stdout and stderr do not
  reach the CSharpFar terminal. A failed launcher start may advance to the next
  candidate; CSharpFar does not wait for the application opened by a successful
  launcher.
- On macOS, `AssociatedDetached` delegates to `/usr/bin/open` using the file's
  full path as a separate argument. It does not switch CSharpFar out of its
  panel UI, expose launcher output in the terminal, or wait for the opened
  application to finish. The launcher may wait briefly for the `open` broker
  itself to report an immediate failure, and reports a start error or prompt
  nonzero exit to the user.
- An association launch reports only immediate launch failures, including a
  missing association or launcher, an unavailable path, or an operating-system
  refusal. Failures occurring later in the detached application are not tracked.
- Hosts validate shell defaults at startup: Linux and macOS replace unavailable
  Windows-like shell defaults with `/bin/sh -c`, and Windows replaces an
  unavailable `/bin/sh` default with `cmd.exe /c`, then saves corrected
  settings.
- On macOS, user-launched shell commands, registered PowerShell aliases, and
  executable files opened from panels share an effective child-process `PATH`
  controlled by `shell.macOsPathMode`:
  - `appendStandard` is the default, including when this setting is absent.
    It keeps existing `PATH` entries intact and in order, then appends only
    existing, not-already-present standard Homebrew directories in this order:
    `/opt/homebrew/bin`, `/usr/local/bin`, `/opt/homebrew/sbin`,
    `/usr/local/sbin`. A missing or empty inherited `PATH` starts with
    `/usr/bin:/bin:/usr/sbin:/sbin` before the additions.
  - `inherited` passes through the current process `PATH` without modification.
    An unrecognized mode warns and falls back to the inherited behavior.
  - This policy affects only the launched child process. It does not mutate
    CSharpFar's process environment, change detached file associations, initialize
    login-shell configuration, or alter unrelated background processes.
- Make the Application hide/restore the UI around current-console file launches,
  matching the existing command-line execution path.
- When the Windows host terminates because of an unexpected exception, save a
  timestamped diagnostic report containing the exception details next to the
  application executable, so errors occurring during or after a current-console
  command can be investigated after the console closes.
- Preserve the existing shared Enter and double-click open flow.
- Cover launch selection and process start options with unit tests that do not
  start real external programs.
- Demo-mode composition may substitute a disabled shell/launcher implementation
  that keeps the shared command and open flows but returns a clear disabled
  result instead of starting a real external process.

## Non-goals

- Do not implement Far Manager file association tables.
- Do not add a compatibility path for the old Shell-only executable launch.
- Do not redirect external program output into CSharpFar UI widgets.
- Do not run an associated non-executable file in the current CSharpFar console.
- Do not parse arbitrary command-line arguments for files opened from the panel.

## Acceptance criteria

- On Windows, after `set BASE=C:\\Tools` and `set SDK=%BASE%\\dotnet`,
  `echo %SDK%` produces `C:\\Tools\\dotnet`. Assignments may reference
  existing process variables such as `PATH`, `TEMP`, and `USERPROFILE`, and a
  self-reference uses the variable's value before replacement.
- Typed commands still run via the configured shell in the current console and wait
  for exit.
- `ps: Get-Date`, `pwsh: Get-ChildItem`, and `PS: Get-Process` run through
  PowerShell, while `foo: bar`, paths such as `C:\\Tools\\tool.exe`, and commands
  without a registered prefix retain default-shell behavior.
- An explicit shell command that looks like a CSharpFar built-in, for example
  `ps: cd C:\\Temp`, is executed by the selected shell and does not navigate the
  active panel.
- Typed commands and executable panel launches write to the terminal main screen buffer,
  not to the alternate screen buffer used for CSharpFar UI, and start from the visible
  bottom of that main screen buffer without first blanking the visible main viewport.
- Pressing `Ctrl-C` while a current-console child process is running interrupts
  that child process without terminating CSharpFar.
- Windows executable files opened from a panel use current-console process start
  options, do not redirect standard streams, do not create a new window, and
  wait for exit.
- Windows `.bat` and `.cmd` opened from a panel use `cmd.exe /c` with the same
  current console behavior.
- Linux and macOS executable files opened from a panel use current-console process
  start options and wait for exit.
- Non-executable local files use `AssociatedDetached`: system association is
  preserved, panels remain visible, CSharpFar remains interactive, and no
  external output appears in its terminal.
- On Windows, opening an associated file with a console-noisy application such
  as VS Code does not place that application's diagnostics below or over the
  panels.
- On macOS, a non-executable document opens via the system `/usr/bin/open`
  association without hiding the panels, redirecting its output into the
  terminal, or waiting for the opened GUI application to exit; immediate launch
  failures are reported.
- On macOS, `appendStandard` preserves inherited `PATH` entries and adds only
  existing, not-already-present standard Homebrew directories for typed shell
  commands, PowerShell aliases, and executable panel launches. Missing `PATH`
  receives the documented system fallback. `inherited` leaves the child `PATH`
  unchanged; an unknown setting warns and behaves as `inherited`. Neither mode
  modifies the CSharpFar process environment or detached association launches.
- Association launch reports immediate failures clearly, without waiting for a
  detached application to exit.
- Opening executable files hides/restores the CSharpFar UI through the terminal screen
  mode boundary and refreshes panels after the process exits.
- On Unix-like terminals, external commands do not run while the application
  leaves the terminal in raw mode.
- Unit tests verify routing without launching real external programs, including
  Windows extension/PATHEXT detection, Linux/macOS execute-bit detection,
  macOS association command construction, and effective `PATH` selection.
- Unit tests verify Windows and Unix shell command builders preserve complex
  commands and quoted command arguments using the platform-appropriate
  `ProcessStartInfo` command-line API.
- Windows commands whose executable path and arguments require quotes are passed
  intact to `cmd.exe`; spaces do not split the executable path or quoted arguments.
- In demo mode, typed commands and external executable launches do not start a
  real child process and instead fail with a clear demo-mode-disabled result.
- An unexpected Windows-host exception creates a diagnostic report beside the
  application executable with the exception type, message, and stack trace.

## Verification

Manual checks:

1. Run a console `.exe` from a panel and confirm its output appears in the same
   console before panels are redrawn.
2. Run a long-running command such as `ping 127.0.0.1 -t`, press `Ctrl-C`, and
   confirm the child command stops while CSharpFar redraws and continues running.
3. Run a `.cmd` or `.bat` file from a panel and confirm it uses the same console.
4. Open a PDF or JSON document and confirm it uses the system association while
   panels remain usable and the associated application writes no output into
   the CSharpFar terminal.
5. Cause an unexpected application exception and confirm a timestamped
   diagnostic report is created next to the application executable.
6. Run a command whose executable path and final argument both contain spaces and
   are quoted; confirm the executable starts and receives the argument intact.
7. Run `ps: Write-Host "hello world"` and a multi-line PowerShell pipeline; verify
   quotes and line breaks reach PowerShell intact. Temporarily make both
   PowerShell executables unavailable and verify CSharpFar displays an error but
   remains usable.
8. On macOS, run an executable file from a panel and confirm it runs in the
   current console; open a PDF or text document and confirm the system-associated
   application starts while CSharpFar panels remain interactive.
9. On macOS, launch CSharpFar with a reduced or absent `PATH` from Finder or a
   terminal. Under `appendStandard`, confirm available Homebrew directories are
   appended without duplicating existing entries and commands can find installed
   tools. Switch to `inherited` and confirm the child receives the unmodified
   inherited `PATH`. Check that association opening is unaffected.
