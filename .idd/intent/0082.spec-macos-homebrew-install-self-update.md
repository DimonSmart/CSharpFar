# 0082 - macOS Homebrew install and self-update orchestration

## Intent

CSharpFar provides one simple recommended command for first installation and
later updates of the macOS application, plus an **About → Update now** action
when the currently running application can be safely identified as the standard
Homebrew-managed bundle.

Homebrew Cask remains the only package/install mechanism for the GUI
distribution. Neither the installer script nor CSharpFar downloads, unpacks,
checksums, caches, or replaces release archives independently.

## Recommended installer

The repository-owned source is `docs/install-macos.sh`. GitHub Pages publishes
that exact source as:

```text
https://dimonsmart.github.io/CSharpFar/install-macos.sh
```

The recommended command is:

```bash
curl -fsSL https://dimonsmart.github.io/CSharpFar/install-macos.sh | bash
```

The script is idempotent. It accepts macOS only, finds Homebrew from the current
`PATH` and then the standard Apple Silicon and Intel locations, and fails with
installation guidance when Homebrew is absent. It never installs Homebrew
itself.

The script ensures the `dimonsmart/csharpfar` tap exists, runs `brew update`,
and operates only on `dimonsmart/csharpfar/csharpfar-app` with
`--appdir=/Applications`. It never runs an unscoped `brew upgrade`.

A fresh install refuses to overwrite an existing
`/Applications/CSharpFar.app` when the Cask is not installed. Repeated runs
upgrade the Cask or accept the already-current state.

After a successful Homebrew operation the script removes
`com.apple.quarantine` only from `/Applications/CSharpFar.app`, verifies that
the attribute no longer remains, and runs the bundled
`Contents/Resources/csharpfar --version`. Package failure and post-install
quarantine failure are distinct results. A quarantine failure does not roll
back the installed package and reports the exact manual `xattr` command.

The quarantine step is temporary because the application is currently unsigned
and not notarized. Direct manual Homebrew installation may continue to require
the normal Gatekeeper workflow. Once Developer ID signing and notarization are
introduced, this workaround and the corresponding documentation must be
removed.

## Application update abstraction

GitHub release discovery remains the sole responsibility of
`UpdateCheckService`. Homebrew execution, installation detection, quarantine,
and relaunch are owned by a separate `IApplicationUpdateInstaller`
implementation.

Process execution is isolated behind a small testable abstraction that returns
exit code, stdout, and stderr. Dynamic shell command strings are not used;
arguments are passed through `ProcessStartInfo.ArgumentList`.

Windows and Linux retain release checking without Homebrew self-update.

## Availability

**Update now** is offered only when all of the following are true:

1. the OS is macOS;
2. Homebrew is available;
3. the Cask `dimonsmart/csharpfar/csharpfar-app` is installed;
4. the current process is
   `/Applications/CSharpFar.app/Contents/Resources/csharpfar`;
5. the installation uses the standard `/Applications` application location.

A development build, Formula executable, manual copy, second application copy,
or custom-`--appdir` application is not eligible. Those installations retain
**Open release page**.

Availability is structured so diagnostics and tests can distinguish unsupported
platform, missing Homebrew, missing Cask, process mismatch, non-standard
location, and package-query failure without exposing internal enum names in the
normal About UI.

## About and update operation

When GitHub reports a newer version and the updater is available, About shows:

```text
[ Update now ] [ Open release page ] [ Close ]
```

**Update now** is the default action. If self-update is unavailable, About shows
only the existing release-page action.

Starting an update closes About and opens a separate **Updating CSharpFar**
operation dialog. The generic operation-dialog lifecycle is not extended merely
to support updater restarts.

The updater reports high-level stages rather than raw Homebrew output.

## Update sequence

The guarded update sequence is:

1. run `brew update`;
2. query `brew info --cask --json=v2 dimonsmart/csharpfar/csharpfar-app`;
3. compare the Cask version with the expected GitHub release;
4. if Homebrew metadata is older, stop without changing the package and report
   the temporary publication delay;
5. run
   `brew upgrade --cask --no-quit --appdir=/Applications dimonsmart/csharpfar/csharpfar-app`;
6. verify
   `/Applications/CSharpFar.app/Contents/Resources/csharpfar --version` and
   require the installed version to be at least the expected version;
7. remove and verify CSharpFar's quarantine attribute;
8. run `/usr/bin/open -n /Applications/CSharpFar.app`;
9. only after a successful relaunch request does the old application process
   leave its normal run loop.

An already-up-to-date Homebrew package is not an error if the installed bundle
passes version verification.

Homebrew failures leave the running application open. Quarantine failure leaves
the newly installed package in place but suppresses automatic restart and shows
the manual repair command. Relaunch failure does not roll back the package and
leaves the old process available for normal closure.

## Cancellation

Cancellation is allowed before package modification. Once the Homebrew package
operation begins, the UI disables cancellation and does not kill the Homebrew
process. Integrity of the Cask operation takes priority over immediate
cancellation.

## Diagnostics

Updater events use the existing opt-in, in-memory diagnostics contract from
0081 under the `ApplicationUpdate` category. No dedicated updater log file is
created.

Safe diagnostics include availability, Homebrew executable classification,
current-process classification, expected/available/installed versions,
high-level process stages and exit codes, sanitized short stderr, quarantine
result, and relaunch result.

## Security

The Cask name, standard application path, `/usr/bin/xattr`, and
`/usr/bin/open` are fixed constants. Homebrew is resolved once to an absolute
executable path. The updater does not invoke `sh -c` for package operations.

Homebrew Cask remains responsible for architecture selection, immutable release
asset download, and SHA-256 verification.

## Verification

Unit tests use fake process execution and require neither macOS nor Homebrew.
They cover availability classifications, release/Cask publication lag, malformed
Cask metadata, targeted upgrade arguments, installed-version verification,
already-current packages, quarantine outcomes, and relaunch outcomes.

The build validates `docs/install-macos.sh` with `bash -n`. Manual macOS
verification covers fresh install, repeated install/update, manual-copy
collision, release/Cask publication lag, and the complete in-app update/relaunch
path. Apple Silicon is required for routine manual validation; Intel is checked
when suitable hardware or CI is available.
