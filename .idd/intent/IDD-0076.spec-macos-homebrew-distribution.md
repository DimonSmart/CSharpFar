# IDD-0076 - macOS Homebrew distribution specification

## Intent

CSharpFar provides Homebrew as the primary installation and upgrade path on
macOS while continuing to publish transparent self-contained Apple Silicon and
Intel archives through GitHub Releases.

Homebrew exposes both supported usage shapes:

- a Formula for the `csharpfar` terminal command;
- a Cask for the `CSharpFar.app` Finder/Applications bundle.

The Homebrew metadata is derived from release artifacts automatically so a
normal CSharpFar release does not require a separate manual package-maintenance
step.

## Related specifications

- IDD-0064
- IDD-0065
- IDD-0077 - macOS application bundle
- IDD-0082 - recommended installer, quarantine handling and in-app self-update
- IDD-0077 owns .app identity, bundle composition and signing/notarization state;
  this document owns Formula/Cask metadata, artifacts, architecture selection
  and Homebrew package lifecycle, not runtime update orchestration.

## Behavior

The main `DimonSmart/CSharpFar` repository also acts as a custom Homebrew tap.
Because its GitHub repository name does not use Homebrew's `homebrew-<tap>`
convention, users add it with the explicit repository URL:

```bash
brew tap dimonsmart/csharpfar https://github.com/DimonSmart/CSharpFar.git
```

### Command-line Formula

Users who want the terminal command install the Formula:

```bash
brew install dimonsmart/csharpfar/csharpfar
```

The Formula installs the existing self-contained `csharpfar` release binary and
does not require a separately installed .NET runtime.

It supports both currently published macOS architectures:

- Apple Silicon uses `CSharpFar-v<version>-osx-arm64.tar.gz`;
- Intel uses `CSharpFar-v<version>-osx-x64.tar.gz`.

The Formula selects the archive from the current CPU architecture and installs
`csharpfar` into Homebrew's binary path.

The Formula has a Homebrew test that executes `csharpfar --version` and verifies
that the installed executable reports the Formula version.

### Application Cask

Users who want CSharpFar in Applications/Finder install the Cask:

```bash
brew install --cask dimonsmart/csharpfar/csharpfar-app
```

The Cask installs the architecture-matching `CSharpFar.app` produced according
to specification IDD-0077:

- Apple Silicon uses `CSharpFar-v<version>-osx-arm64-app.zip`;
- Intel uses `CSharpFar-v<version>-osx-x64-app.zip`.

The Cask installs only the application bundle. It does not create another
`csharpfar` command, so the Formula and Cask can coexist without competing for
the same Homebrew binary path.

The application's bundle identity and signing/notarization status are owned
by `IDD-0077`; Gatekeeper handling and any narrowly scoped temporary
quarantine workaround belong exclusively to `IDD-0082`. The Cask does
not define a competing installer or post-install policy.

### Upgrade and removal

Formula users upgrade through normal Homebrew commands:

```bash
brew update
brew upgrade dimonsmart/csharpfar/csharpfar
```

Cask users may upgrade directly through Homebrew:

```bash
brew update
brew upgrade --cask dimonsmart/csharpfar/csharpfar-app
```

The recommended repeatable installer, About self-update eligibility and
guarded in-app update sequence are owned by `IDD-0082`, which uses this
same Cask and does not define another package artifact or update channel.

## Homebrew metadata publication

`Formula/csharpfar.rb` is generated from a published GitHub Release rather than
edited manually.

`eng/packaging/update-homebrew-formula.ps1` accepts the release version and the
release `SHA256SUMS.txt`. It requires checksums for both macOS CLI archives and
writes a Formula containing immutable versioned release URLs and matching
SHA-256 hashes.

`Casks/csharpfar-app.rb` is also generated from a published release. It is not
created until a release contains both architecture-specific app ZIP assets.
`eng/packaging/update-homebrew-cask.ps1` requires checksums for both app archives
and writes architecture-aware Cask metadata.

The `Homebrew` GitHub Actions workflow refreshes both metadata files after a
successful `Release` workflow. It resolves the release tag from the completed
release run, downloads `SHA256SUMS.txt`, generates and syntax-checks Formula and
Cask metadata, and commits the updated distribution metadata to `main`.

`eng/packaging/homebrew-current-tag.txt` records the release currently targeted
by Homebrew metadata. A change to this file also triggers the Homebrew workflow,
which provides a deterministic bootstrap/recovery mechanism for an
already-published release. The workflow can additionally be run manually with
an explicit tag.

Homebrew metadata commits are distribution metadata updates. They do not create
another release because the Release workflow is tag-triggered.

## Architecture and patterns

GitHub Releases remain the source of binary history and checksums. Homebrew is a
thin installation layer over those release artifacts rather than a second build
pipeline.

The Homebrew workflow must not rebuild macOS binaries or application bundles. It
consumes only a successfully completed CSharpFar Release and its checksums. The
Release workflow remains responsible for compilation, tests, macOS terminal
verification, bundle assembly, packaging, and release publication.

A separate `DimonSmart/homebrew-tap` repository is not required for the current
distribution model. Homebrew supports custom taps with an explicit Git URL, so
keeping Formula, Cask, and product source in one repository removes
cross-repository credentials and synchronization from the release path.

A dedicated `homebrew-*` repository may be introduced later if the one-command
Homebrew shorthand becomes more valuable than the simpler single-repository
maintenance model. Such a move must preserve the same versioned assets,
architecture selection, SHA-256 verification, and automatic update behavior.

## Non-goals

- Homebrew does not build CSharpFar from source during installation.
- Homebrew does not replace GitHub Releases as the release artifact source.
- Homebrew does not add a .NET runtime dependency for packaged releases.
- The Homebrew workflow does not build or modify macOS application bundles.
- The Cask does not replace the CLI Formula.
- Code signing and Apple notarization are separate distribution-hardening work.

## Acceptance criteria

- README presents both Homebrew installation shapes clearly.
- A macOS user can add the CSharpFar tap once.
- Formula installation selects `osx-arm64` on Apple Silicon and `osx-x64` on
  Intel and exposes the `csharpfar` command.
- Cask installation selects the matching `*-app.zip` asset and installs
  `CSharpFar.app`.
- Formula and Cask can coexist.
- Packaged Homebrew installation does not require the .NET runtime.
- Formula and Cask metadata contain SHA-256 verification for both macOS
  architectures.
- A successful Release workflow is followed by automatic Homebrew metadata
  refresh on `main`.
- Metadata generation fails clearly if any required architecture checksum is
  absent.
- A previously published compatible release can be used to refresh Homebrew
  metadata through the tracked current-tag file or manual workflow dispatch.
- Documentation includes install, upgrade, uninstall, version verification, and
  self-test commands where applicable.
- The Cask remains the single Homebrew GUI package used by the installer and
  updater governed by `IDD-0082`; their eligibility, quarantine and relaunch
  behavior are not independently specified here.

## Verification

- Validate generated Formula and Cask files with Ruby syntax checking.
- Verify architecture URLs and checksums correspond to the same release version.
- On Apple Silicon, install the Formula and run `csharpfar --version`.
- On an Intel runner or Intel Mac, install the Formula and run
  `csharpfar --version`.
- Install the Cask on macOS and confirm `CSharpFar.app` appears in Applications.
- Launch the installed app and confirm it opens CSharpFar's own terminal window
  with the application identity required by IDD-0077.
- Run `csharpfar --self-test` separately as a Formula diagnostic check.
