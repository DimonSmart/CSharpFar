# IDD-0088 - Deterministic demo recording specification

Related:
- IDD-0001 (product-wide intent)
- IDD-0067 (committed UI rendering and overlays)
- IDD-0087 (isolated Demo Mode runtime)
- IDD-0032 / IDD-0046 (viewer and editor workflows)
- IDD-0010 (file-operation workflows)

## Goal and ownership

Produce reproducible README and documentation demonstrations using the real
CSharpFar UI, input model and isolated Demo Mode filesystem. This document
exclusively owns scripted recording, rendered-frame capture, supported
workflows and media artifacts; `IDD-0087` owns sandboxing and runtime safety.

`docs/demo.md` is the human-facing execution guide, not a competing
normative specification.

## Recording contract

- The supported recorder is product-owned (`CSharpFar.DemoRecorder`). It
  executes source-controlled scenarios against the in-memory demo fixture,
  through the application's actual input and rendering paths.
- Use a deterministic scripted runner with a fake or recording console
  driver capable of supplying keyboard/UI input and capturing committed
  application frames. Capture what the application actually rendered, not
  independently drawn mock screens.
- Scenarios may navigate panels and exercise visible viewer/editor flows,
  create-folder and create-file dialogs, copy/move and rename flows, delete
  flows, and the visible delete confirmation surface.
- Recording workflows should prefer the real dialogs, confirmations and
  editor/viewer interactions over hidden internal shortcuts when illustrating
  a user workflow. A recording does not require manual keystrokes outside
  its scripted runner.
- The runner may export committed frames as screenshots and produce GIF or
  video artifacts (including PNG, GIF and MP4) from the same UI presentation.
  A fake/recording driver may also provide evidence for visual regressions
  without changing observable application behavior.
- Recordings run entirely through the isolated runtime owned by
  `IDD-0087`. The recorder does not introduce another live filesystem,
  credential store or network access path. Fixture and user-data safety
  obligations are defined and verified solely under `IDD-0087`.
- Do not use an external browser-hosted recording pipeline or terminal-video
  DSL (including the former VHS workflow) as the supported source of
  documentation recordings. Such tools must not become required runtime
  dependencies or a second source of UI behavior.
- Asset generation is an explicit documentation workflow; it is not required
  during the default application build, test or release publish pipeline.

## Supported repository workflow

The canonical fixture, scripted scenario and manual runner entry point are
documented in `docs/demo.md` (currently under `docs/demo/filesystem`,
`scripts/demo/readme-demo.json` and `scripts/demo/generate-demo-assets.ps1`).
The README presentation uses the resulting product-owned visual artifacts.
Exact invocation examples and output locations are documentation concerns,
not independent product behavioral contracts.

## Non-goals

- A second file-manager implementation or browser rendering system.
- Recording from the user's normal filesystem or persistent credentials.
- Turning documentation asset regeneration into a mandatory build step.
- Redefining transactional frame acceptance (`IDD-0067`) or Demo Mode
  filesystem access rules (`IDD-0087`).

## Acceptance criteria

1. A checkout can regenerate README demo artifacts from a source-controlled
   fixture and scripted scenario without a browser-hosted recorder.
2. Scenario execution reaches real UI surfaces for navigation, viewer,
   editor, file creation, copy, move, rename and delete confirmation.
3. The capture represents committed CSharpFar UI frames and supports
   screenshots plus GIF/video artifacts without separate mock rendering.
4. Recording uses the isolated session and source boundary from
   `IDD-0087`, without a separate safety or persistence policy.

## Verification

Run a representative scripted demo against the in-memory fixture. Confirm
that the resulting committed frames include actual viewer, editor, create,
copy, move, rename and delete confirmation UI and that at least one
screenshot matches the displayed committed frame. Verify exported media
artifacts can be produced and recorder input stays within the `IDD-0087`
session. Fixture and configuration isolation tests belong to `IDD-0087`;
renderer commit semantics belong to `IDD-0067`.
