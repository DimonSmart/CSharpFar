## Goal

Linux/macOS production input uses raw VT as the transport and compatibility
baseline. When the attached terminal stack supports the Kitty keyboard
protocol, CSharpFar negotiates enhanced keyboard reporting and consumes
enhanced CSI-u events through the same production input pipeline. Unsupported
or unconfirmed terminals continue to use legacy VT behavior. The application
continues to consume the shared, protocol-neutral `ConsoleInputEvent` model
through `IConsoleDriver`; Windows input behavior is unchanged.

## Production input behavior

The ANSI terminal console driver owns one internal input reader that:

- enters the current platform's raw terminal mode;
- reads keyboard and mouse input from the terminal byte stream;
- parses ordinary and UTF-8 text, Enter, Tab, shifted Tab, Backspace,
  standalone Escape, arrows, navigation keys, F1-F12, CSI modifiers,
  Alt-prefixed text, and Alt-prefixed VT keys;
- recognizes Kitty/CSI-u keyboard events before legacy keyboard fallback,
  preserving key identity, modifiers, and terminal-provided associated text;
- preserves associated text as a complete UTF-16 string, including multiple
  Unicode code points, combining characters, non-BMP code points, and valid
  text-only events with key code zero;
- parses SGR mouse button press, release, wheel, button-motion, and unpressed
  pointer-motion packets into zero-based viewport-relative
  `MouseConsoleInputEvent` coordinates; unpressed movement has no button and
  does not reuse prior pressed-button state;
- polls terminal size and emits `ConsoleResizeInputEvent` when it changes;
- on Linux, may additionally use evdev to detect standalone Shift press and
  release events that are not delivered through the terminal byte stream;
- ignores malformed mouse packets and handles unknown keyboard sequences
  without terminating the application.

The legacy `Console.ReadKey` Unix backend is not supported. The
`CSHARPFAR_UNIX_INPUT` environment variable does not select production input
behavior. Kitty support is progressive enhancement over the same raw-VT byte
stream; it is not a second input backend.

## Kitty keyboard protocol

CSharpFar detects support through protocol negotiation, not through `TERM`,
`TERM_PROGRAM`, terminal-emulator names, or allowlists. Detection sends the
Kitty current-flags query (`CSI ? u`) together with Primary Device Attributes
as a sentinel. A Kitty flags response means support is available; a PDA response
without a Kitty response means unsupported; an inconclusive timeout means
unknown. Unsupported and unknown states fall back to legacy VT without startup
failure.

Production requests progressive-enhancement flags `25`:

- disambiguate escape codes (`1`);
- report all keys as escape codes (`8`);
- report associated text (`16`).

Activation pushes the current keyboard state with the requested flags, then
queries the active flags and enables enhanced input only when all required bits
are confirmed. Failed or partial activation restores the previous keyboard
state. Terminal protocol responses are control traffic and never become
application key events; unrelated bytes observed during negotiation are replayed
to the normal parser.

Main and alternate screens have independent Kitty keyboard-mode stacks. Screen
changes therefore use the order: deactivate/pop on the old screen, switch the
terminal screen, then activate/push on the new screen. Repeated enable, disable,
screen-change, suspend, restore, and dispose operations are idempotent and do
not pop a stack entry that CSharpFar did not push.

Malformed CSI-u packets do not become synthetic Escape key presses and do not
insert garbage. Modifier-only enhanced events do not replace the Linux evdev
Shift tracker and must not create sticky modifier state. Recognized CSI-u input
may still be parsed when the protocol was not negotiated by CSharpFar, because
some terminal stacks emit compatible extended sequences independently.

## Linux Shift-only tracking

On Linux, production input may create an optional evdev modifier tracker that
observes only left and right Shift key state from readable `/dev/input/event*`
devices. When available, pressing Shift alone emits
`ModifierKeyConsoleInputEvent(ConsoleModifiers.Shift)` and releasing the final
held Shift emits `ModifierKeyConsoleInputEvent(default)`. These events update
the function-key bar layer without executing commands or inserting command-line
text.

The tracker must remain narrowly scoped:

- it activates only when `OperatingSystem.IsLinux()` is true;
- it reads only readable Shift-capable evdev devices;
- it ignores every event except left and right Shift key down/up;
- it does not store, log, or expose raw keyboard input;
- it tracks left and right Shift independently so releasing one held Shift does
  not clear the layer while the other Shift remains held;
- duplicate effective Shift states do not produce duplicate modifier events.

Evdev access is optional. Missing `/dev/input`, unreadable event devices,
permission denied, unsupported devices, and initialization failures must not
prevent startup or normal stdin/ANSI input. In those cases Shift-only tracking
is unavailable, while ordinary terminal input, modified function-key escape
sequences, resize, and mouse behavior continue to work.

The input reader suspends evdev modifier tracking while child-process console
mode is active and resumes it when application input mode is restored, matching
raw terminal lifetime.

## Diagnostics

The terminal diagnostics command reports runtime and input environment details:

- OS description, OS architecture, process architecture, framework, and
  platform flags for Windows, Linux, and macOS;
- Unix effective user id, root status, sudo environment variables, and whether
  the process appears to be running via sudo;
- Windows elevated/admin status when available, or an explicit not-applicable
  or not-checked value;
- console driver, input backend, and mouse tracking status;
- keyboard protocol separately from the backend, including requested state,
  support status, requested flags, confirmed flags, active state, active
  terminal screen, and fallback reason;
- modifier tracking backend, platform support, enabled status, whether
  Shift-only can currently be tracked, status, failure reason, and evdev device
  discovery summary.

Diagnostics must distinguish theoretical platform support from the tracker
being enabled and from Shift-only tracking being currently usable. When evdev
tracking is unavailable, diagnostics explain the reason without recommending
sudo as a normal requirement.

`ReadKey` skips mouse and resize events until it receives a key event so callers
that require a key keep their existing contract.

## Terminal mode lifetime

Production mouse input uses xterm all-motion tracking (`1003`) and SGR mouse
encoding (`1006`) while the application alternate screen is active, so explicit
hover interaction can receive unpressed pointer movement. Drag and button
semantics remain distinct from passive movement.

Raw keyboard mode and application mouse tracking have separate lifetimes. While
the application alternate screen is active for the `Panels` workspace, mouse
tracking uses `1003 + 1006`. When CSharpFar switches to the main screen for
`HiddenCommandLine`, raw keyboard input remains active but mouse modes `1000`,
`1002`, `1003`, and `1006` are disabled so the terminal can perform native text
selection and copy. Returning to the application screen restores `1003 + 1006`.

Entering child-process console mode first restores any CSharpFar keyboard
protocol state, then suspends raw input and mouse tracking and returns to the
main screen. The main-screen transition while application input is suspended
must not re-activate Kitty mode, so child processes never inherit CSharpFar's
enhanced keyboard state. Restoring application input re-enters raw mode, restores
the application screen as required by the workspace, re-activates the keyboard
protocol on that screen when supported, and preserves the mouse-tracking request
implied by the current screen mode rather than unconditionally enabling mouse
reporting. Repeated mouse/keyboard toggles, suspend, restore, and disposal
operations are safe.

Disposal and error paths restore the original terminal input mode and disable
mouse modes `1000`, `1002`, `1003`, and `1006`.

The combined input laboratory is the shared Linux/macOS interactive input
diagnostic. It exercises the production keyboard profile (flags `25`) by
default and reports raw bytes, parsed key, modifiers, associated text, parser
kind, and protocol. Its standard Enter stage covers plain Enter, Shift+Enter,
Ctrl+Enter, and Ctrl+Shift+Enter. Modifier press/release lifecycle is not a
requirement of the production-profile test because production intentionally
does not request event-type reporting.

## Acceptance Criteria

- `AnsiTerminalConsoleDriver` delegates Unix production input to one raw VT
  input reader through the internal input-reader abstraction.
- Unix production input does not use `Console.ReadKey` or backend-selection
  environment variables; raw VT remains the transport, while unsupported or
  unconfirmed Kitty negotiation falls back to legacy VT parsing.
- Kitty support is determined by protocol negotiation rather than terminal name.
- Production requests flags `25`, confirms the active bits after activation,
  and restores the prior state if confirmation fails.
- Terminal negotiation responses never reach application keyboard handling, and
  unrelated bytes read during negotiation are preserved.
- Production parsing accepts enhanced CSI-u and legacy VT through one input
  reader, with SGR mouse handling retained.
- Terminal-provided associated text is preserved exactly, including
  multi-codepoint, combining, non-BMP, and key-code-zero text input.
- Malformed CSI-u packets do not create application Escape events.
- Raw VT keyboard and SGR mouse input produce only standard
  `ConsoleInputEvent` values.
- On Linux with readable Shift-capable evdev devices, standalone Shift press
  and release produce `ModifierKeyConsoleInputEvent` values.
- When Linux evdev access is missing or denied, production input continues
  without Shift-only tracking and without startup or input-read exceptions.
- Evdev tracking ignores non-Shift events and does not log raw keyboard input.
- Mouse coordinates are zero-based and viewport-relative on Linux and macOS.
- Production application-screen mouse tracking uses `1003 + 1006`, including
  unpressed pointer movement represented without a mouse button.
- Switching from the application screen to the main screen disables mouse
  tracking without leaving raw keyboard mode.
- Switching back to the application screen re-enables `1003 + 1006` mouse
  tracking.
- Raw mode and mouse tracking are disabled for child processes; restoring input
  respects the current screen's mouse-tracking state.
- Kitty keyboard mode is popped before child-process handoff, is not activated
  during the suspended alternate-to-main transition, and is restored only after
  CSharpFar resumes application input.
- Main and alternate screen keyboard stacks use pop-before-switch and
  push-after-switch ordering.
- Disposal and input error paths restore terminal and mouse modes.
- Child-process console mode suspends optional evdev modifier tracking and
  restores it afterwards.
- Unknown keyboard sequences and malformed mouse packets do not crash the UI
  or write diagnostic text into it.
- Resize is represented by `ConsoleResizeInputEvent`, not a synthetic key.
- Linux and macOS use separate native terminal-mode implementations appropriate
  to their respective `termios` ABIs; shared ANSI parsing does not select an OS
  implementation itself.
- macOS does not create the Linux evdev modifier tracker. Ordinary keyboard,
  ANSI/Option input, mouse, resize, and terminal restoration remain available.
- `--check-terminal` and `--check-terminal --input-lab` remain available on
  both Linux and macOS, use the same shared Input Lab implementation, and the
  lab uses production profile `25` by default; old overlapping input experiment
  commands are not public diagnostics.
- Terminal diagnostics include OS/runtime, privilege/sudo/elevation,
  input-backend, mouse-tracking, keyboard-protocol, and modifier-tracking
  status, and distinguish requested/support/confirmed/active keyboard state.
- Parser tests retain coverage for text, UTF-8, standalone Escape, navigation,
  F1-F12, modified keys, Alt-prefixed input, mouse buttons, release, wheel,
  drag and passive motion, modifiers, and coordinate conversion.
- Input-reader lifecycle tests cover raw mode, independent mouse tracking,
  suspension, restoration, optional modifier-tracker suspension, repeated
  lifecycle calls, and idempotent disposal.

## Verification

Automated verification covers independent mouse tracking toggles without raw
mode transitions and restoration while mouse tracking is intentionally disabled.

Manual verification in Windows Terminal plus WSL runs the Linux host without
`CSHARPFAR_UNIX_INPUT` and checks keyboard navigation, Enter, Escape, arrows,
F-keys, mouse buttons, wheel, drag, resize, child-process entry/return, hidden
workspace native text selection, passive hover interaction, and clean terminal
restoration. On Linux with
readable evdev devices, hold and release Shift alone and verify the bottom
function-key bar changes to and from the Shift layer. On Linux without evdev
access, verify the diagnostics report why Shift-only tracking is unavailable and
the app otherwise works normally. Run `--check-terminal` and
`--check-terminal --input-lab` for focused terminal diagnostics. In Input Lab,
verify Enter, Shift+Enter, Ctrl+Enter, Ctrl+Shift+Enter and the requested versus
confirmed flags. On macOS, run the executable inside the application bundle
directly from a real terminal/TTY, verify enhanced negotiation when supported,
verify fallback in a legacy terminal, and confirm raw mode can be entered and
restored, hidden workspace text can be selected and copied with the terminal
mouse, and returning to panels restores normal application mouse interaction
without the Linux modifier tracker.
