# IDD-0080.spec-file-usage-panel

## Intent

CSharpFar provides a persistent File Usage panel for diagnosing whether the
current local file is in use, which local processes own it, which ordinary file
operations are currently restricted, and—after an explicit confirmation—whether
an eligible owner process can be terminated to release the file.

## Behavior

File Usage is a panel mode separate from Quick View. Its command toggles the
opposite panel between File Usage and its preceding ordinary mode, using a
non-conflicting binding. While it is open, the active file panel remains
navigable and File Usage follows its current item.

For a local ordinary file, the panel reports `Free`, `In Use`, or `Blocked`.
`Free` means no local owner and no detected sharing restriction. `In Use` means
one or more local owners exist but read, write, delete, and rename are allowed.
`Blocked` means at least one of those operations is blocked. Each operation is
shown independently as allowed, blocked, or unknown; unsupported or
indeterminate checks must not be represented as allowed. The panel may report a
blocked network file with no local owner and explain that a remote machine or
server could own the lock.

The panel displays an inspect-in-progress state without blocking input, and
shows the most recent valid result until a replacement is available when
practical. Moving the active-panel cursor, refreshing, closing the mode,
switching modes, or disposing the owner cancels obsolete inspection. A late
result must never change a later File Usage view. Refresh performs a fresh
inspection. Process selection supports keyboard and shared routed pointer
interaction; resizing preserves a valid selection or normalizes it when its
entry disappears.

File Usage presents diagnostics in an ordered visual hierarchy: the overall
state and per-operation states come first, followed by any operation failure
reason, owners, and details for the selected owner. A blocked state is visually
more prominent than an allowed state, including the overall state and every
blocked operation. An operation's error message is a separate, labelled reason
block beneath that operation, rather than a suffix of the operation row. The
reason wraps at word boundaries within the visible panel width and preserves an
indent on continuation lines; only an individual unbreakably long token may be
ellipsized. On constrained height, state, operations, their reasons, and the
start of the owners list take precedence over selected-owner details. Long
detail values, especially paths, may be ellipsized instead. The selected owner
is distinctly highlighted and its name and PID remain readable. Detail labels
are visually subordinate to their values and to failure reasons. All such
styling comes from the active palette, not renderer-local color choices.

Long single-line owner names, paths, and other ellipsized detail values may be
revealed through the shared hover text behavior while the pointer remains over
their own text region. Multi-line failure reasons retain their wrapping behavior
and are not hover-revealed.

When a selected owner is eligible for Unlock, the bottom action bar advertises
`Ctrl+U Unlock owner`; it does not advertise that action when Unlock is
unavailable. This hint is separate from the diagnostic body and neither changes
the existing shortcut nor its confirmation and release behavior.

Each discovered owner is selectable and shows available process name, PID,
executable path, start time, application or service classification, service
name, restartability, and metadata availability. Inaccessible metadata does not
hide the owner or invalidate other results. Enter changes no process state.

Unlock is available only for a selected eligible non-service owner and always
requires a confirmation that identifies the process and warns about unsaved
work. It uses process identity including PID and start time, never terminates
CSharpFar itself, rejects stale identities, and reports already-exited or denied
outcomes clearly. It does not close foreign handles. After every release
attempt, the panel performs a new inspection and makes remaining owners clear.
Service stopping and automatic process restart are unavailable in this version.

The Windows MVP supports only ordinary local files. Non-local sources,
archives, virtual panels, remote providers, and directories explain why they
cannot be inspected. Sharing-violation failures during delete, move, or rename
may open File Usage for the affected path. Demo sessions do not inspect or
terminate real system processes.

## Durable Architecture And Constraints

File-usage diagnostics are a distinct platform-service responsibility, separate
from file operations and file metadata. Shared application and UI code consume
a platform-neutral file-usage snapshot and release contract; platform selection
remains in platform composition rather than scattered OS checks. Unsupported
hosts provide an explicit unavailable result so future Linux and macOS support
can be added without changing application or UI semantics.

Windows owner discovery uses the documented Windows Restart Manager API and is
encapsulated in the Windows platform implementation. The product does not use
external utilities, WMI, undocumented NT handle enumeration, or direct foreign
handle closure. Windows access probes determine observable sharing conflicts
without changing file content, deleting, or renaming the target.

Owner metadata and safe termination reuse the product's common process identity
and metadata semantics, including PID-reuse protection, rather than creating an
independent process model.

## Non-Goals

- Forced closure of foreign handles or kernel-handle enumeration.
- Recursive directory lock inspection, remote SMB owner discovery, or background
  monitoring of all panel files.
- File-usage support for SFTP, FTP, archive, virtual, or other remote sources.
- Windows service management, automatic restart, or automatic unlock.
- Linux or macOS file-usage implementations in the Windows MVP.

## Acceptance Criteria

1. On Windows, a user can toggle File Usage for the current local file while
   continuing to navigate the active file panel.
2. The panel distinguishes Free, In Use, and Blocked and shows independent
   read, write, delete, and rename results, including Unknown where necessary.
3. It displays locally discovered owners and all available process or service
   details without failing the entire view when one owner's metadata is denied.
4. Cursor movement, refresh, closing, mode switching, and disposal leave the UI
   responsive and prevent stale inspection results from being displayed.
5. The user can select an owner, refresh the diagnostic, and request Unlock;
   Unlock is confirmed, PID-reuse safe, never targets CSharpFar, and refreshes
   the diagnostic afterward.
6. Unsupported sources, directories, unsupported hosts, access failures,
   vanished files, partial results, and unavailable process metadata are
   understandable and do not crash the application.
7. File-usage diagnostics remain platform-neutral outside the Windows platform
   boundary, which uses only documented Restart Manager owner discovery.
8. Delete, move, and rename sharing violations can lead the user to File Usage
   for the affected local file.
9. A blocked operation with a long diagnostic message displays a labelled,
   word-wrapped reason without losing ordinary words to right-edge clipping;
   blocked states and the selected owner are visually distinct from secondary
   details in every supported palette.
10. File Usage advertises `Ctrl+U Unlock owner` in the bottom action bar exactly
    when Unlock is available, while preserving existing keyboard and pointer
    owner interaction and Unlock confirmation behavior.
11. Hovering a truncated single-line owner or detail value can reveal its full
    value without changing selection or actions; wrapped failure reasons remain
    non-animated.

## Verification

Automated coverage verifies Windows owner-discovery session lifetime, empty,
single-owner, multiple-owner, resizing-result, cancellation, native-error, and
partial-metadata cases without requiring unrelated real processes. It verifies
access probes against unrestricted, restrictive, and exclusive sharing modes by
their platform error semantics.

Automated coverage verifies cancellation and stale-result rejection across item
changes, refresh, mode changes, and disposal; selection normalization after
resize or an owner exit; and release safety for self, stale, exited, denied, and
eligible processes. It also verifies that a release followed by inspection
accurately retains any remaining owner.

Manual verification covers the File Usage toggle and restoration, process
selection by keyboard and mouse, confirmation and refresh after Unlock, an
elevated or inaccessible owner, a network-file restriction with no local owner,
and the explanatory unsupported-source and directory views. It also covers a
long blocked-operation message at normal and narrow widths, multiple owners,
an eligible and an ineligible Unlock selection, a long owner path, and a short
panel height where the failure reason remains visible ahead of secondary owner
details.
It also covers hover reveal of a truncated owner or detail value and confirms
that a wrapped failure reason does not animate.
