# IDD-0084 - Embedded macOS terminal engine

Type: ADR
Status: Accepted

Related:
- IDD-0064
- IDD-0077
- IDD-0082

## Context

The previous CSharpFar.app launcher delegated its window to Kitty or
Terminal.app, so the desktop identity belonged to another program. A native
macOS application requires a terminal view, a real controlling PTY, enhanced
keyboard reporting, and a reliable native process boundary without duplicating
the shared file manager. The CLI artifact must remain unchanged.

## Options evaluated

- **SwiftTerm (AppKit + LocalProcessTerminalView):** macOS embedding, forkpty,
  VT/alternate-screen, resize, clipboard, mouse, Unicode/IME and Kitty keyboard
  protocol handling are available. It is MIT licensed and supports macOS 11+.
- **libghostty:** powerful terminal engine with native macOS rendering and
  enhanced keyboard support, but the embedding C API has not yet been versioned
  and integration/distribution would require additional Zig/native toolchain
  maintenance.
- **Custom AppKit terminal:** would duplicate mature VT parsing, renderer,
  keyboard and input-method functionality, creating a large maintenance burden.

## Decision

Use **SwiftTerm v1.14.0** as an explicitly pinned SwiftPM dependency. Build it
on each native macOS release runner and package the resulting Swift executable
and SwiftPM resources inside CSharpFar.app. Keep the existing portable
self-contained .NET CLI unchanged under Contents/Resources/csharpfar.

The AppKit host owns one NSWindow, its application identity and menu, and a
LocalProcessTerminalView. The latter uses forkpty to give the C# process a
controlling terminal and separate session. SwiftTerm interprets its output,
delivers interactive keyboard, IME and pointer input, and forwards PTY resizing.
The C# process continues to own all panels, editor, file operations, settings,
external commands and safe-exit prompts.

The bundle launcher runs the CLI directly in an attached terminal or for
no-window diagnostic arguments. Other no-TTY bundle invocations start the
AppKit host with the original arguments. Kitty and Terminal.app remain
independent and are not touched.

## Consequences and validation limits

- The SwiftPM dependency is fetched at build time, not at first user launch.
- macOS build agents are needed for the native application package; CLI builds
  are unaffected.
- Reuse SwiftTerm keyboard negotiation rather than reporting unsupported
  protocol modes as available.
- Keep host-specific tests to packaging, process lifetime, input and resize
  boundaries; existing .NET tests guard shared behavior.
- The macOS GUI acceptance matrix (Dock activation, text input/IME,
  modifiers, child interruption and update-relaunch) requires a WindowServer
  session. Repository-only changes and headless CI do not close manual
  acceptance; record it explicitly rather than claiming full verification.
