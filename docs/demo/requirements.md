# ТЗ на автоматическое создание и запись демо-ролика

## Назначение

Нужно реализовать проектовый механизм автоматической записи демо-ролика
работы CSharpFar с использованием `demo`-режима программы.

Результат должен собираться детерминированно из исходников репозитория без
зависимости от внешних browser-hosted recorder-ов и без доступа сценария к
реальной файловой системе пользователя как к live-состоянию.

## Цель

Система должна по сценарию:

- запускать CSharpFar в `demo`-режиме;
- подавать приложению последовательность пользовательских действий;
- снимать реальные визуальные кадры интерфейса;
- собирать из кадров screenshot, GIF и MP4;
- гарантировать, что все изменения происходят только внутри импортированного
  in-memory demo snapshot;
- оставлять физический fixture и обычную пользовательскую конфигурацию
  неизменными после завершения записи.

## Основание

`demo`-режим уже даёт нужную изоляцию:

- fixture читается один раз на старте;
- runtime-состояние файловой системы существует только в памяти;
- все мутации исчезают после завершения сессии;
- shell, external launch и built-in network providers отключены.

Это делает `demo`-режим единственным поддерживаемым источником данных для
автоматического демо-ролика.

## Почему не VHS

Предыдущий вариант с VHS считается неподходящим как поддерживаемое решение,
потому что он:

- зависит от внешнего browser-hosted terminal-video стека;
- требует сторонние runtime-зависимости вне продукта;
- чувствителен к системным библиотекам, шрифтам, окружению Linux/WSL и
  особенностям headless browser rendering;
- смешивает продуктовую проблему записи демо с проблемами внешней
  инфраструктуры;
- затрудняет детерминированную отладку, так как причина сбоя часто лежит
  вне CSharpFar;
- не использует напрямую уже существующую внутреннюю модель ввода и рендера
  приложения.

Поддерживаемое решение должно быть продуктовым и опираться на собственный
input/render pipeline CSharpFar.

## Область работ

Нужно создать внутренний demo-recorder, который использует:

- `demo`-fixture из `docs/demo/filesystem/`;
- сценарий пользовательских шагов;
- application input model;
- fake или recording console driver;
- frame capture из committed screen state;
- постобработку кадров в PNG/GIF/MP4.

## Вне области работ

На первом этапе не требуется:

- запись реального окна терминала через ОС;
- поддержка VHS, `ttyd` или browser automation;
- интерактивный ручной recorder;
- внедрение новой пользовательской команды `PrintScreen` в продуктовый UI;
- изменение существующих тестов на визуальные snapshot-тесты.

## Функциональные требования

### 1. Источник данных

- Recorder всегда работает только против `csharpfar --demo <fixture>`.
- Канонический fixture хранится в `docs/demo/filesystem/`.
- Recorder не должен читать runtime-состояние из физического fixture после
  завершения импорта demo snapshot.

### 2. Сценарий записи

- Сценарий описывает последовательность шагов уровня пользователя:
  запуск, навигация, просмотр, редактирование, копирование, переименование,
  вызов help, завершение.
- Сценарий должен выражаться в проектовом формате, контролируемом из
  исходников репозитория.
- Сценарий должен уметь задавать:
  - input events;
  - ожидания по экрану или по committed frame state;
  - точки съёмки screenshot;
  - точки задержки между шагами;
  - завершение записи.

### 3. Подавание ввода

- Recorder должен отправлять в приложение input events через ту же модель,
  которую приложение использует в runtime и integration tests.
- Поддерживаемые действия должны покрывать как минимум:
  - Enter;
  - Tab;
  - стрелки;
  - Escape;
  - function keys и их нужные модификаторы;
  - при необходимости текстовый ввод.

### 4. Захват кадров

- Кадры должны сниматься из committed screen state приложения, а не через
  внешний screenshot окна.
- Захват должен отражать реальный визуальный результат рендера CSharpFar.
- Кадр должен содержать:
  - символы;
  - цвета;
  - фон;
  - видимый layout;
  - состояние курсора, если оно должно быть показано в артефакте.

### 5. Форматы артефактов

- Recorder должен уметь сохранять:
  - канонический PNG screenshot;
  - GIF-анимацию;
  - MP4-видео.
- GIF и MP4 должны строиться из одного и того же набора кадров.
- `artifacts/demo/` должен оставаться директорией generated output.

### 6. Детерминизм

- Один и тот же commit и один и тот же fixture должны давать воспроизводимый
  результат записи.
- Внешние системные шрифты, браузеры и web-terminal bridge не должны быть
  частью обязательной цепочки генерации.
- Локальная генерация и CI должны использовать один и тот же продуктовый
  recording path.

### 7. Контроль изоляции

- После записи physical fixture должен оставаться byte-for-byte неизменным.
- После записи обычные пользовательские settings, history и credentials не
  должны быть изменены.
- Если сценарий или recorder пытается выйти за границы demo-only режима,
  генерация должна завершаться ошибкой.

## Нефункциональные требования

### Надёжность

- Ошибки сценария должны приводить к диагностируемому падению с указанием
  шага, ожидания и фактического состояния кадра.

### Поддерживаемость

- Сценарии и recorder должны быть понятны из кода репозитория без знания
  внешних DSL и внешних runtime-стеков.

### Минимум внешних зависимостей

- Допустимы только утилиты финальной сборки артефактов, например `ffmpeg`,
  если они не участвуют в логике управления приложением и захвата кадров.
- Захват кадров и управление приложением должны оставаться внутри продуктового
  кода.

## Архитектурные требования

- Recorder должен использовать существующую модель рендера и абстракции
  console driver.
- Предпочтительный путь: отдельный recording driver или reuse
  `FakeConsoleDriver` с возможностью экспорта committed frame в raster image.
- Логика сценария записи не должна быть зашита в README или внешний tape DSL.
- Механизм записи должен быть пригоден для повторного использования в:
  - документации;
  - ручной регенерации demo assets;
  - будущих visual evidence tests.

## Дополнительное требование на будущее

Использование fake screen driver должно открывать путь к сохранению реальных
визуальных screenshot-артефактов, которые можно прикладывать к тестам как
evidence rendered UI state.

На этом этапе сами тесты менять не требуется, но recorder и frame-capture
должны проектироваться так, чтобы такой путь не был заблокирован.

## Ожидаемый сценарий README demo

Минимальный сценарий должен показывать:

- старт приложения в `demo`-режиме;
- двухпанельную навигацию;
- просмотр файла;
- редактирование файла;
- copy;
- rename;
- built-in help;
- корректное завершение приложения.

## Локальный запуск

Для разработчика должна существовать одна поддерживаемая команда
локальной генерации demo assets из репозитория.

Эта команда должна:

- подготавливать runtime приложения;
- запускать recorder;
- собирать PNG/GIF/MP4;
- проверять неизменность fixture;
- завершаться неуспехом при любом расхождении сценария или нарушении
  изоляции demo-mode.

## CI-требования

- В CI должен существовать workflow генерации demo assets на поддерживаемом
  product-owned recording path.
- CI не должен зависеть от VHS, `ttyd` и browser automation.
- CI должен проверять:
  - успешность записи;
  - наличие артефактов;
  - неизменность fixture;
  - отсутствие побочных изменений user-like state.

## Критерии приёмки

- Из чистого checkout можно сгенерировать demo assets одной поддерживаемой
  командой.
- Генерация использует только `demo`-fixture и in-memory runtime snapshot.
- Сценарий стабильно проходит без VHS и без browser-hosted recorder stack.
- PNG, GIF и MP4 создаются успешно и не пусты.
- После генерации physical fixture не изменён.
- После генерации normal user config не изменён.
- При падении сценария система сообщает шаг, ожидание и фактический кадр.
- Архитектура recorder-а допускает дальнейшее использование frame screenshots
  как visual evidence в тестовой инфраструктуре.
